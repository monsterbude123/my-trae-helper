# 质疑性校验协议 — Skeptical Validation Protocol

> **触发**: 任何技能升级、新建 P0/P1 缺陷修复、Agent 决策点、用户反馈验证。
> **核心立场**: 接受用户/子代理输入前，必须独立校验，不盲信。
> **本质**: 防止"看似合理的修复"实际是"矫枉过正"或"重复造轮子"。

---

## §0 触发场景

```
MUST 激活质疑性校验:
  - 用户提出 P0/P1 缺陷清单（任何"必须修"列表）
  - 用户提出升级方案（含具体修改点）
  - 子代理返回"完成"/"通过"声明
  - Agent 在两个方向间二选一时
  - 文档与现实疑似漂移（路径不存在 / 描述不符）

不适用:
  - 用户明确"按 X 执行"且 X 已通过质疑性校验
  - 纯文本查询（Read/Glob 不触发）
  - 子代理返回的 evidence 已附 file:line 且通过 Read 抽检
```

## §1 P0/P1 必要性质疑（来自 2026-08-10 my-trae-helper V10.12 升级会话蒸馏）

针对每个 P0/P1 主张，独立校验 4 维度：

### §1.1 根因验证

```
质疑: 这是真问题吗？还是衍生品？
检查:
  [ ] 引用的章节/SKILL.md 条款真实存在？（不要基于"应该存在"决策）
  [ ] 失效模式有真实证据？（用户反馈 / 日志 / 测试报告，不是"理论推断"）
  [ ] 根因不在更上游？（如果根因在 A，P0/P1 只修了 B，则修复是衍生品）

输出: 根因定位 file:line + 失效证据 + 影响面估算
```

### §1.2 责任主体校验

```
质疑: 这个修复应该改在哪个文件/哪一层？
检查:
  [ ] 改在当前层 vs 改在上游层，效果是否一致？
  [ ] 已有别的 skill/rule 是否已覆盖？（避免重复）
  [ ] 改在错误位置会导致什么？例如改在 SKILL.md 而项目级 rules/ 已有 = 重复

输出: 修复位置论证 + 拒绝方案 + 候选位置列表

反例: fullstack4TraeV10 §10 反向提示词"挂 implementer/reviewer 铁律" 
  → 质疑发现 reviewer.md L29-30 已有 ZERO TRUST + EVIDENCE MANDATORY 等价铁律
  → 改 reviewer.md = 冗余（这就是"矫枉过正"）
```

### §1.3 与已有规则重叠校验

```
质疑: 新加的规则和已有的规则是补强还是重复？
检查:
  [ ] 现有规则 grep 关键词，命中几处？
  [ ] 已覆盖章节的"反向提示词" / "NEVER" 是否已包含新主张？
  [ ] 新规则的"差异化"在哪里？必须说清楚"已有的没说 X，新加是为了 X"

输出: 重叠检查表 + 差异化论证

反例: §0.10 启动验证加"Playwright 截图 ≥1 张"
  → 质疑发现 acceptance-gates-v10.md §通过依据 [2] 已有同等约束
  → 但 §0.10 是 Phase 3.5 实施者层，[2] 是 Phase 4 Review 层 — 不重叠
  → 处理: §0.10 缩窄为"可见产物定义"，明示边界区分
```

### §1.4 修复成本 vs 价值校验

```
质疑: 这个修复值得做吗？
检查:
  [ ] 修复行数 / 影响范围（10 行 vs 100 行）
  [ ] 是否破坏 §11 铁律（Agent 文件遵循 vibe-coding-standards v2.5 弹性 100~350 行）
  [ ] 是否有更低成本的等价方案？（如文档引用优于内联）
  [ ] 修复能否被"挂载时机"取代？（如反向提示词写到铁律里 vs 写在文档里）

输出: 成本估算 + 替代方案 + 推荐处理（采纳 / 缩窄 / 取消）

反例: §10 反向提示词挂 reviewer.md 铁律
  → 成本: 改 reviewer.md 1 行
  → 价值: 0（已覆盖）
  → 推荐: 取消
```

## §2 通用质疑三层（防盲信）

### §2.1 问题质疑层

```
检查问题的"前提合法性":
  [ ] 错误前提: 用户/子代理描述基于不存在的路径 / 不存在的章节 / 不存在的规则
      → 不基于错误前提决策，直接指出
  [ ] 逻辑跳跃: "A 出错 → 必须修 B" 但 A 与 B 的因果没证明
      → 列出 A→B 的因果链，要求证据
  [ ] 信息缺失: 缺少必要的上下文（哪个项目 / 哪个版本 / 哪个文件）
      → 补全信息后再决策
```

### §2.2 方案质疑层

```
检查方案的"必要性 + 副作用":
  [ ] 必要性: 这个修复真的解决问题，还是治标不治本？
  [ ] 副作用: 改了这里，会不会破坏那里的约束？（如 §11 ≤10 条铁律 / 单文件 ≤800 行）
  [ ] 替代方案: 有没有更简单的做法？
  [ ] 优先级: 是 P0 还是 P1？敢不敢延后？
```

### §2.3 实施质疑层

```
检查实施的"可执行性 + 验证手段":
  [ ] 路径是否真实存在？（不是基于"应该存在"）
  [ ] 委派协议是否触发？（仅在 SKILL.md 写不算，挂到铁律才算）
  [ ] 验证手段是什么？（evidence 抽检 / phase-gate / 单元测试）
  [ ] 失败兜底: 改了之后回归测试怎么办？
```

## §3 强制声明格式（升级方案回报）

每次汇报升级方案前必须按质疑性校验声明：

```markdown
## 质疑性校验通过依据

### [1] 根因验证
- ✅/⚠️/❌ 引用的章节/SKILL.md 条款真实存在 — 证据: file:line
- ✅/⚠️/❌ 失效模式有真实证据 — 证据: 用户反馈/日志/测试报告

### [2] 责任主体校验
- ✅/⚠️/❌ 修复位置 vs 上游层效果一致 — 论证
- ✅/⚠️/❌ 已有 skill/rule 不覆盖 — grep 结果

### [3] 与已有规则重叠校验
- ✅/⚠️/❌ 现有规则 grep 不重叠 — grep 关键词
- ✅/⚠️/❌ 新规则差异化 — 一句话说明

### [4] 修复成本 vs 价值
- ✅/⚠️/❌ 修复行数 / 影响范围 — 数字
- ✅/⚠️/❌ 不破坏 §11 铁律 — 论证
- ✅/⚠️/❌ 替代方案已评估 — 列 1-2 个

结论: [1][2][3][4] 全 ✅ → 可执行 / 任一 ❌ → 修正方案
```

## §4 反例（V10.12 升级会话蒸馏）

### 反例 1: 盲信 P0 必要性

```
现象: 反馈会话列出 5 条 P0，主上下文未质疑直接采纳
后果: P0-2"反向提示词挂铁律"实际是冗余（已有等价铁律），属于矫枉过正
教训: P0/P1 必须按 §1.1-§1.4 四维度独立校验，不基于"用户列了就是 P0"
```

### 反例 2: 责任主体误判

```
现象: "Playwright MCP :filename Downloads 陷阱"反馈归属到 fullstack4TraeV10
实际: 陷阱是 MCP 工具行为，应归 .trae/skills/screenshot/ 或 .trae/rules/视觉证据铁律.md
教训: 修复前必须 §1.2 责任主体校验，不基于"反馈语境就改当前包"
```

### 反例 3: 与已有规则重叠未检出

```
现象: §0.10 启动验证加 "Playwright 截图 ≥1 张"
实际: acceptance-gates-v10.md §通过依据 [2] 已有同等约束
处理: 缩窄为"可见产物定义"，明示两层边界
教训: §1.3 grep 现有规则关键词是必做，不是可选
```

### 反例 4: AGENTS.md 路径漂移盲信

```
现象: AGENTS.md §187-234 写"`.trae/skills/skill-optimization-method/SKILL.md`"
实际: 路径不存在，真实文件在 `skill-markets/fullstack4TraeV10/references/skill-optimization-method.md`
教训: 引用任何路径前必须 Glob 验证，不基于"AGENTS.md 写的就存在"
```

### 反例 5: 验收"货不对版"盲信（V10.12 my-trae-helper）

```
现象: implementer 提交"模型管理"任务，evidence 是欢迎页截图
      reviewer 看到"有截图" → 放行
实际: evidence 与当前 feature 完全无关（货不对版）
      用户打开欢迎页看不到任何"模型管理"功能
根因: reviewer 跳过 §Step 2.5 产品侧验收，只看 evidence 路径不看内容
      AGENTS.md §10 "禁止编造 evidence" 有但未强制 reviewer 验证内容
教训: 验收必须按 §Step 2.5 三件必读（用户原文 + spec.md + evidence 实际内容）
      强制 3 问判定（需求归属 / 行为匹配 / 用户会认可吗）
      任一 ❌ → 失败分类标签 + 自动循环机制
```

## §6 验收门禁

```
升级方案汇报前自检:
  [ ] 已按 §3 强制声明格式回复
  [ ] 4 维度质疑校验全 ✅ 或显式标 ⚠️
  [ ] 任一 ❌ → 修正方案，不接受"P0 用户说了就必须做"借口

reviewer 验收升级:
  [ ] 主代理回复含 §3 格式声明
  [ ] 4 维度独立验证（不基于主代理自述）
  [ ] 反例 §4 的 4 种盲信模式已检查
```
