# 规则编写工艺

> 触发：编写新规则 / 修改已有规则 / 合并多条规则时生效。
> 核心：**每个规则 = 触发条件清晰 → 决策树全覆盖 → 异常分支 ≥ 条 → MUST/NEVER 双向约束。**

---

## §1 结构铁律（7 要素缺一不可）

```
每条规则必须包含以下 7 要素，缺失任一条 → 规则不合格：

1. 触发配置 — .mdc frontmatter 中 alwaysApply: true/false + description
2. 触发条件 — 正文中说明什么时候生效（"当用户要求 X / 当检测到 Y"）
3. 核心约束 — 1 句话概括规则灵魂
4. 决策树 — 覆盖所有分支，含兜底分支（"不确定 → 走 A"）
5. 异常处理表 — ≥ 1 个异常场景，每个含 [判定标准 + 处理动作]
6. MUST 清单 — 必须做什么
7. NEVER 清单 — 绝对不做什么
```

---

## §2 无死引用

```
规则文件间不写路径引用：
  ❌ "详见 strict.md §3"
  ❌ "参见 ../rules/视觉验收.md"
  ✅ "与视觉验收阶段形成闭环"（概念性关联即可）

原因: 所有规则自动加载到上下文，路径引用 = 噪音 + 文件名变更即断裂。
```

---

## §3 零概念重叠

### 3.1 检测标准

```
同一概念在 2 个文件中出现 > 1 句实质性描述 → 判定为重叠 → 必须消解。
```

### 3.2 消解规则

```
消解方式:
  1. 确定主归属方 — 哪个文件定义此概念的完整规则
  2. 对端压缩 — 非主归属方只留 1 句核心约束 + 概念名
  3. 不复制细节 — 不写主归属方已有的决策树/参数/操作步骤

示例:
  主归属方: gitnexus-铁律.mdc（定义完整的 impact/detect_changes 流程）
  对端 (strict.mdc): "修改代码前 → impact() → 汇报风险等级"（仅此一句，不展开）
```

---

## §4 决策树全覆盖

### 4.1 分支原则

```
每个决策点必须覆盖至少以下 4 路:
  1. 正常路径 — 理想情况
  2. 降级路径 — 工具不可用/超时
  3. 模糊路径 — 判断条件不明确时的兜底行为
  4. 阻断路径 — 什么情况必须停止

若某路在当前规则不适用 → 显式标注 "N/A（原因）"，不可遗漏。
```

### 4.2 可执行判定

```
决策树每个分支条件必须是 AI 可机械判断的客观标准：
  ❌ "如果结果质量不高"
  ✅ "如果返回结果缺少 spec/proposal/contracts 中任一必须章节"
  ❌ "如果 agent 表现不好"
  ✅ "同一 agent 连续 2 次委派均未通过门禁"
```

---

## §5 异常处理表规范

```
异常表每行 3 列:
  | 异常场景 | 判定标准（客观可测） | 处理动作（具体操作） |

"判定标准" 和 "处理动作" 不允许出现:
  ❌ "酌情处理"
  ❌ "根据情况判断"
  ❌ "适当调整"
  ✅ "补充缺失部分，不重新委派完整任务"
  ✅ "引用 spec 原文指出偏差点，退回修正"
```

---

## §6 死引用检测清单（7 类）

| # | 检测项 | 正则检测 |
|---|--------|---------|
| 1 | 路径引用 | `详见\|参见.*\.md\|完整版详见` |
| 2 | 错项目名 | 搜索非当前项目的项目名 |
| 3 | 错仓库路径 | 搜索非当前项目的目录路径 |
| 4 | 不存在的 agent 名 | 搜索文档中引用的 agent 是否实际存在 |
| 5 | 不存在的规则文件名 | 搜索 "xxx.mdc" 是否在 rules/ 目录 |
| 6 | 不存在的 MCP 工具名 | 交叉校验 mcp.json |
| 7 | 硬编码路径 | 搜索 Windows/Linux 绝对路径 |

---

## §7 正反约束必须成对

```
每类行为必须有正向（MUST）和反向（NEVER）：
  ✅ "MUST: 修改代码前 → impact()"
  ✅ "NEVER: GitNexus 可用时降级为 grep/glob"
  
单一方向 = 规则不完整：
  ❌ 只有 "MUST 用 GitNexus" 无 NEVER → AI 不知道 GitNexus 失败时能不能用 grep
  ❌ 只有 "NEVER 跳过 DOC SYNC GATE" 无正向 → AI 不知道 DOC SYNC GATE 具体是什么
```

## §8 编写后自检

```
规则编写完成后，逐条验证:

  [ ] 触发配置正确？（alwaysApply: true/false 符合规则性质？description 足够描述触发场景？）
  [ ] 触发条件明确？（AI 能否判断何时激活此规则？）
  [ ] 决策树有兜底分支？（遇到"不确定"情况有明确行为？）
  [ ] 异常处理每行有判定标准？（AI 能否机械判断"何时触发此行"？）
  [ ] 每条禁止有替代方案？（NEVER 后面跟着"应该怎么做"？）
  [ ] 全文无路径引用？（搜索 "详见" "参见" ".md" 确认）
  [ ] 全文无错项目名？
  [ ] 与 strict.mdc 无 > 1 句的概念重叠？
  [ ] 硬编码路径已替换为变量或概念描述？
```

## §9 AGENTS.md 专项纪律

> AGENTS.md = 快速操作地图；rules/ = 行为约束引擎。职责不同。

AGENTS.md 应包含: 项目定位 / 启动命令 / 目录地图 / 关键入口 / 特有约定。
AGENTS.md 不应包含: 规则/铁律 / 决策树 / MUST/NEVER 清单 / 工具教学 / 自动生成的过期数据。

```
上下文预算: 硬上限 120 行（v2.5 放宽 +50%），理想值 50-80 行。
自检: ≤120 行？无铁律/决策树/过期数据？含启动命令+目录地图？
```

## §10 规则触发配置（.mdc frontmatter）

触发类型选择:
```
├── alwaysApply: true  → 每次加载全文（核心门禁/GitNexus/编码心法/委派/项目约束 ≤5个）
├── alwaysApply: false → 按需加载（测试/视觉/原型/路径/规则编写）
└── Manual → 用户手动 @mention（可选参考）
```

Frontmatter 模板:
```yaml
---
description: {触发场景描述}
alwaysApply: {true|false}
enabled: true
updatedAt: {ISO 8601}
provider:
---
```

**Always 规则 ≤ 5 个**。当前推荐: strict / gitnexus-铁律 / 编码心法 / agent协调协议 / 项目核心。

## §11 禁止行为

| 禁止 | 替代 |
|------|------|
| 规则中引用其他规则文件路径 | 概念性关联（"与 X 阶段形成闭环"） |
| 同一概念在多文件重复展开 | 确定主归属方，对端只留 1 句核心约束 |
| 决策树有分支遗漏 | 显式标注 "N/A（原因）"，补齐 4 路 |
| 异常处理用模糊词（酌情/适当/根据情况） | 客观判定标准 + 具体操作步骤 |
| 只有 MUST 没有 NEVER | 成对出现 |
| 硬编码项目名/路径 | 概念描述或变量化 |
| 新增规则前不检测是否与已有规则重叠 | 先用自检清单 + 搜索已有规则中的关键词 |
| 规则使用 .md 而非 .mdc | .mdc 才有 frontmatter 触发控制 |

## §12 Context Engineering 5 Pillar 联动（2026-08-14 增量）

> 来源：[external-report 2026-08-14 §M-03](../2026-08-14/external-report.md)

规则文件最容易踩 **5 Pillar 之 4.相关代码示例** 缺失——只写抽象约束("必须重命名")不写 good/bad 对比,agent 看不懂"什么样的算合格"。

**最小可行示例**(每个 MUST/NEVER 至少配 1 个):

```markdown
✅ 允许:  §GitNexus: rename symbolName → 用 call graph 批量替换调用点
❌ 禁止:  §GitNexus: rename symbolName → 用 shell sed -i 全仓替换
反例:     上一季度因为 sed -i 重命名,跨 8 个文件的动态调用未更新,CI 全红
```

**反例**:只写 "用 gitnexus rename" → agent 不知道"为什么不用 sed" → 还是会选错的。**对比 + 反例 = 真实可参考的范例,胜过抽象描述 10×**。

**关联**:本文件 §1 结构铁律的 5 Pillar 维度——示例属于"内容质量"而非"结构"。结构对了但内容空,agent 仍然失灵。
