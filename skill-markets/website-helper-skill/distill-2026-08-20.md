## §2 .env 解析三重坑（最常见）

### 2.1 引号剥离

| 来源 | 行为 |
|------|------|
| `store._parse_env_file` (publish) | **不剥引号**，原样保存 |
| Windows 上 PowerShell `Out-File` 默认加双引号 | `"C:\Users\xxx\.ssh\id_rsa"` |
| paramiko `from_private_key_file` | 把字符串当文件名打开 → `OSError [Errno 22]` |

**解法**：自己重写 parser，剥首尾匹配 `'`/`"`：

```python
def _strip(s):
    if s is None: return None
    s = s.strip()
    if len(s) >= 2 and s[0] in '"\'' and s[-1] == s[0]:
        s = s[1:-1]
    return s or None
```

### 2.2 字段优先级陷阱

publish `load_ssh_config` **优先级是 `key_path > password`**——只要 `key_path` 非空就走密钥。如果你想改密码、但前一行定义了 `SSH_KEY_PATH`，**根本不会 fallback 到 password**。

**解法**：临时切换时把 `SSH_KEY_PATH=` 这一行**注释掉**，不是清空，因为空字符串仍是 `"" not None`。

### 2.3 跨项目 .env 污染

`d:\workspace\my-trae-helper\.env` 不是 publish 独有——本项目里 [doc-map-manager / minimax-multimodal 等多个工具](file:///d:/workspace/my-trae-helper/skill-markets/CAPABILITY-MAP.md) 都在它里面写自己的字段。

publish 自己有优先 fallback `~/.publish/config.yaml` —— `publish config dns` 与 `publish config ssh` 把它当 header 交互式重写 → **绕过 .env 污染**。

## §3 publish deploy 是耦合单元，反代场景必须拆原子

publish 的 `cli.py deploy` 是一个"上帝命令"——四步流水（DNS + webroot tar + nginx root + SSL）。设计假设 webroot 是**静态文件目录**。反代场景三大碰撞：

| 耦合点 | 代码位置 | 反代场景的问题 | 拆原子解法 |
|--------|---------|--------------|-----------|
| webroot **强校验** | `utils/validators.py:44` `validate_webroot` | 必须 `path.exists()` | 用 publish 的 `_get_dns_provider` + `request_cert` 单独调 |
| nginx 模板**写死 root** | `nginx/config.py:generate_server_block` | 不能反代 `:8088` | 自己写 `proxy_pass http://127.0.0.1:8088` |
| `with_ssl=True` 默认嵌进 deploy | `nginx/deploy.py:37` | 一次部署混杂 root + ssl | 拆 SSL 走 certbot standalone |

**正确拆解**：

```python
# DNS
dns = _get_dns_provider(load_dns_config())
dns.create_record(subdomain, ip)

# Nginx 反代（自己 SSH 写 /etc/nginx/sites-available/$sub.conf 或宝塔目录）
with SshClient(ssh_cfg) as ssh:
    ssh.exec_command("cat > /etc/nginx/sites-... << EOF\n...EOF")

# SSL
request_cert(ssh, subdomain)  # certbot --standalone（避开 nginx 插件）
```

## §4 宝塔 / 自定义 nginx 环境的"vhost 不读 sites-enabled"陷阱

### 4.1 现象

用户访问 `https://<子域>.<域>/` → **404 Not Found** 且响应头 `server: nginx` + `content-length: 138`。

但 `curl` 直连后端 `<server>:8088` 正常 302 install.php → 200。

### 4.2 真因

宝塔 Linux 自带 nginx (`/www/server/nginx/conf/nginx.conf`)，`include` 顺序里**没有** `sites-enabled`，而是读：

```nginx
include /www/server/panel/vhost/nginx/*.conf;
```

→ 写到 `/etc/nginx/sites-available/*.conf` + `/etc/nginx/sites-enabled` 是**原生 nginx 习惯**，宝塔环境不生效；落到 `server_name _` 默认 server → 138B placeholder。

### 4.3 验证命令

```bash
nginx -T 2>&1 | grep -E 'server_name\s+子域名'
```

没结果 = **配置没被加载**。

### 4.4 解法

写到 `/www/server/panel/vhost/nginx/<子域>.conf`，宝塔会**自动 include**。

### 4.5 引申：每个 nginx-based 工具都有自己的 include 目录

| 工具 | include 路径 |
|------|----------|
| 原生 nginx (Debian/Ubuntu) | `/etc/nginx/sites-enabled/` |
| 宝塔 nginx | `/www/server/panel/vhost/nginx/` |
| cPanel nginx | `/etc/nginx/conf.d/` |
| DirectAdmin | `/usr/local/directadmin/data/users/<user>/nginx.conf` |
| OpenLiteSpeed | `/usr/local/lsws/conf/vhosts/<vhost>/vhost.conf` |

**部署前先 explore** include 路径——别上手就 sites-enabled。

## §5 zentao 18.5 首次部署交付模板

### 5.1 docker-compose.yml（实战通过版）

```yaml
version: "3.8"
services:
  zentao:
    image: hub.zentao.net/app/zentao:18.5
    container_name: zentao
    restart: always
    ports:
      - "127.0.0.1:8088:80"   # 关键：127.0.0.1 反代用，外网直接 8088 不安全
    volumes:
      - zentao_data:/data
      - zentao_app:/app
    environment:
      MYSQL_HOST: db
      MYSQL_PORT: "3306"
      # 关键：18.5 启动时 ZenTao init wizard 会用 root 登录 + 自建 zentao user
      # 所以这里用 root 凭证，而不是预建 zentao user
      MYSQL_USER: root
      MYSQL_PASSWORD: <root_mysql_password>
      ZENTAO_ADMIN_USER: admin
      ZENTAO_ADMIN_PASSWORD: <random_22char_urlsafe>
    depends_on:
      db:
        condition: service_healthy
  db:
    image: mysql:5.7
    container_name: zentao-db
    restart: always
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_unicode_ci
    environment:
      MYSQL_ROOT_PASSWORD: <root_mysql_password>
    volumes:
      - zentao_db:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "root", "-p<root_mysql_password>"]
      interval: 10s
      timeout: 5s
      retries: 12
volumes:
  zentao_data:
  zentao_app:
  zentao_db:
```

### 5.2 关键踩坑

| 错配 | 现象 | 修复 |
|------|------|------|
| `MYSQL_USER: zentao` + `MYSQL_PASSWORD: ...` | `ERROR 1045 Access denied for user 'zentao'@'172.20.0.X'` | 改用 `root`（禅道 wizard 会自建库与用户）|
| `version: 3.8` 但 docker compose v2 不识别 | `compose down -v` 不重建命名卷 | 保持 `version: "3.8"` |
| 把 8088 绑到 `0.0.0.0` | 反代无效 + 额外攻击面 | 用 `127.0.0.1:8088` |

### 5.3 凭据存放

**强建议**：

```
/root/.zentao-credentials   # chmod 600
ZENTAO_ADMIN_PASSWORD=...
MYSQL_ROOT_PASSWORD=...
```

不要写到入仓路径、git 不查的 logs 下。

### 5.4 安装向导字段（用户在浏览器填）

| 字段 | 值 |
|------|---|
| 数据库主机 | `db`（docker 网络名） |
| 数据库端口 | `3306` |
| 数据库用户名 | `root` |
| 数据库密码 | `<root_mysql_password>` |
| 数据库名 | `zentao` |
| 表前缀 | `zt_` |
| 管理员 | 用户自填（不是你给的密码 ！禅道 wizard 自己 hash+salts） |

### 5.5 教训

⚠ **禅道 18.5 没有运行时默认初始密码**——管理员密码是 wizard 那一刻哈希进数据库的，不在 docker 容器 env 里。**不要尝试寻找或猜测默认值**。

## §6 凭据伦理与污染检测（部署自动化铁律）

### 6.1 三条永不破

```
1. 绝不打 .env 字段值（即使只是用于诊断）
2. 绝不回显 SSH 密码到对话（即使 .env 已 chmod）
3. 绝不"自动续用"上一轮的密码（即使是同一项目）

例外: 用户显式 request "给我密码清单"，且仅一次性写到聊天
      + 远端存在 /root/.zentao-credentials chmod 600 双备份
      + 用户 prompt 里确认已抄写
```

### 6.2 .env 污染检测

当 `.env` 字段前缀混乱（如 SSH_HOST 写真值 + doc-map-manager 写 chromadb 配置），导致 publish 工具解析到非预期值：

```bash
# 只看 key 一栏（不读 value）
grep -E '^[A-Z]' .env | cut -d= -f1
```

### 6.3 credential-management.md §5 应急路径
