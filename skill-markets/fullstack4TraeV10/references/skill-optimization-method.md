# 技能包优化方法论

> 触发：用户对技能包"觉得太重/臃肿"、"想精简"、"要瘦身"、"想优化升级"。
> 核心：精简 ≠ 降级。优化的目的是更好用，至少不能开倒车。

---

## §0 十铁律（核心）

```
1. 体积诊断先行 — 优化前必须测量总体积 + 定位膨胀模块 TOP 5
2. 根因分层分析 — 不能只说"太重"，必须拆出 3+ 个具体根因
3. 外部对标必做 — 设计新协议前必须调研业界标准（≥3 个对标对象）
4. 方案分级提案 — 至少给 2 个方向 + 每个的优缺点 + 适用场景
5. 决策点前置 — 关键选择让用户决定，不是自己闷头做
6. 核心价值保底 — 精简必须保留不可协商的核心价值
7. 全量缺口对照 — 新版本必须逐项对照旧版本的所有能力
8. 三级缺口分级 — 缺口分 MUST FIX / SHOULD ADD / ACCEPTABLE
9. 最小修复原则 — 不重建复杂度，只补齐 MUST 项
10. 门禁显式化 — 质量门禁必须写得可执行（命令/检查项/阈值）
```

---

## §1 五步流程

```
Step 1: 体积诊断 → 测量总体积（文件数 + KB）+ 定位 TOP 5 膨胀模块 + 识别最大文件（≥15KB 必须标记）
Step 2: 根因分析 → 拆出 3+ 个具体根因 + 每个根因标记影响占比
Step 3: 外部对标 → 调研 ≥3 个业界标准 + 记录哲学 + 判断是否可替代自定义协议
Step 4: 方案提案 → 至少 2 个方向 + 优缺点 + 让用户选关键决策
Step 5: 缺口对照 + 修复 → 逐项对照 + 分级 + 只补 MUST 项 + 验证体积 ≤ 目标
```

---

## §2 三级缺口判定标准

| 级别 | 判定标准 | 处理方式 |
|------|---------|---------|
| **MUST FIX** | 影响核心流程可执行性 | 必须补，否则不发版 |
| **SHOULD ADD** | 明显提升质量 | 应该补，但可延后 |
| **ACCEPTABLE** | 合理精简，不影响核心价值 | 不补 |

## §3 反例

```
反例 1: 膨胀式"吸收经验" — 以"吸收实战经验"为名给技能包 +1265 行
  后果: 上下文击穿，违反"简洁反臃肿"原则
  教训: 反例价值 > 正例价值；MUST 通用方法论，NEVER 项目特定解决方案

反例 2: 矫枉过正式规则堆砌 — 子代理不加载规则，主代理内联大量规则到委派 prompt
  后果: prompt 膨胀 + 进一步上下文击穿
  教训: 解决机制问题（如宪法式加载），而非堆砌规则；委派 prompt ≤1KB

反例 3: 跳过外部对标就设计新协议 — 自定义"五阶段门禁链"，未调研业界
  后果: 重复造轮子 + 与业界脱节
  教训: 设计前 MUST 调研 ≥3 个业界标准
```

## §4 触发场景

```
用户说: "这个技能包太重了" / "想精简" / "要瘦身" / "想优化升级" / "要新建 V 版本替代旧版本"

你执行: 1.体积诊断 → 2.根因分析 → 3.外部对标 → 4.方案提案（让用户选）→ 5.缺口对照（只补 MUST 项）
```
