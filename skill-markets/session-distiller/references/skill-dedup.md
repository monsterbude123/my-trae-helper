# 技能去重检查详细指南

> 确保蒸馏会话后不会产生重复技能，避免项目技能库混乱。
>
> **核心原则**: 内容优先 — 先分析会话定位，再针对性匹配已有技能。

---

## 零、正确的去重流程 (内容优先)

> **为什么必须"内容优先"?**
> 因为只有先理解会话解决的是什么问题，才能知道要去匹配哪个已有技能。
> 盲目扫描所有技能既浪费算力又可能误判。

### 0.1 内容优先的去重流程

```
Step 1 — 分析会话内容定位 (先做这个!)
  ├─ 提取会话核心主题
  │   └─ 例: "反复道歉治理"
  ├─ 识别解决的问题
  │   └─ 例: "Agent 反复道歉但无效,缺少失败分析"
  ├─ 提炼方法论关键词
  │   └─ 例: ["失败计数", "切换 agent", "阻塞报告"]
  └─ 生成"会话主题指纹"

Step 2 — 带着主题指纹去扫描已有技能
  ├─ 扫描 .trae/skills/ + skill-markets/ + 全局 skills/
  ├─ 用核心主题过滤 → 找到候选技能
  │   └─ 例: 包含"道歉"关键词的技能
  └─ 对候选技能计算相似度

Step 3 — 针对性匹配
  ├─ 匹配核心主题 → 找到候选技能
  ├─ 匹配解决的问题 → 缩小范围
  └─ 匹配方法论关键词 → 确认相似度

Step 4 — 决策路径
  ├─ 无匹配 → 继续蒸馏 → 生成新技能
  ├─ 有匹配 + 有增量价值 → 更新已有技能
  └─ 有匹配 + 无增量价值 → 跳过,告知用户
```

### 0.2 为什么旧流程是错的

```
❌ 旧流程 (先扫描技能):
  1. 扫描所有已有技能 → 100+ 个技能
  2. 对每个技能计算相似度 → 浪费算力
  3. 盲目匹配 → 可能误判

问题:
  - 不知道要匹配什么,盲目计算所有技能的相似度
  - 项目有 100 个技能,就要做 100 次相似度计算
  - 可能匹配到不相关的技能,产生误判

✅ 新流程 (内容优先):
  1. 先分析会话 → 提取"反复道歉治理"主题
  2. 带着主题去扫描 → 只匹配包含"道歉"的技能
  3. 精准定位 → 发现已有 apology-discipline
  4. 增量判断 → 决定合并还是跳过

优势:
  - 明确知道要匹配什么
  - 只对相关技能做相似度计算
  - 精准定位,不会误判
```

## 一、为什么去重至关重要

### 1.1 真实问题场景

```
会话 1: "反复道歉" → 蒸馏出 "apology-discipline" 技能
会话 2: "反复道歉" → 又蒸馏出 "repeat-apology" 技能
会话 3: "反复道歉" → 再蒸馏出 "agent-apology-fix" 技能

结果:
  - 同一个问题有 3 个技能
  - 铁律重复定义
  - 用户不知道用哪个
  - 维护成本 × 3
```

### 1.2 去重的价值

```
无去重:
  - 技能数量爆炸
  - 相似技能混淆
  - 维护成本线性增长

有去重:
  - 技能数量收敛
  - 一个问题一个技能
  - 增量更新,质量提升
```

## 二、相似度判定算法

### 2.1 四维相似度检查

```
维度 1: 核心主题相似度
  ├─ 提取技能的 name + description
  ├─ 分词 + 去停用词
  ├─ 计算关键词重合度
  └─ 公式: 重合关键词数 / max(关键词数)

维度 2: 触发词相似度
  ├─ 提取 triggers 列表
  ├─ 计算重叠比例
  └─ 公式: 重叠触发词数 / max(触发词数)

维度 3: 解决的问题相似度
  ├─ 提取技能解决的问题域
  ├─ 判定是否解决同一问题
  └─ 布尔值: 是/否

维度 4: 方法论相似度
  ├─ 提取铁律 (MUST/NEVER)
  ├─ 计算铁律重合度
  └─ 公式: 重合铁律数 / max(铁律数)
```

### 2.2 相似度阈值

```
综合相似度计算:
  综合相似度 = (主题相似度 × 0.4)
             + (触发词相似度 × 0.2)
             + (问题相似度 × 0.3)
             + (方法论相似度 × 0.1)

判定标准:
  ├─ 综合相似度 ≥ 80% → 高度相似 → 必须合并
  ├─ 综合相似度 50%-80% → 中度相似 → 建议合并
  └─ 综合相似度 < 50% → 低相似 → 可新建
```

## 三、合并策略详解

### 3.1 三种决策路径

| 场景 | 条件 | 决策 | 动作 |
|------|------|------|------|
| **新建** | 无相似技能 或 相似度 < 50% | 创建新技能 | 正常蒸馏流程 |
| **合并** | 有相似技能 + 新会话有增量价值 | 更新已有技能 | 补充增量内容 |
| **跳过** | 有相似技能 + 无增量价值 | 跳过蒸馏 | 告知用户"已有相似技能" |

### 3.2 增量价值判定

```
新会话有以下之一 → 有增量价值:
  1. 新的铁律 (MUST/NEVER)
  2. 新的反例 (失败案例)
  3. 新的方法论 (验证方法)
  4. 更详细的流程 (Step 细化)
  5. 补充边界条件 (适用/不适用场景)

全无 → 无增量价值
```

### 3.3 合并执行协议

```
发现相似技能 + 有增量价值 → 执行合并:

Step 1 — 读取已有技能
  └─ Read {skill-name}/SKILL.md

Step 2 — 识别增量内容
  ├─ 对比新会话提炼的铁律 vs 已有铁律
  ├─ 对比新会话的反例 vs 已有反例
  └─ 识别新增部分

Step 3 — 确定合并位置
  ├─ 新铁律 → 补充到 SKILL.md §N
  ├─ 新反例 → 补充到 references/traps.md
  ├─ 新方法论 → 补充到 references/methodology.md
  └─ 新流程 → 细化对应 Step

Step 4 — 执行合并
  └─ Edit 已有技能文件

Step 5 — 输出合并报告
  ├─ 合并了哪些内容
  ├─ 更新了哪些文件
  └─ 版本号升级建议
```

## 四、实战示例

### 示例一: 高度相似 → 合并

```
已有技能: apology-discipline
  - name: "apology-discipline"
  - description: "反复道歉治理 — 失败计数 + 切换 agent + 阻塞报告"
  - triggers: ["反复道歉", "道歉", "失败计数"]

新会话提炼: agent-apology-fix
  - 核心主题: 反复道歉
  - 触发词: 反复道歉、道歉、agent 道歉
  - 解决的问题: Agent 反复道歉但无效
  - 铁律: 连续失败 ≥ 2 次 → 切换 agent

相似度计算:
  - 核心主题: 100% (都是"反复道歉")
  - 触发词: 66% (2/3 重叠)
  - 解决的问题: 100% (相同问题)
  - 方法论: 80% (铁律相似)

综合相似度: 0.4×1.0 + 0.2×0.66 + 0.3×1.0 + 0.1×0.8 = 88.4%

判定: 高度相似 → 合并

增量内容:
  - 新铁律: "道歉必须配具体改进方案"
  - 新反例: "2026-05-16 搜索框盲目重试"

合并执行:
  - Edit apology-discipline/SKILL.md
  - 补充 §N 新铁律
  - Edit apology-discipline/references/traps.md
  - 补充新反例
```

### 示例二: 中度相似 → 评估后决策

```
已有技能: code-review-discipline
  - name: "code-review-discipline"
  - description: "代码审查铁律 — 影响面评估 + 漂移检测 + 完成审计"
  - triggers: ["代码审查", "review", "影响面"]

新会话提炼: code-merge-gate
  - 核心主题: 代码合并门禁
  - 触发词: 代码合并、merge、门禁
  - 解决的问题: 防止不合格代码合并
  - 铁律: 无测试禁止合并

相似度计算:
  - 核心主题: 40% (代码审查 vs 代码合并)
  - 触发词: 20% (1/5 重叠)
  - 解决的问题: 50% (代码质量,但角度不同)
  - 方法论: 30% (部分铁律相似)

综合相似度: 0.4×0.4 + 0.2×0.2 + 0.3×0.5 + 0.1×0.3 = 38%

判定: 低相似 → 可新建

决策: 新建独立技能 "code-merge-gate"
```

### 示例三: 无增量价值 → 跳过

```
已有技能: test-blocking-resolver
  - name: "test-blocking-resolver"
  - description: "测试阻塞解决 — 分区定位 + 坏测试识别"
  - 铁律: 分区测试 + 连续失败阻塞报告

新会话提炼: test-partition-runner
  - 核心主题: 测试分区运行
  - 解决的问题: 测试阻塞定位
  - 铁律: 分区测试 + 连续失败阻塞报告

相似度: 95%

增量检查:
  - 新铁律? → 无
  - 新反例? → 无
  - 新方法论? → 无

判定: 无增量价值 → 跳过

决策: 告知用户"已有相似技能: test-blocking-resolver,无增量价值,跳过蒸馏"
```

## 五、去重检查清单

蒸馏会话后,强制执行以下检查:

```
[ ] Step 1 — 扫描已有技能
    ├─ 扫描 .trae/skills/
    ├─ 扫描 skill-markets/
    └─ 提取每个技能的核心特征

[ ] Step 2 — 计算相似度
    ├─ 核心主题相似度
    ├─ 触发词相似度
    ├─ 问题相似度
    └─ 方法论相似度

[ ] Step 3 — 判定决策
    ├─ 综合相似度 ≥ 80% → 合并
    ├─ 综合相似度 50%-80% → 评估
    └─ 综合相似度 < 50% → 新建

[ ] Step 4 — 执行决策
    ├─ 合并 → Edit 已有技能
    ├─ 新建 → Write 新技能
    └─ 跳过 → 告知用户

[ ] Step 5 — 输出去重报告
    └─ 包含在 Completion Report 中
```

## 六、常见问题

### Q1: 如果两个技能都有价值,但角度不同怎么办?

```
答: 判定为"中度相似" → 独立维护,但在各自的 SKILL.md 中交叉引用。

示例:
  - code-review-discipline (审查铁律)
  - code-merge-gate (合并门禁)

在 code-merge-gate 中补充:
  "前置条件: 参考 code-review-discipline 的审查铁律"
```

### Q2: 如何判断"增量价值"是否真的有价值?

```
答: 增量价值必须满足:
  1. 具体可执行 (不是空泛建议)
  2. 有反例支撑 (有失败案例)
  3. 未在已有技能中出现 (真增量)

否则视为"伪增量" → 跳过
```

### Q3: 合并后版本号如何更新?

```
答: 小版本号升级:
  - 补充铁律: x.X.0 → x.X+1.0
  - 补充反例: x.X.Y → x.X.Y+1
  - 补充方法论: x.X.0 → x.X+1.0

示例:
  - apology-discipline V2.0.0 → 补充新铁律 → V2.1.0
```

## 七、模板与工具

### 去重检查脚本 (伪代码)

```python
def check_skill_duplication(new_skill, project_skills_dir):
    """去重检查主流程"""

    # Step 1: 扫描已有技能
    existing_skills = scan_existing_skills(project_skills_dir)

    # Step 2: 计算相似度
    for skill in existing_skills:
        similarity = calculate_similarity(new_skill, skill)

        if similarity >= 0.8:
            # Step 3: 判定为高度相似
            increment_value = check_increment_value(new_skill, skill)

            if increment_value:
                # Step 4: 合并
                merge_skills(skill, new_skill)
                return "merged", skill.name
            else:
                # Step 5: 跳过
                return "skipped", skill.name

    # Step 6: 无相似技能 → 新建
    return "created", new_skill.name

def calculate_similarity(skill1, skill2):
    """计算四维相似度"""
    theme_sim = calculate_theme_similarity(skill1, skill2)
    trigger_sim = calculate_trigger_similarity(skill1, skill2)
    problem_sim = calculate_problem_similarity(skill1, skill2)
    method_sim = calculate_method_similarity(skill1, skill2)

    return (theme_sim * 0.4 + trigger_sim * 0.2 +
            problem_sim * 0.3 + method_sim * 0.1)
```

> **核心要义**: 去重不是"删减",而是"收敛"。通过相似度判定 + 增量价值检查 + 智能合并,确保一个项目针对一类问题只有一个权威技能,质量持续提升而非数量爆炸。
