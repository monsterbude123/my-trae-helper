# 20-development / 变更管理流程

> **定位**：所有"改"的入口。区分小/中/大变更，分流到不同流程。
>
> **何时加载**：用户说"改动"/"修改"/"重构"/"紧急修复"时。

---

## 一、核心原则

**变更不是"偷偷改一下"，而是"有意识地调整知识系统"。**

每次变更都涉及两个系统：代码系统和文档系统。变更管理的目标是确保两个系统同步演进。

---

## 二、变更分类

| 类型 | 定义 | 流程 |
|------|------|------|
| 小变更 | ≤3 文件，≤50 行，单模块内，无接口变更 | 轻量流程 |
| 中变更 | >3 文件或跨模块，有接口/模型变更 | 标准四阶段 |
| 大变更 | 跨模块架构调整，技术选型变更 | 标准四阶段（fullstack-planner 架构模式） |

---

## 三、小变更流程

**适用条件**（必须全部满足）：
- 修改文件 ≤ 3
- 代码变更 ≤ 50 行
- 仅限单模块内
- 无公开接口签名变更
- 无数据模型变更

```
识别变更需求
    ↓
1. 更新模块文档
   ├── 接口契约表（如有行为变更）
   ├── 变更记录（添加一行）
   └── 版本号（修订版本 +1）
    ↓
2. 实施代码变更（TDD）
    ↓
3. 验证
   ├── 测试通过
   └── 文档一致性快速检查
    ↓
4. 完成
```

**不需要**：完整的文档影响清单、同步报告、一致性验证报告。

---

## 四、中变更流程

**适用条件**（任一满足）：
- 修改文件 > 3
- 跨模块
- 接口签名变更
- 数据模型变更

走标准四阶段流程：

```
① PLAN（10-design/planning.md）
   ├── 输出文档影响清单
   └── 苏格拉底式澄清
    ↓
② DOC SYNC（20-development/doc-sync-protocol.md）
   ├── P0 同步：接口契约 + 数据模型
   └── P1 同步：关联模块、版本号
    ↓
③ TDD CODE（20-development/tdd-workflow.md）
   └── 🔴RED → 🟢GREEN → ♻️REFACTOR
    ↓
④ VERIFY & CLOSE（40-acceptance/）
   ├── 代码审查
   ├── 验证门禁
   └── 一致性验证报告
```

---

## 五、大变更流程

**适用条件**（任一满足）：
- 架构调整（模块拆分/合并/新增）
- 技术选型变更
- 跨 3 个以上模块

```
1. fullstack-planner 切换到架构模式
   ├── 现状分析
   ├── 权衡分析
   └── ADR 记录到 docs/DECISIONS.md
    ↓
2. fullstack-planner 接手
   ├── 标准四阶段流程
   └── 逐模块实施
    ↓
3. 逐模块执行
   ├── 每个受影响模块独立走 DOC SYNC → CODE → VERIFY
   └── 模块间依赖按依赖矩阵顺序处理
    ↓
4. 全局验证
   ├── 所有模块一致性验证
   ├── 架构文档更新
   └── 依赖矩阵更新
```

---

## 六、紧急修复流程

**适用场景**：线上 Bug，需要立即修复，来不及走完整流程。

```
紧急 Bug
    ↓
1. 快速修复代码（TDD 仍然必须）
    ↓
2. 验证修复有效
    ↓
3. 同步文档（可延后，但必须在同一工作会话内完成）
   ├── 模块文档变更记录
   └── 如涉及接口变更 → 接口契约表
    ↓
4. 补充文档影响清单（事后补充）
```

**关键原则**：紧急修复可以跳过"编码前同步文档"，但**不能跳过"编码后同步文档"**。

---

## 七、变更影响分析

每次变更前，需要评估两个维度的影响：

### 文档影响（必做）

| 维度 | 问题 | 行动 |
|------|------|------|
| 模块文档 | 接口/模型是否变更？ | 更新接口契约/数据模型 |
| 关联模块 | 下游模块是否受影响？ | 校验兼容性 |
| 架构文档 | 模块关系是否变化？ | 更新依赖矩阵 |
| ADR | 是否涉及架构决策？ | 记录决策 |

### 代码影响（如涉及现有代码修改）

使用代码分析工具或 grep 评估：
- 修改的符号被哪些地方调用
- 是否有 d=1 的直接依赖需要同步更新
- HIGH/CRITICAL 风险必须先警告用户

---

## 八、变更单号

重大变更建议分配变更单号，格式：`CHG-{日期}-{序号}`

示例：
- `CHG-20260507-001` — 2026 年 5 月 7 日第 1 个变更

变更单号记录在模块文档的变更记录表中，便于追溯。

---

## 九、变更回退

如果变更需要回退：

```
1. Git revert 回退代码
    ↓
2. 同步回退文档
   ├── 恢复接口契约到变更前状态
   ├── 恢复数据模型描述
   └── 添加回退变更记录
    ↓
3. 验证回退后的文档一致性
```

**关键**：代码回退，文档也必须同步回退。不能出现"代码是旧版，文档是新版"的不一致状态。
