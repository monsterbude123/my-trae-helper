# 50-debugging / 系统化调试（根因优先 + TDD 轴心修复）

> **定位**：Bug 修复的工程化流程。出 Bug 时反向触发，文档同步回退到 20-development。
>
> **何时加载**：用户说"调试"/"bug"/"报错"/"失败"/"出问题"/"fix"时。

---

## 一、铁律（The Iron Law）

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
没有根因调查，就不要尝试修复

NO ROOT CAUSE WITHOUT VERIFIABLE EVIDENCE
根因必须有可验证的证据

NO FIX CODE WITHOUT A FAILING TEST FIRST (🔴RED)
没有失败测试，就不要尝试修复
```

**随机修复浪费时间并制造新 bug。快速补丁掩盖根本问题。没有测试的修复无法防止回归。**

- 没完成阶段 1 的调查，不能提修复方案
- 没写出 🔴 RED 确认的失败测试，不能写修复代码

---

## 二、四阶段调试法（强制执行 — TDD 轴心版）

```
阶段 1: 根因调查 ──────── 收集证据、分析
阶段 2: 模式分析 ──────── 找到工作示例、对比差异
阶段 3: 假设验证 ──────── 形成假设、最小化验证
阶段 4: 🔴🟢 TDD 修复 ─── 先写失败测试 → 再修复 → 验证  ← TDD 轴心
```

---

### 阶段 1: 根因调查（强制先完成）

#### 1.1 仔细阅读错误信息

- 不要跳过错误或警告
- 完整阅读堆栈跟踪
- 记录行号、文件路径、错误代码

#### 1.2 稳定复现问题（硬性门禁）

```
✅ 复现确认
├── 复现步骤: {1. 2. 3.}
├── 复现率: {10/10}
├── 环境信息: {浏览器/Node 版本/OS}
└── 错误信息: {完整错误消息和堆栈}
```

不能复现 → 收集更多数据，不要猜测。

#### 1.3 检查最近变更

- `git log --oneline -10`
- `git diff` 看最近改动
- 新依赖、配置变更、环境差异

#### 1.4 多组件系统证据收集

在每个组件边界添加诊断日志，确认问题出现在哪一层。**禁止跳过直接猜测。**

#### 1.5 追踪数据流

```
数据流追踪
├── 入口: {函数 A} 接收参数 {value}
├── 第 1 跳: {函数 B} 处理后变成 {value'}
├── 第 2 跳: {函数 C} 抛出异常 ← 症状在此
├── 源头: {函数 A 的参数} 就已经是坏值 ← 根因在此
└── 结论: 根因在入口，不在抛出点
```

---

### 阶段 2: 模式分析

找到工作示例对比：
- 有没有"能工作"的相似代码？
- 工作的代码 vs 不工作的代码，差异在哪？
- 切掉一半变量，看哪一半有问题（二分法）

---

### 阶段 3: 假设验证

#### 3.1 形成假设（附带证据）

```
假设 A: 根因是 {X}，证据 {Y}
假设 B: 根因是 {Z}，证据 {W}
```

#### 3.2 验证假设

**一次只验证一个假设**，验证失败 → 形成新假设，不在上面叠加修复。

验证方式：日志 / 二分 / 隔离 / 排除

#### 3.3 根因证据清单（强制输出）

```
🎯 根因证据清单
├── 声称的根因: {具体代码行 + 为什么是根因}
├── 症状位置: {文件:行号}
├── 根因位置: {文件:行号}
├── 数据流证据: 入口 → 传递 → 破坏点
├── 日志证据: {实际日志输出}
├── 排除的替代假设: ❌假设 A: {原因} ❌假设 B: {原因}
└── 验证方式: {日志/二分/隔离/排除}
```

**缺少任一项 → 根因分析不完整 → 禁止进入修复阶段。**

---

### 阶段 4: 🔴🟢 TDD 修复

> **禁止在 🔴 RED 确认之前编写任何修复代码。**

#### TDD 修复速查

```
1. 🔴 RED：编写重现 Bug 的失败测试
   - 测试必须精确复现 Bug 现象
   - npx vitest path/to/test.test.ts → 必须看到失败
   - 输出 🔴 RED 确认

2. 编译验证（强制）
   npx tsc --noEmit → 0 errors

3. 🟢 GREEN：最简修复代码
   - 只修 Bug，不重构不相关代码
   - npx vitest path/to/test.test.ts → 通过
   - 输出 🟢 GREEN 确认

4. 回归验证
   npm test → 原有测试全部通过，无回归
```

**🔴 RED 标记没输出 = 不能写修复代码。🟢 GREEN 标记没输出 = 不能声称修复完成。**

详见 `20-development/tdd-workflow.md`。

## 三、调试门禁（GATE）

```
接到调试任务
    ↓
门禁 1: 问题已复现？ ← 🛑 未复现禁止分析
    ↓
门禁 2: 证据已收集？ ← 🛑 无证据禁止声称根因
    ↓
门禁 3: 假设已验证？ ← 🛑 未验证禁止进入修复
    ↓
门禁 4: 失败测试已编写并确认 🔴RED？ ← 🛑 无失败测试禁止修复
    ↓
进入 🟢GREEN 修复
```

## 四、常见调试场景

### 空指针/未定义错误

```typescript
if (!user?.profile) throw new Error('User profile is required');
```

### UI 不更新 / 状态卡住

**分层排查**：
```
数据在哪里？→ 应该去哪里？→ 哪一步断了？
1. 网络 → 收到了吗？
2. 收到 → 解析了吗？
3. 解析 → 字段对吗？
4. 字段 → 调用了吗？
5. 调用 → 状态更新了吗？
```

**"网络有数据，UI 没变化，一定是哪里没接住"**
- 先分层再缩小，不要猜要验证
- 常见坑优先查：初始化时序 > 字段名 > 闭包捕获

## 五、调试心法

> **当用户多次汇报同一个问题，说明之前的解决思路片面，可能存在冗余代码或死代码。以用户反馈为绝对事实，强力排查。**

1. 相信用户反馈
2. 推翻重来，从零梳理架构
3. 查冗余：多入口/多推送/多连接？
4. 查死代码：路径走不到？变量被 shadow？
5. 强力排查：逐行走一遍

---

## 六、3 次修复失败规则

**尝试 3 次均失败 → 🛑 停止！质疑架构，不要继续修复。**

---

## 七、红旗信号 - 立即停止

- "先快速修复，以后再调查"
- "只是尝试改变 X 看看是否有效"
- "我觉得根因是 X"（没有代码证据）
- "GitNexus 返回了 X，所以根因就是 X"（相关性 ≠ 因果性）

**→ 🛑 返回阶段 1，重新收集证据。**

---

## 八、调试安全铁律

- **禁止循环无效修改**：连续 5 轮修改同一个文件同一段代码，说明思路有问题，必须停下来重新复现问题，换一种排查方式
- **禁止篡改测试**：绝对不允许修改原问题的测试用例来让测试通过
- **验证必须独立**：必须通过运行独立的测试脚本来验证，不能仅凭代码修改就判断成功

---

## 九、修复后的文档同步

修复完成后，回退到 `20-development/`：

```
1. 更新模块文档变更记录
2. 如接口变更 → 更新接口契约
3. 更新 Spec §13 变更记录（如涉及 Spec 描述）
4. 输出根因证据清单给 fullstack-reviewer 验证
```

## 十、检查清单

**调试前**：
- [ ] 错误信息完整
- [ ] 问题已复现

**根因分析**：
- [ ] 多条假设 + 证据
- [ ] 假设已验证
- [ ] 根因证据清单完整
- [ ] 指向具体行号

**TDD 修复**：
- [ ] 失败测试编写 + RED 确认
- [ ] 最简修复
- [ ] GREEN 确认
- [ ] 影响评估

**修复验证**：
- [ ] 回归测试通过
- [ ] 原有测试通过
- [ ] 文档已同步
