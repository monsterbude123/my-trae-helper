# 测试避坑方法论 — AI 辅助开发通用

> 来源：多轮 agent 并行开发中反复踩坑的真实教训。编写/修改测试代码前，MUST 逐条核对。
> 详细代码示例见 `.trae/skills/test-experience/SKILL.md`。

## §1 测试超时 — 环境与配置

1. 真实 LLM 调用 = 测试杀手 → 使用 autouse fixture 默认 Mock 外部服务
2. 新增 LLM 调用路径 → 检查是否被 autouse fixture 覆盖
3. Windows + asyncio 下 pytest-timeout 可能无效 → 用 marker 分级跳过，不依赖 timeout 硬杀
4. venv 路径污染 → 安装新依赖后确认虚拟环境同步到正确位置

## §2 Mock 策略 — monkeypatch 三大陷阱

1. **`from X import Y` 引用不同步**：patch 模块导出后，grep 所有下游 `from X import Y` 引用并逐一 `monkeypatch.setattr(downstream_mod, "alias", ...)`
2. **单例/工厂需显式重置**：patch 过的单例/工厂在测试间不会自动重置，需在 fixture teardown 中显式清理
3. **import-time 常量复制**：如果常量在 import 时被多模块复制，新增持有者必须在 conftest monkeypatch 循环中注册

## §3 Fixture 设计原则

1. 不要拉着 DB 跑纯函数测试 — 只测逻辑的测试不需要 fixture 初始化 DB
2. autouse fixture 只放"关闭外部服务"逻辑，不放业务 mock（除非全局都需要）
3. 新增 fixture 自问三问：会被几个测试用？（≥3 才值得抽 fixture）会多慢？（DB 操作放 module scope）会被污染吗？（用 factory as fixture 模式隔离）

## §4 marker 使用规范

| marker | 耗时 | 执行策略 |
|--------|------|---------|
| 无 marker（unit） | < 1s | 每次保存都跑 |
| `@pytest.mark.slow` | 1-30s | PR 前和 CI 跑，`-m "not slow"` 跳过 |
| `@pytest.mark.integration` | > 30s | 仅 CI 全量跑 |

## §5 测试编写自检清单

```
[ ] 这个测试会触发真实网络请求吗？
    → grep openai/anthropic/httpx 等关键字确认，必须 mock
[ ] 这个测试需要数据库吗？
    → 是则显式声明 fixture，不隐式依赖 autouse
[ ] 这个测试有文件系统副作用吗？
    → 用 tmp_path 或隔离的 temp dir
[ ] 这个测试依赖外部服务状态吗？
    → 用 mock 或 test double 替代
[ ] 改代码后，哪些测试应该失败？
    → 如果全绿而预期至少有一个失败 → 测试覆盖有盲区
```
