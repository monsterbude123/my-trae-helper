# 40-acceptance / 代码审查清单

> **定位**：验收阶段第一道门禁。代码质量 + 安全 + 文档一致性的清单式审查。
>
> **何时加载**：用户说"审查"/"检查"/"提交前"/"code review"时。

---

## 一、审查七维度

### 1. 功能正确性
- [ ] 代码实现了 Spec 预期功能
- [ ] 边界条件处理正确
- [ ] 错误处理完善

### 2. 代码质量
- [ ] 函数 < 50 行
- [ ] 文件 < 800 行
- [ ] 嵌套 < 4 层
- [ ] 命名清晰，无魔法数
- [ ] 无重复代码（DRY）
- [ ] 公共 API 有 JSDoc

### 3. 类型安全
- [ ] 无 `any` 类型
- [ ] 无 `console.log`
- [ ] 无突变模式
- [ ] 无降级兼容写法（`|| 'xxx'`、`?? 'xxx'`）

### 4. 安全性（CRITICAL）
- [ ] 无硬编码凭证（API keys、密码、tokens）
- [ ] 无 SQL 注入风险（字符串拼接查询）
- [ ] 无 XSS 漏洞（未转义的用户输入）
- [ ] 无 `localStorage` 直接调用（必须用 `safeLocalStorage`）
- [ ] 输入校验完善

### 5. 测试覆盖
- [ ] 新代码有测试
- [ ] 覆盖率 > 80%
- [ ] 边界条件已测试
- [ ] 错误路径已测试
- [ ] 前端 UI 修改有组件测试

### 6. 文档一致性
- [ ] 模块文档存在
- [ ] 接口契约与代码同步
- [ ] 数据模型与代码同步
- [ ] 变更记录已更新
- [ ] Spec 状态已更新

### 7. 死代码清理（commit/push 前）
- [ ] 本次修改是否使某些函数/类不再被调用？→ 删除或标注 `@deprecated`
- [ ] 本次修改是否使某些 import 变为未使用？→ 清理
- [ ] 本次修改是否使某些常量/枚举项变为无用？→ 清理
- [ ] 本次修改是否使某些文件变为空壳？→ 删除文件

**原则**：代码变更后的"尸体"必须清理，不留死代码。死代码是未来 Bug 的温床。

## 二、审查输出格式

```markdown
# 代码审查报告

## 审查概览
- **审查范围**: {文件列表}
- **审查时间**: {时间}
- **Spec 引用**: docs/specs/{编号}-{feature}/spec.md

## 结果汇总

| 维度 | 状态 | 问题数 |
|------|------|--------|
| 功能正确性 | ✅/⚠️/❌ | X |
| 代码质量 | ✅/⚠️/❌ | X |
| 类型安全 | ✅/⚠️/❌ | X |
| 安全性 | ✅/⚠️/❌ | X |
| 测试覆盖 | ✅/⚠️/❌ | X |
| 文档一致性 | ✅/⚠️/❌ | X |
| 死代码清理 | ✅/⚠️/❌ | X |

## 关键问题（必须修复）
1. {问题描述}
   - 文件: {路径}
   - 行号: {行号}
   - 建议: {修复建议}

## 警告（建议修复）
1. {警告描述}

## 建议（可选改进）
1. {建议描述}

## 审查结论
- ✅ **批准**: 无关键问题，可以提交
- ⚠️ **有条件批准**: 有警告但可合并，建议后续修复

```

## 三、批准标准

### ✅ 批准
- 无关键问题
- 测试覆盖率达标（>80%）
- 文档一致性通过
- 安全扫描无 HIGH

### ⚠️ 有条件批准
- 只有警告级别问题
- 关键路径无问题
- 文档一致性通过

### ❌ 拒绝
- 有关键问题
- 测试覆盖率不达标
- 文档不一致
- 安全扫描有 HIGH

## 四、审查特别情况：接手 fullstack-debugger 修复时

**额外门禁**：根因验证（不可跳过）

```
fullstack-debugger 产出 → Stage 0: 根因验证 → 通过？ → 常规审查
                                    ↓ 不通过
                                   🛑 退回 fullstack-debugger
```

### Stage 0.1 检查根因证据清单

必须检查 fullstack-debugger 产出是否包含：
- [ ] 声称的根因: {具体代码行 + 为什么是根因}
- [ ] 症状位置: {文件:行号}
- [ ] 根因位置: {文件:行号}
- [ ] 数据流证据: {入口 → 传递 → 破坏点}
- [ ] 日志证据: {实际日志输出}
- [ ] 排除的替代假设: {至少排除 1 个}
- [ ] 验证方式: {日志/二分/隔离/排除}

**缺少任一项 → 🛑 退回 fullstack-debugger 补充。**

### Stage 0.2 检查 TDD 证据

- [ ] 🔴 RED 确认标记: {测试文件 + 测试名称 + 失败原因}
- [ ] 🟢 GREEN 确认标记: {修复文件 + 修复行号 + 通过确认}
- [ ] 测试文件存在于对应 `__tests__` 目录

**特别检查**：
- 测试名称描述了 bug 行为（不是模糊的"works"）？
- 测试确实会因为 bug 而失败（不是碰巧通过）？
- 修复代码是**最小化的**（没有"顺带改"的其他东西）？

### Stage 0.3 输出根因验证结果

```
🔍 根因验证结果
├── 证据完整性: ✅/❌ ({缺失项})
├── TDD 证据: ✅/❌ 🔴RED={有/无} 🟢GREEN={有/无}
├── 症状-根因一致性: ✅/❌
├── 修复-根因一致性: ✅/❌
├── 替代假设排除: ✅/❌
└── 结论: ✅ 通过，进入常规审查 / ❌ 退回 fullstack-debugger
```

## 五、审查特别情况：涉及 UI 时

UI 代码额外审查：
- [ ] 组件可访问性（aria 标签、键盘导航）
- [ ] 响应式（至少 mobile / tablet / desktop 三档）
- [ ] 加载状态、空状态、错误状态三态处理
- [ ] 设计系统一致性（颜色、字体、间距来自设计 token）

---

## 六、审查检查清单总览

**审查前**：
- [ ] 查看变更范围（`git diff --stat`）
- [ ] 读取对应 Spec
- [ ] 检查文档影响清单是否已完成

**审查中**：
- [ ] 7 维度逐项检查
- [ ] 接手 fullstack-debugger 产出时执行 Stage 0 根因验证

**审查后**：
- [ ] 输出审查报告
- [ ] 给出明确结论（批准 / 有条件批准 / 拒绝）
- [ ] 关键问题返回 fullstack-implementer 修复
- [ ] 发现 Bug 转 fullstack-debugger
