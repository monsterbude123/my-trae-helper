# PRD 整合决策树

> 触发：用户给出多个 PRD/需求文档，要求整合到项目。
> 核心：决策树驱动，避免凭直觉合并。

---

## §0 三大铁律

```
1. MUST 先做影响面评估
   - 读 ARCHITECTURE.md + modules/ + contracts/schema
   - 用 GitNexus impact() 评估代码影响（如有源码）

2. MUST 输出决策表
   - 每个功能点标注：合并/新建/复用
   - 每个决策必须有理由（性能/复用/边界清晰）

3. NEVER 凭直觉合并
   - "看起来差不多" ≠ 应该合并
   - 必须走决策树判定
```

---

## §1 决策树流程（4 步）

```
Step 1 — 识别模块定位
  ├─ PRD 核心能力是什么？ → 对比现有模块
  ├─ 与现有模块重叠度？
  │   ├─ ≥70% → 合并到现有模块
  │   ├─ 30-70% → 候选复用（显式声明依赖）
  │   └─ <30% → 新建模块
  └─ 输出: 模块定位决策表

Step 2 — 识别跨模块复用点
  ├─ 数据模型复用？ → 表结构相似 → 复用表（加字段/加索引）
  ├─ 能力复用？ → 下载/标签/文件操作 → 复用现有模块
  └─ 输出: 复用决策表（含理由）

Step 3 — 识别冲突点
  ├─ 表名冲突？ → 检查 schema → 重命名或合并
  ├─ API 路径冲突？ → 检查现有 API → 调整路径
  └─ 输出: 冲突解决表

Step 4 — 输出整合方案
  └─ 模块定位 + 表结构设计 + 跨模块协作 + 功能清单（去重）+ 待确认项
```

---

## §2 重叠度判定标准

| 重叠度 | 决策 | 理由 |
|--------|------|------|
| ≥70% | 合并到现有模块 | 元数据/能力高度重合，避免冗余 |
| 30-70% | 候选复用（显式声明依赖） | 部分能力可复用，但有独特需求 |
| <30% | 新建模块 | 元数据/能力差异大，边界清晰 |

---

## §3 反例

```
反例 1: 凭直觉合并导致混乱
  场景: 两个 PRD 直接合并到同一模块
  后果: 表字段冲突 + API 路径混乱 + 后期拆分成本高
  教训: NEVER 凭"都是文件管理"就合并；MUST 检查元数据差异 + API 语义

反例 2: 忽略表名冲突
  场景: PRD 要求新建 tags 表，Agent 直接写 DDL
  后果: 与现有 tag-system 的 tags 表冲突，迁移时才发现
  教训: MUST 先 grep "CREATE TABLE" schema；NEVER 假设"新模块不会有冲突"
```
