> **定位**：开发过程中需要查阅的"原则参考"和"模式参考"。
>
> **何时加载**：设计模块接口时 / Code Review 时 / 决定是否引入抽象时。
>
> **来源**：合并自原 `programming-principles` 和 `design-patterns` 两个 skill，去重精简。

---

## 第一部分：程序设计原则

### 核心铁律

**原则是指导而非教条。在冲突时，正确性 > 可维护性 > 性能 > 简洁性。**

---

### 一、SOLID 五原则

#### 1. SRP — 单一职责原则

> 一个模块/类/函数只应该有一个引起它变化的原因。

| 维度 | 内容 |
|------|------|
| 通俗理解 | 一个类只做一件事，一个函数只做一件事 |
| 违规信号 | 函数超过 50 行；类的字段超过 8 个；文件里有"and"命名的函数；**单文件超过 800 行** |
| 实践 | impl 块如果包含多个不相关的方法组，应该拆分 |
| **文件级硬约束** | **≤ 800 行正常，800-1000 行警告拆分，> 1000 行硬阻断** |

```
✅ 好: ScannerService 只负责文件遍历和调度
       ↓ 委托
     MetadataExtractor trait → PngExtractor, VideoExtractor

❌ 坏: ScannerService 自己写 PNG 解析、视频解析、标签提取
```

#### 2. OCP — 开闭原则

> 软件实体应该对扩展开放，对修改封闭。

| 维度 | 内容 |
|------|------|
| 通俗理解 | 新增功能通过"加代码"实现，不是"改已有代码" |
| 违规信号 | 每次新增功能都要修改 match 分支或 if-else 链 |
| 实践 | 用 trait/接口分发，新增类型只加新实现 |

#### 3. LSP — 里氏替换原则

> 子类型必须能够替换其基类型而不破坏程序正确性。

| 维度 | 内容 |
|------|------|
| 通俗理解 | 子类不能比父类更严格 |
| 违规信号 | 子类抛出父类不会抛的异常；子类忽略父类方法的行为 |

#### 4. ISP — 接口隔离原则

> 客户端不应该被迫依赖它不使用的方法。

| 维度 | 内容 |
|------|------|
| 通俗理解 | 接口要小而专，不要"胖接口" |
| 违规信号 | 实现类有空方法体或抛 NotImplementedError 的方法 |
| 实践 | 大接口拆分为多个小接口，按客户端分组 |

#### 5. DIP — 依赖倒置原则

> 高层模块不应依赖低层模块，两者都应依赖抽象。

| 维度 | 内容 |
|------|------|
| 通俗理解 | 依赖接口，不依赖实现 |
| 实践 | 高层定义接口，低层实现接口；通过依赖注入传递 |

---

### 二、KISS — Keep It Simple, Stupid

> 简单是可靠的最佳过滤器。

| 信号 | 应对 |
|------|------|
| 一个函数有 3 层以上嵌套 | 提取子函数或提前 return |
| 用了反射/元编程才能实现 | 重新审视设计 |
| 注释比代码还多 | 简化逻辑或拆分函数 |
| 引入第三方库只为用 1 个函数 | 自己写或找替代 |

---

### 三、DRY — Don't Repeat Yourself

> 每一个知识点在系统内都应该有唯一、明确、权威的表述。

**注意**：DRY 是关于"知识"的重复，不是"代码"的重复。两段看起来一样的代码可能表达不同的业务概念，强行合并反而引入耦合。

| 信号 | 应对 |
|------|------|
| 3 处以上相同业务逻辑 | 提取公共函数 |
| 多个模块维护同一份配置 | 集中到 config |
| 文档和代码描述同一份接口 | 文档作为契约，代码实现契约 |

---

### 四、YAGNI — You Aren't Gonna Need It

> 不要为"未来可能需要"的功能写代码。

**这是过度设计的刹车。** 抽象应该在第 3 次重复时引入，而不是第 1 次预判时。

| 信号 | 应对 |
|------|------|
| "以后可能会用到" | 现在不用就不写 |
| "为了灵活性加了一层" | 等真正有第二种实现时再加 |
| "先做个接口预留" | YAGNI，等需要时再抽 |

---

### 五、其他重要原则

| 原则 | 一句话 | 实践 |
|------|--------|------|
| 组合优于继承 | 优先用组合，少用继承 | 用 has-a 而不是 is-a |
| 最小知识（迪米特法则） | 只与直接朋友说话 | A→B→C 调用链应该断开 |
| 告知不要询问（Tell, Don't Ask） | 让对象做事，不要问它状态再做事 | `obj.doAction()` 而不是 `if (obj.isX()) obj.doY()` |
| 失败快速（Fail Fast） | 错误尽早暴露 | 参数校验在入口处，错误立即抛 |

## 第二部分：常用设计模式

### 核心铁律

**先问"这个模式解决什么问题"，再决定是否使用。不要为了用模式而用模式。**

---

### 一、创建型模式

#### 1. 工厂方法（Factory Method）

| 维度 | 内容 |
|------|------|
| 一句话 | 定义一个创建对象的接口，让子类决定实例化哪个类 |
| 适用判断 | ✅ 创建逻辑复杂（读配置、解密 Key、注册回调）<br>❌ 创建只需要 `new` — 不要用，过度设计 |

#### 2. 单例（Singleton）

| 维度 | 内容 |
|------|------|
| 一句话 | 保证一个类只有一个实例，并提供全局访问点 |
| 适用场景 | 数据库连接池、全局配置、日志器 |
| 反模式 | ❌ 用单例代替依赖注入；❌ 单例持有可变业务状态 |

#### 3. 建造者（Builder）

| 维度 | 内容 |
|------|------|
| 一句话 | 将复杂对象的构造与其表示分离 |
| 适用场景 | 对象有 5+ 个可选参数；构造过程多步骤 |
| 实践 | 链式调用 + 最后 `.build()` 返回不可变对象 |

---

### 二、结构型模式

#### 4. 适配器（Adapter）

| 维度 | 内容 |
|------|------|
| 一句话 | 将一个接口转换成客户端期望的另一个接口 |
| 适用场景 | 第三方 SDK 接口与项目接口不一致 |
| 反模式 | ❌ 项目内部两个自己的接口也用适配器 — 应该统一接口 |

#### 5. 装饰器（Decorator）

| 维度 | 内容 |
|------|------|
| 一句话 | 动态地给对象添加职责 |
| 适用场景 | 日志、缓存、权限校验等横切关注点 |
| 实践 | TypeScript 用装饰器语法；React 用 HOC 或 hooks |

#### 6. 代理（Proxy）

| 维度 | 内容 |
|------|------|
| 一句话 | 为其他对象提供代理以控制访问 |
| 适用场景 | 远程代理、虚拟代理（懒加载）、保护代理（权限） |

#### 7. 外观（Facade）

| 维度 | 内容 |
|------|------|
| 一句话 | 为复杂子系统提供统一接口 |
| 适用场景 | 封装多个第三方服务为一个内部服务 |

---

### 三、行为型模式

#### 8. 策略（Strategy）

| 维度 | 内容 |
|------|------|
| 一句话 | 定义一系列算法，封装每一个，使它们可互换 |
| 适用场景 | 多种支付方式、多种排序规则、多种导出格式 |
| 实践 | 定义接口 → 多个实现 → 上下文按配置选择 |

#### 9. 观察者（Observer / Pub-Sub）

| 维度 | 内容 |
|------|------|
| 一句话 | 一对多依赖，当一个对象状态变化时，所有依赖被通知 |
| 适用场景 | 事件系统、消息总线、React 状态管理 |
| 反模式 | ❌ 观察者持有发布者引用导致内存泄漏 |

#### 10. 命令（Command）

| 维度 | 内容 |
|------|------|
| 一句话 | 将请求封装为对象，支持撤销/重做、队列、日志 |
| 适用场景 | 编辑器撤销、任务队列、事务 |

#### 11. 责任链（Chain of Responsibility）

| 维度 | 内容 |
|------|------|
| 一句话 | 沿链传递请求，每个处理者决定处理或传递 |
| 适用场景 | 中间件、过滤器链、审批流 |

#### 12. 状态（State）

| 维度 | 内容 |
|------|------|
| 一句话 | 对象行为随状态变化，将状态封装为独立类 |
| 适用场景 | 订单状态机、文档工作流（draft → review → published） |
| 实践 | 与 Spec §7 状态机章节对应 |

---

### 四、模式选择决策树

```
问题类型？
│
├── 创建对象逻辑复杂 ─────────→ 工厂方法 / 建造者
│
├── 接口不兼容 ───────────────→ 适配器
│
├── 需要动态添加职责 ─────────→ 装饰器
│
├── 多种算法/规则可互换 ──────→ 策略
│
├── 一对多通知 ───────────────→ 观察者
│
├── 状态多分支 ───────────────→ 状态模式
│
├── 请求多步骤处理 ───────────→ 责任链
│
├── 需要撤销/队列 ────────────→ 命令
│
└── 子系统复杂需统一入口 ─────→ 外观
```

---

### 五、反模式警示

| 反模式 | 描述 | 应对 |
|--------|------|------|
| God Class | 一个类什么都知道什么都能做 | SRP 拆分 |
| Spaghetti Code | 模块互相直接调用，无层次 | 引入层次 + 接口 |
| Golden Hammer | 一个模式/工具解决所有问题 | 学习多种模式 |
| Premature Abstraction | 还没重复就抽象 | YAGNI，等 3 次重复 |
| Not Invented Here | 不用别人的，自己造轮子 | 优先用成熟库 |
| Magic Numbers/Strings | 散落各处的硬编码 | 提取常量/枚举 |
