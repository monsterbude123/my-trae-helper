# §14 落地路线图

> 验收体系不是一天建成的。本路线图按"先止血 → 再加固 → 后优化"三阶段推进，每阶段有明确里程碑与可验证产出。

---

## 阶段总览

| 阶段 | 周期 | 核心目标 | 关键产出 |
|------|------|---------|---------|
| **Phase 1：止血** | 0-30 天 | 解决当前最痛的验收问题，建立基础共识 | 5 条铁律 + PR Checklist + Bad Test 清单 |
| **Phase 2：加固** | 31-90 天 | 系统化覆盖测试金字塔，引入度量 | 测试金字塔成型 + 度量看板 + CI 门禁 |
| **Phase 3：优化** | 91 天-长期 | 持续演进，引入性能/安全/自动化 | 性能基线 + 安全扫描 + AI Agent 协议落地 |

---

## Phase 1：止血（0-30 天）

**目标**：用最小成本止血当前最痛的 6 类问题（Bad Test 阻塞 / Mock 不生效 / 异步陷阱 / E2E 假验收 / 修复不验证 / 全量跑太重）。

### Week 1-2：建立共识与基础工具

| 任务 | Owner | 完成标志 |
|------|-------|---------|
| 团队宣讲 5 条铁律 | Tech Lead | 全员签到 + 签字 |
| 整理当前 Bad Test 清单（案例库） | QA | 至少识别 10 个 Bad Test，按 Bad Test 反馈模板记录 |
| 引入 `pytest-timeout` / vitest 超时机制 | 工程师 | 全局测试默认 30s 超时，避免卡死 |
| 落地 PR Self-Check Checklist | Tech Lead | 所有 PR 必须附 Checklist 截图 |

### Week 3-4：止血当前痛点

| 任务 | Owner | 完成标志 |
|------|-------|---------|
| 清理 Flaky Test（连跑 10 次稳定性 ≥ 99.5%）| 模块 Owner | Flaky 清单 0 项 |
| 修复 Mock 不生效案例（案例 3/8） | 模块 Owner | Mock 覆盖率 ≥ 90% |
| 引入 E2E Workflow B 协议 | 主 agent | 修复后必须重跑验证，有截图证据 |
| 建立测试分区跑脚本 | 工程师 | `npm test -- src/lib/<module>` 可独立跑 |

### Phase 1 验收

```
[ ] 5 条铁律全员签字
[ ] PR Self-Check Checklist 100% 覆盖
[ ] Bad Test 清单 ≥ 10 项，每项有修复计划
[ ] Flaky Test 数 < 5
[ ] E2E 修复后 100% 有重跑验证证据
[ ] 测试分区跑脚本可用
```

---

## Phase 2：加固（31-90 天）

**目标**：系统化覆盖测试金字塔，引入度量体系，建立 CI 门禁。

### Month 2：测试金字塔成型

| 任务 | Owner | 完成标志 |
|------|-------|---------|
| 单元测试覆盖率 ≥ 70% | 工程师 | `pytest --cov` 报告 |
| 集成测试用 temp_data_dir 模板 | 工程师 | 100% 集成测试使用标准 fixture |
| E2E Workflow A 模板落地 | 模块 Owner | 至少 3 个核心模块有 spec 文件 |
| autouse fixture 关闭外部服务 | 工程师 | 全量测试无真实网络调用 |
| 速度预算达成 | 工程师 | 250 测试全量 < 30s |

### Month 3：度量与门禁

| 任务 | Owner | 完成标志 |
|------|-------|---------|
| 度量指标看板上线 | QA | 周会看板自动生成 |
| Flaky Score 自动化 | 工程师 | CI 夜间任务跑 10 次，输出 Flaky 报告 |
| Mock 覆盖率检测 | 工程师 | autouse fixture 检测真实网络调用 |
| L1 PR Gate CI 接入 | 工程师 | PR 必须通过 Lint + 单测 + SAST + SCA 才能合并 |
| 验收债务看板 | QA | 所有 skip / xfail / 例外登记入看板 |

### Phase 2 验收

```
[ ] 单测覆盖率 ≥ 70%
[ ] E2E Workflow A 覆盖 ≥ 3 个核心模块
[ ] 全量测试 < 30s
[ ] 度量看板自动生成，周会review
[ ] Flaky Score ≥ 99.5%
[ ] Mock 覆盖率 100%
[ ] L1 PR Gate 强制执行
[ ] 验收债务看板单调下降
```

---

## Phase 3：优化（91 天-长期）

**目标**：引入性能 / 安全验收，落地 AI Agent 协议，持续演进。

### Month 4：性能与安全验收

| 任务 | Owner | 完成标志 |
|------|-------|---------|
| 关键 API 性能基线 | 性能 Owner | 至少 5 个核心 API 有 P99 基线 |
| k6 性能回归脚本 | 性能 Owner | PR 上跑 30s 采样回归 |
| 安全扫描全栈接入 | 安全 Owner | pre-commit + CI + 夜间三层扫描 |
| 鉴权矩阵测试模板 | 安全 Owner | 核心模块 100% 覆盖 |

### Month 5：AI Agent 协议落地

| 任务 | Owner | 完成标志 |
|------|-------|---------|
| acceptance-discipline skill 部署到所有 agent | Tech Lead | agent 加载本 skill 并按协议执行 |
| 多 agent RACI 落地 | Tech Lead | 每个验收任务有明确 Accountable |
| 子 agent 委派规范执行 | 主 agent | 所有委派任务包含完整 prompt 字段 |
| worklog 协议执行 | 所有 agent | 每个任务追加 worklog 记录 |

### Month 6+：持续演进

| 任务 | Owner | 频率 |
|------|-------|------|
| 案例库 review 与补充 | QA | 每季度 |
| Checklist review 与演进 | Tech Lead | 每季度 |
| 工具链评估与升级 | 工程师 | 每半年 |
| 验收体系年度复盘 | Tech Lead | 每年 |

### Phase 3 验收

```
[ ] 关键 API 100% 有性能基线
[ ] PR 性能回归自动化
[ ] 安全扫描三层防护落地
[ ] 鉴权矩阵 100% 覆盖
[ ] AI Agent 协议全员遵守
[ ] 验收债务 ≤ 5 项
[ ] 团队验收文化形成（无人需要被催才做验收）
```

---

## 路线图的风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| 团队抵触"流程变重" | 高 | 中 | Phase 1 强调"止血"，让团队先看到收益 |
| 度量指标被"刷" | 中 | 高 | 指标必须组合使用，单一指标不决策 |
| 工具链碎片化 | 中 | 中 | 工具选型严格评估，避免随意引入 |
| AI Agent 协议不遵守 | 中 | 高 | 主 agent 强制监督，违反协议必须修正 |
| 验收债务再次累积 | 高 | 高 | 债务看板必须单调下降，Tech Lead 月度 review |

---

## 路线图的退出标准

每个阶段必须满足"验收"才能进入下一阶段。**禁止跳级**——Phase 1 没做完就上 Phase 2，等于在沙地上盖楼。

```
Phase 1 → Phase 2 的门禁：
  [ ] 5 条铁律全员签字
  [ ] Flaky Test < 5
  [ ] PR Self-Check 100% 覆盖
  [ ] Bad Test 清单建立并修复 ≥ 50%

Phase 2 → Phase 3 的门禁：
  [ ] 单测覆盖率 ≥ 70%
  [ ] 度量看板上线
  [ ] L1 PR Gate 强制执行
  [ ] 验收债务看板单调下降 4 周
```
