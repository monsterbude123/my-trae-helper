# 原型设计方法论（Prototype Design v5.1）

> **定位**：spec 阶段的扩展产出。当能力涉及 UI 时，fullstack-spec-writer 额外产出模块化的原型文档（ASCII 线框图 + 交互 + 样式），供 fullstack-contract-writer 推导接口数据需求，并移交 ui-ux-pro-max 做详细视觉设计。
>
> **核心理念**：全栈不只是后端契约。UI 原型是前后端协作的桥梁 —— 没有原型，fullstack-contract-writer 不知道前端需要什么数据；没有原型，ui-ux-pro-max 无从下手做视觉设计。
>
> **上游**：`fullstack-spec-writer`（spec.md 的 BDD 场景）
> **下游**：`fullstack-contract-writer`（从原型推导接口）+ `ui-ux-pro-max`（详细视觉设计）

---

## 零、4 条原型铁律（违反任一条 → 退回重画）

```
1. UI MUST HAVE PROTOTYPE       涉及 UI 必先画原型
2. REAL TEXT NOT PLACEHOLDER    线框图标实际文字，禁止 [按钮] [输入框] 等占位符
3. ALL STATES DRAWN             4 状态齐全（默认/加载中/空数据/错误）
4. MODULAR NOT MONOLITHIC       每个页面/模块一个独立文件，不塞单文件
```

---

## 一、为什么需要原型设计

### 痛点

```
V5.0 缺失原型设计导致：
  ├── fullstack-contract-writer 只能从 spec 文字猜前端数据需求 → 接口字段缺失/冗余
  ├── fullstack-implementer 写前端时无布局参考 → 边写边改，样式反复调整
  ├── ui-ux-pro-max 拿不到上下文 → 详细设计与实际功能脱节
  └── fullstack-reviewer 审查时无 UI 验收基准 → 前端质量靠直觉
```

### 解药

```
V5.1 引入原型设计：
  fullstack-spec-writer 写 spec 时 ── 涉及 UI ──▶ 产出 prototypes/{module}.md
    │                                      │
    │  ASCII 线框图（低成本，30 秒画完）      │
    │  交互说明（点击/输入/跳转/状态）         │
    │  样式说明（布局/断点/层级）             │
    │                                      │
    ▼                                      ▼
  fullstack-contract-writer                     ui-ux-pro-max
  从原型推导接口数据需求               做详细视觉设计文档
  （字段/类型/嵌套）                   （配色/组件/间距/动效）
```

---

## 二、原型设计的三个层次

```
层次 1: ASCII 线框图（fullstack 负责，快速原型）
  └─ 用 ┌┐└┘├┤│┬┴┼─ 画页面布局，标出实际文字和按钮
  └─ 目的：明确布局结构 + 交互逻辑 + 数据需求
  └─ 成本：30 秒 - 2 分钟/页面

层次 2: 交互说明 + 样式说明（fullstack 负责）
  └─ 每个可交互元素的交互行为 + 关联 spec Scenario
  └─ 布局方式 + 响应式断点 + 状态变化
  └─ 目的：给 fullstack-implementer 和 fullstack-contract-writer 明确指引

层次 3: 详细视觉设计（ui-ux-pro-max 负责，移交）
  └─ 配色方案 / 设计 tokens / 组件库 / 间距规范 / 动效
  └─ 目的：给前端实现最终视觉标准
  └─ 产出：模块化设计文档（每页面/模块一个）
```

**fullstack 只做层次 1 和 2，层次 3 移交 ui-ux-pro-max。**

## 三、ASCII 线框图规范

### 基本字符集

```
┌ ┐ └ ┘    框线四角
├ ┤        左右分支
┬ ┴        上下分支
┼          十字交叉
─ │        横线竖线
[ ]        按钮/可点击元素
( )        输入框
< >        图标占位
~~~        加载/骨架屏
...        省略/更多
```

### 线框图示例

```
┌─────────────────────────────────────────────┐
│  <Logo>          [搜索框___________]  [登录]  │  ← Header (60px)
├──────────┬──────────────────────────────────┤
│  侧边栏   │  主内容区                         │
│  ┌──────┐│  ┌──────────┐  ┌──────────┐      │
│  │菜单 1 ││  │  卡片 1   │  │  卡片 2   │      │
│  │菜单 2 ││  │  <图片>   │  │  <图片>   │      │
│  │菜单 3 ││  │  标题     │  │  标题     │      │
│  │菜单 4 ││  │  [详情]   │  │  [详情]   │      │
│  └──────┘│  └──────────┘  └──────────┘      │
│          │  ┌──────────┐  ┌──────────┐      │
│          │  │  卡片 3   │  │  卡片 4   │      │
│          │  │  ...      │  │  ...      │      │
│          │  └──────────┘  └──────────┘      │
├──────────┴──────────────────────────────────┤
│  [关于]  [帮助]  [反馈]       © 2026 公司     │  ← Footer (40px)
└─────────────────────────────────────────────┘
```

### 线框图绘制原则

```
1. 标出实际文字，不用 "文本占位符"
   ✅ [登录]  [注册]  [搜索]
   ❌ [按钮]  [按钮]  [按钮]

2. 标出实际数据，不用 "数据占位符"
   ✅ 用户名: 张三
   ❌ 用户名: {data}

3. 标出布局尺寸（关键约束）
   ← Header (60px)
   ← 侧边栏 (200px)
   ← 主内容 (1fr)

4. 每个状态画一张图
   - 默认状态
   - 加载中（~~~ 骨架屏）
   - 空数据
   - 错误状态

5. （V5.2 NEW）环境感知 — 嵌入式扩展须标注宿主区域
   如果功能是嵌入已有应用的扩展，线框图必须包含宿主应用的
   固定布局元素（Header/Sidebar/StatusBar），用注释标注：
   - "【宿主区域】— 本次不改动"
   - "【扩展区域】— 本次变更"
   如果是独立页面或新应用 → 画完整页面。
```

## 四、原型文档结构（模块化）

每个页面/模块一个独立文件：

```
docs/specs/changes/{change}/
├── prototypes/
│   ├── README.md              # 原型索引 + 模块清单
│   ├── {page-module-1}.md     # 页面/模块 1 的原型
│   ├── {page-module-2}.md     # 页面/模块 2 的原型
│   └── {component-module}.md  # 共享组件的原型
```

### 何时产出原型

```
fullstack-spec-writer 写 spec 时自问：
  ├── spec 的 BDD 场景涉及用户可见的界面吗？
  │     ├── 是 → 产出 prototypes/{module}.md
  │     └── 否（纯后端/纯 API）→ 跳过原型
  │
  ├── 涉及几个页面/模块？
  │     └── 每个页面/模块一个独立原型文件
  │
  └── 有共享组件吗？
        └── 共享组件单独一个原型文件
```

### 原型文档内容

每个 `prototypes/{module}.md` 包含 5 段：

```markdown
# Prototype: {页面/模块名}

> 来源 Spec: specs/{capability}/spec.md
> 模块类型: 页面 / 组件 / 布局
> 创建日期: YYYY-MM-DD

## 1. 线框图（ASCII Wireframe）

{ASCII 线框图，含实际文字和按钮}

## 2. 交互说明

| 元素 | 交互 | 行为 | 关联 Scenario |
|------|------|------|--------------|
| [登录] | 点击 | 弹出登录弹窗 | spec.md#用户登录 |
| [搜索] | 输入+回车 | 跳转搜索结果页 | spec.md#搜索 |

## 3. 样式说明

- 布局: Flexbox / Grid
- 断点: mobile (<768px) / tablet (768-1024px) / desktop (>1024px)
- 层级: Header(60px) + Main(1fr) + Footer(40px)

## 4. 状态变化

| 状态 | 线框图差异 | 触发条件 |
|------|----------|---------|
| 加载中 | 主内容区显示骨架屏 | 首次进入 |
| 空数据 | 显示空状态插画 | 无搜索结果 |
| 错误 | 显示错误提示 | API 失败 |

## 5. 移交 ui-ux-pro-max

以下设计决策需 ui-ux-pro-max 详细定义：
- [ ] 配色方案 / 设计 tokens
- [ ] 组件库选型
- [ ] 间距 / 圆角 / 阴影规范
- [ ] 动效规范
```

## 五、与 fullstack-contract-writer 的衔接

fullstack-contract-writer 从原型推导接口数据需求：

```
原型线框图                      fullstack-contract-writer 推导
┌──────────────┐
│  <图片>       │  ──▶  接口需返回 imageUrl 字段
│  标题         │  ──▶  接口需返回 title 字段
│  [详情]       │  ──▶  点击跳转需 itemId 参数
└──────────────┘

卡片 1, 2, 3, 4    ──▶  接口返回数组 items[]
骨架屏状态          ──▶  需要 loading 状态字段
空数据状态          ──▶  需要空数组判断
```

**铁律**：fullstack-contract-writer 读取 prototypes/ 作为接口设计的 UI 上下文。prototypes/ 缺失 = fullstack-contract-writer 退回 fullstack-spec-writer 补充。

---

## 六、与 ui-ux-pro-max 的衔接

fullstack 的原型是**低保真**的（ASCII 线框图），ui-ux-pro-max 接手做**高保真**设计：

```
fullstack 产出                     ui-ux-pro-max 产出
prototypes/{module}.md    ──▶     design-system/
  ASCII 线框图                       tokens.md (配色/字体/间距)
  交互逻辑                           components.md (组件库)
  布局结构                           {page}.md (高保真视觉稿)
  状态变化                           responsive.md (响应式细节)
```

**移交清单**：
1. 把 `prototypes/` 目录所有文件交给 ui-ux-pro-max
2. 声明"这是低保真原型，请做详细视觉设计"
3. ui-ux-pro-max 产出模块化设计文档
4. 设计文档回归到 `docs/design/` 或 `docs/modules/{module}.md`

---

## 七、与 fullstack-implementer 的衔接

fullstack-implementer 实现前端时：
1. 读取 `prototypes/{module}.md` 获取布局结构和交互逻辑
2. 读取 `contracts/` 获取接口数据
3. 读取 ui-ux-pro-max 产出的设计文档获取视觉规范
4. 三者结合实现前端代码

```
prototypes/  ──▶  布局结构 + 交互逻辑
contracts/   ──▶  接口数据
ui-ux 设计   ──▶  视觉规范
     │
     ▼
  前端代码实现
```

**fullstack-spec-writer 产出原型时**：
- [ ] 识别了所有涉及 UI 的 spec Scenario
- [ ] 每个页面/模块一个独立原型文件
- [ ] 共享组件单独一个原型文件
- [ ] 线框图标出实际文字和按钮（非占位符）
- [ ] 线框图标出布局尺寸约束

- [ ] 交互说明关联到 spec Scenario
- [ ] 标注了响应式断点
- [ ] 列出了所有状态变化（加载/空/错误）

- [ ] 从状态变化推导了状态字段

| 反面（禁止） | 正确（必须） |
|---|---|
| 不画原型直接写 contract | 涉及 UI 时必须先画原型 |

| [按钮] [按钮] [按钮] | [登录] [注册] [搜索] |

| 原型散放在 spec.md 里 | 独立 prototypes/ 目录 |

## 十一、异常分支

| 异常 | 处理 |
|------|------|
| 页面极少（只有 1 个页面） | 仍需 prototypes/README.md + 1 个 page 文件，不可省略目录结构 |
| 原型与实现发现矛盾 | implementer 不自行修改原型 → 回流 spec-writer 更新 |
| 某个状态的 UI 在设计时不确定 | 画"最佳猜测"，标注【待确认】，不跳过该状态 |
| ASCII 字符在目标显示环境中乱码 | 改用 + - \| = 等基础字符替代，保持结构不变 |
| contract-writer 无法从原型推导字段 | 标记缺失项，回流 spec-writer 补充交互说明中的字段信息 |
