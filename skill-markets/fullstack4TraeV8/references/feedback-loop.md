# 反馈回流机制（Feedback Loop）

> **定位**：SDD 流程的免疫系统。防止 specs/契约漂移导致"目标失真、代码漂移、永远打补丁"。
>
> **触发**：任意阶段执行中发现 specs/契约与现实不一致时。

---

## 一、核心命题

**SDD 的灵魂是"Spec 是唯一事实来源"。如果发现 spec 错了却不去改 spec，SDD 就退化成"带着文档的 vibe coding"。**

```
传统 SDD（线性）:  Spec → Design → Code → Review → 验收
                        ↑ 漂移发生但不回流

反馈回流（闭环）:  Spec → Design → Code → Review
                       ↑    ↑    ↑    ↓
                       └────┴────┴──── 发现漂移 → 强制回流改 spec
```

---

## 二、漂移的五种类型

| 类型 | 定义 | 检测方式 | 严重度 |
|------|------|---------|--------|
| **Spec 漂移** | spec.md 描述的行为与实际实现不一致 | fullstack-reviewer 对比 spec vs 代码 | 🔴 高 |
| **契约漂移** | contracts/ 与代码实现不一致 | Hook + fullstack-reviewer 对比 | 🔴 高 |
| **文档漂移** | docs/modules/ 与代码不一致 | DOC SYNC VERIFY | 🟡 中 |
| **目标漂移** | 当前产出偏离 proposal.md 的原始目标 | 阶段切换时对齐检查 | 🔴 高 |
| **跨目录漂移**（V5.2 NEW） | 不同 change 目录的 specs/contract 对同一概念的定义不一致 | 多目录间交叉对比 | 🟡 中 |
| **事实重复漂移**（V11 NEW） | 同一事实（架构描述/领域模型/通用约定）在项目级文档和多个 change 工件中重复出现 | reviewer 6.4 事实唯一性检查 | 🔴 高 |

---

## 三、反馈回流铁律

```
┌─────────────────────────────────────────────────────────────┐
│  1. NO DRIFT UNCHECKED      发现漂移必须报告，不能静默继续    │
│  2. SPEC IS SOURCE OF TRUTH 发现 spec 错 → 改 spec，不是改代码迁就 │
│  3. STOP AND FIX            严重漂移 → 停下当前工作，先回流   │
│  4. DRIFT REPORT MANDATORY  每个阶段结束必须输出漂移报告      │
│  5. USER CONFIRMS BREAKING  BREAKING 漂移修复需用户确认       │
└─────────────────────────────────────────────────────────────┘
```

---

## 四、漂移检测时机

```
① 编码后（Hook: drift-detect.ps1）
   对比: contracts/ vs 代码 vs spec.md
   输出: 漂移报告（🟢/🟡/🔴）

② 阶段切换时（fullstack-reviewer 强制）
   对比: 当前产出 vs 原 spec 目标 vs 契约
   输出: 目标对齐检查报告

③ 提交前（pre-commit）
   对比: 文档 vs 代码
   输出: DOC SYNC VERIFY 报告

④ 任意阶段执行中（AI 自检）
   触发: AI 发现"代码与 spec 描述不符"
   行动: 立即停下 → 输出漂移报告 → 回流

⑤ 多目录交叉检查（V5.2 NEW，reviewer 阶段扩展 / 圆桌审计时）
   对比: 当前变更的 PhaseName/ToolName/CommandName 等枚举 vs 其他已有变更目录中的同名概念
   方法: Grep 当前变更定义的枚举名在 docs/specs/changes/*/contracts/
   输出: 跨目录一致性报告

⑥ 事实唯一性检查（V11 NEW，reviewer 阶段 6.4）
   对比: 当前 change 工件关键段落 vs docs/ 顶级文件 + docs/modules/*.md
   方法: Grep 关键段落在 docs/ 中的出现次数
   输出: 事实重复清单（≥3 处 = REJECT）
```

---

## 五、漂移报告格式

```markdown
# 📊 Spec Drift Report

## 漂移概览
- 检测时机: {编码后/阶段切换/提交前}
- 漂移类型: Spec漂移 / 契约漂移 / 文档漂移 / 目标漂移
- 漂移等级: 🟢无 / 🟡轻微 / 🔴严重

## 漂移详情
| # | 类型 | 位置 | specs/契约描述 | 实际实现 | 等级 |
|---|------|------|-------------|---------|------|
| 1 | 契约漂移 | api-contracts.md L23 | code=40400 | code=400 | 🔴 |
| 2 | Spec漂移 | spec.md#happy-path | 返回 data.id | 返回 data.userId | 🔴 |

## 影响面
- 受影响文件: [list]
- 受影响测试: [list]
- 受影响下游模块: [list]

## 建议行动
- [ ] 🔴 严重: 回流改 specs/契约 → 同步代码
- [ ] 🟡 轻微: 警告但可继续，记入技术债

## 用户决策点（BREAKING 漂移）
- [ ] 改 spec 迁就代码（spec 错了）
- [ ] 改代码迁就 spec（代码错了）
- [ ] 双向调整（都部分对）
```

## 六、回流流程

```
任意阶段执行中
    ↓
AI 发现 specs/契约与现实不一致
    ↓
🛑 强制停下当前工作（铁律 3）
    ↓
输出 Spec Drift Report
    ↓
判断漂移等级
    │
    ├── 🟢 无漂移 → 继续
    ├── 🟡 轻微 → 警告但继续，记入技术债清单
    └── 🔴 严重 → 必须回流
                ↓
            回流到哪个 Agent？
                ├── spec 错了 → 回流 fullstack-spec-writer 改 spec
                ├── 契约错了 → 回流 fullstack-contract-writer 改契约
                ├── 代码错了 → 回流 fullstack-implementer 改代码
                ├── 目标错了 → 回流 fullstack-proposal-writer 重新评估
                └── intake 判断错误（V5.2 NEW）→ 回流 fullstack-intake 重新评估
                      触发条件: 选错流程链 / 低估风险等级 / 遗漏关键约束
                      输出: 更新 .state-card.md 的风险等级字段
                ↓
            BREAKING 变更需用户确认（铁律 5）
                ↓
            specs/契约/代码更新后才能继续
                ↓
            重新跑漂移检测确认无新漂移
```

## 七、目标对齐检查点（防目标漂移）

**每个阶段切换时强制执行**，防止"简单功能做几天还在修补"的目标失真。

```markdown
# 🎯 目标对齐检查（阶段切换时强制）

## 原始目标（来自 proposal.md）
- Why: {动机}
- What: {变更清单}
- Capabilities: {能力列表}
- Non-Goals: {不做的事}

## 当前产出对齐度
| 维度 | 原始目标 | 当前状态 | 对齐度 |
|------|---------|---------|--------|
| 能力覆盖 | {N 个能力} | {已实现 M 个} | M/N % |
| Non-Goals | {不做 X} | {是否做了 X?} | ✅/❌ |
| 接口契约 | {N 个接口} | {已实现 M 个} | M/N % |
| 测试覆盖 | spec 场景 {N} | 已写测试 {M} | M/N % |

## 目标漂移预警
- 🟢 对齐度 ≥ 90% → 继续
- 🟡 对齐度 70-89% → 警告，用户确认是否继续
- 🔴 对齐度 < 70% → 🛑 停下，回流 proposal 重新评估

## 用户决策点（对齐度 < 90%）
- [ ] 继续当前方向（接受漂移）
- [ ] 回流 proposal 调整目标
- [ ] 回流 spec 调整范围
```

## 八、技术债登记（轻微漂移不阻断）

🟡 轻微漂移不阻断流程，但必须登记，防止遗忘：

```markdown
# 技术债清单

| # | 类型 | 描述 | 登记日期 | 计划处理 | 状态 |
|---|------|------|---------|---------|------|
| 1 | 命名漂移 | spec 用 "userId"，代码用 "id" | 2026-06-28 | 下次迭代统一 | open |
| 2 | 注释漂移 | contracts 注释过时 | 2026-06-28 | 文档同步时修 | open |
```

## 九、AI 自检触发词

AI 在执行中遇到以下情况必须自检漂移：

| 触发情况 | 自问 | 行动 |
|---------|------|------|
| 写代码时发现 spec 描述模糊 | "spec 没说清，我是不是在猜？" | 🛑 输出漂移报告 |
| 写代码时发现契约与 spec 冲突 | "契约和 spec 谁对？" | 🛑 输出漂移报告 |
| fullstack-reviewer 发现实现与 spec 不符 | "代码错了还是 spec 错了？" | 🛑 输出漂移报告 |
| 用户说"这一块不行那一块有毛病" | "是不是目标漂移了？" | 🛑 跑目标对齐检查 |
| 连续打补丁超过 3 次 | "是不是根因没找对？" | 🛑 回流 spec 重新评估 |

---

## 十、检查清单

每个阶段结束时自检：

- [ ] 已输出 Spec Drift Report（即使无漂移也要输出 🟢）
- [ ] 🔴 严重漂移已回流修复
- [ ] 🟡 轻微漂移已登记技术债
- [ ] 目标对齐度 ≥ 90%（或用户确认接受漂移）
- [ ] BREAKING 变更已获用户确认
- [ ] 技术债清单已更新

---

## 十一、反面范例

| 反面（禁止） | 正确（必须） |
|---|---|
| 发现 spec 错了，改代码迁就 | 停下，先改 spec，再改代码 |
| 发现漂移但不报告 | 静默继续 = 违反铁律 1 |
| 严重漂移继续往前冲 | 🛑 停下回流 |
| 阶段切换不检查目标对齐 | 强制跑目标对齐检查点 |
| 轻微漂移忽略不管 | 登记技术债，不遗忘 |
| 汇报"已完成"但漂移未修 | 漂移未修 = 未完成 |
