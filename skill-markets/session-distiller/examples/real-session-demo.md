## 二、识别的反复道歉模式

### 模式一：搜索框自动填充 — 反复失败 (典型盲目重试)

**对话序列**:
```
User: 这个搜索框总是自己填内容
Agent: 添加 autoComplete="off"
User: 刷新页面还是有啊
Agent: 添加随机 name + type="search"
User: 还是一直出现
Agent: 移除搜索框控件
User: ？？？？？？？？移除这个控件
```

**V2 诊断结果**:

```
检测信号:
  ├─ 同一问题道歉 ≥ 3 次 → ✅ 触发诊断
  ├─ "还是有啊"/"还是一直出现" → ✅ 用户明确表示未解决
  └─ 最终方案是"移除"而非"修复" → ✅ 典型的放弃而非解决

根因分析:
  ├─ 技能缺陷? → ✅ 是
  │   └─ 缺少"浏览器环境特殊性"的系统化排查流程
  ├─ 提示词缺陷? → ✅ 是
  │   └─ Agent 不知道"尝试修复后必须验证是否真的生效"
  └─ 上下文缺失? → ✅ 是
      └─ 未区分"开发环境 HMR" vs "生产环境"的行为差异
```

**生成的反向提示词**:

```markdown
## 禁止项: 盲目尝试浏览器环境修复

NEVER: 添加属性后就声称"已修复"而不实际验证
触发条件: 修改任何浏览器相关的 HTML 属性（autocomplete / name / type）时
错误代价: 用户反复反馈"还是有" → 浪费时间 → 最终放弃
正确替代: 每次修改后必须在真实浏览器中验证

验证协议:
  Step 1 — 修改属性后，明确告知用户"请刷新浏览器验证"
  Step 2 — 用户验证前，不声称"已修复"
  Step 3 — 用户反馈"还是有"时，执行根因分析而非继续尝试
  Step 4 — 连续失败 ≥ 2 次后，停止修补，系统性分析浏览器机制

反例: 2026-05-16 会话中,搜索框自动填充问题连续尝试 4 次失败
  - 第 1 次: autoComplete="off" → 用户:"还是有啊"
  - 第 2 次: 随机 name + type="search" → 用户:"还是一直出现"
  - 第 3 次: 添加更多属性 → 用户:"？？？？？？？？移除这个控件"
  - 第 4 次: 移除搜索框 → 放弃而非解决

  根本原因: 
    1. 未区分 HMR 热更新 vs 浏览器缓存的行为差异
    2. 每次修改后未要求用户在"干净浏览器"中验证
    3. 缺少"浏览器 form restoration"机制的系统性理解
    4. 连续失败后仍未停止，继续盲目尝试

  教训: 浏览器环境的特殊性要求"每次修改必须验证",不能假设"代码改了就生效"
```

### 模式二：RunningHub 调查 — 浅尝辄止

**对话序列**:
```
User: 客户反馈 comfyui RunningHub 提交的 48GB 企业级共享 key 任务总是失败
Agent: (进行初步调查)
User: 这个到底啥原因哦,一直出现
Agent: (继续调查,但仍然在猜测)
User: 检查 AI service 的过时代码和死代码,UI 和后端都要强力检查
```

**V2 诊断结果**:

```
检测信号:
  ├─ 用户明确说"到底啥原因哦" → ✅ 表示 Agent 未找到根因
  ├─ 用户说"强力检查" → ✅ 要求系统性分析而非猜测
  └─ Agent 多次尝试不同方向但未深入 → ✅ 浅尝辄止

根因分析:
  ├─ 技能缺陷? → ✅ 是
  │   └─ 缺少"系统性数据流追踪"方法,容易陷入猜测
  ├─ 方法论缺失? → ✅ 是
  │   └─ 缺少"从错误日志定位 → 反向追踪调用链 → 验证假设"的标准流程
  └─ 验证不足? → ✅ 是
      └─ 修改代码后未确认"是否真的提交了正确的参数"
```

**生成的反向提示词**:

```markdown
## 铁律: 根因定位必须证据链闭环 (V10.6 强制)

MUST: 调查 Bug 时必须构建完整证据链:
  1. 从错误日志/用户反馈中提取**具体错误信息**
  2. 定位错误发生的确切位置（文件:行号）
  3. 反向追踪调用链，找到参数来源
  4. 验证每一层参数传递是否正确
  5. 修改后必须确认"参数真的改变了"

NEVER: 
  - 猜测可能的原因而非从证据出发
  - 修改代码但不验证参数是否真的传递到目标位置
  - 看到"某个参数可能缺失"就修改，不确认调用链

反例: 2026-05-16 RunningHub 调查中,Agent 多次猜测:
  - 猜测 1: "可能是 instanceType 没传递"
    → 修改后仍未解决
  - 猜测 2: "可能是 nodeInfoList 构建错误"
    → 部分正确但未深入
  - 猜测 3: "可能是 retainSeconds 缺失"
    → 最终找到根因

  根本原因:
    1. 没有从"错误日志: Invalid key length"出发
    2. 未构建"前端 → API → Handler → Client"完整调用链
    3. 多次猜测而非系统性排查

  教训: Bug 定位必须"从错误出发,反向追踪,证据闭环",不能"正向猜测,盲目尝试"

修复方案:
  1. 必须从 dev server 日志中提取**具体错误信息**
  2. 定位错误抛出的代码位置
  3. 用 gitnexus context() 理解调用链
  4. 逐层验证参数传递
  5. 修改后必须验证"参数真的改变了"(如添加日志输出完整请求体)
```

### 模式三：死代码清理 — 过度激进

**对话序列**:
```
Agent: (开始激进删除后端模块)
User: 你这删除有点过于激进,你确认这些没用了吗?这是做过计划迁移 lobeHub 的 ai 服务器接入的知识 ui 侧还没有激活这些功能哦
Agent: 明白了!这些文件是计划中的 LobeHub 迁移功能模块...
```

**V2 诊断结果**:

```
检测信号:
  ├─ 用户明确说"过于激进" → ✅ Agent 行为不当
  ├─ Agent 差点删除"计划中的功能模块" → ✅ 严重错误
  └─ Agent 未确认"是否真的无用"就行动 → ✅ 缺少验证

根因分析:
  ├─ 技能缺陷? → ✅ 是
  │   └─ 缺少"确认模块用途"的强制检查步骤
  ├─ 过度自信? → ✅ 是
  │   └─ 看到代码无引用就判定"死代码",未考虑"计划用途"
  └─ 缺少门禁? → ✅ 是
      └─ 没有"删除前必须用户确认"的机制
```

**生成的反向提示词**:

```markdown
## 禁止项: 删除代码前未确认计划用途

NEVER: 仅凭"无当前引用"就判定为死代码并删除
触发条件: 扫描到无引用的模块/文件时
错误代价: 删除计划中的功能模块 → 破坏项目规划 → 用户不满
正确替代: 删除前必须确认"是否为计划中的功能"

确认协议:
  Step 1 — 发现无引用模块时,搜索项目文档/计划/issue
  Step 2 — 检查是否有"TODO"/"计划中"/"待实现"的标注
  Step 3 — **询问用户**: "发现 X 模块无引用,是否可删除?"
  Step 4 — 用户确认后才能删除

反例: 2026-05-16 会话中,Agent 差点删除 LobeHub 迁移模块:
  - 看到 security/ 无引用 → 准备删除
  - 看到 model-runtime/ 无引用 → 准备删除
  - 用户及时阻止:"这是做过计划迁移 lobeHub 的..."

  根本原因:
    1. 缺少"删除前必须确认计划用途"的门禁
    2. 过度自信,未意识到"无引用 ≠ 死代码"
    3. 未询问用户就行动

  教训: 任何删除操作前,必须先询问用户"是否可删除",尤其是大型模块

强制门禁:
  删除文件 ≥ 3 个时 → 必须用户确认
  删除单个文件 ≥ 100 行时 → 必须用户确认
  扫描到"计划"/"TODO"/"待实现"关键词时 → 禁止删除,询问用户
```

## 三、V2 技能包如何阻止这些问题

### 阻止模式一：盲目重试

```
用户说: "搜索框总是自己填内容"
V2 执行:
  1. 🛑 检测到"浏览器环境修改"
  2. 触发验证协议: "修改后必须验证"
  3. Agent 添加 autoComplete="off"
  4. Agent 明确告知用户: "请刷新浏览器验证是否生效"
  5. 用户反馈: "还是有啊"
  6. 🛑 触发"失败分析协议"
  7. Agent 输出: [FAILURE ANALYSIS]
     - 错误操作: 仅添加 autoComplete="off"
     - 错误路径: 未考虑浏览器 form restoration 机制
     - 根因: 技能缺陷 — 缺少浏览器环境特殊性的系统化排查
     - 改进方案: 1) 区分 HMR vs 生产环境 2) 测试干净浏览器 3) 深入理解 form restoration
  8. Agent 不再盲目尝试,而是系统性分析浏览器机制
  9. 找到真正原因并修复
```

### 阻止模式二：浅尝辄止

```
用户说: "客户反馈 48GB 任务总是失败"
V2 执行:
  1. 🛑 触发"根因定位必须证据链闭环"铁律
  2. Agent 必须从 dev server 日志提取具体错误: "Invalid key length"
  3. Agent 定位错误位置: common-utils.ts:32 encryptApiKey()
  4. Agent 用 gitnexus context() 追踪调用链:
     service-manager.ts → updateService → encryptApiKey
  5. Agent 验证每一层参数传递
  6. Agent 找到根因: 密钥派生逻辑存在脆弱路径
  7. Agent 修复后验证: 添加诊断日志输出完整请求体
  8. 确认参数真的改变了
  9. 汇报用户:"根因已定位并修复,证据链完整"
```

### 阻止模式三：过度激进删除

```
Agent 扫描到: security/ 模块无引用
V2 执行:
  1. 🛑 触发"删除前必须确认计划用途"门禁
  2. Agent 搜索项目文档,发现"LobeHub 迁移计划"的标注
  3. Agent 询问用户: "发现 security/ 无引用,但在文档中看到'计划迁移 LobeHub',是否可删除?"
  4. 用户回复: "不能删除,这是计划中的功能"
  5. Agent 保留该模块
  6. 继续扫描其他模块
```

## 五、总结

**V2 技能包的价值**:

```
会话中的问题:
  ├─ 搜索框盲目重试 4 次 → 最终放弃
  ├─ RunningHub 调查浅尝辄止 → 多次猜测
  └─ 死代码清理过度激进 → 差点删除计划模块

V2 如何阻止:
  ├─ 强制验证协议 → 每次修改后必须验证
  ├─ 失败分析协议 → 连续失败时停止并分析根因
  ├─ 证据链闭环 → Bug 定位必须系统性追踪
  └─ 删除门禁 → 删除前必须用户确认

效果:
  ✅ 搜索框问题会在第 2 次失败后停止盲目尝试,系统性分析浏览器机制
  ✅ RunningHub 调查会从错误日志出发,构建完整证据链
  ✅ 死代码清理会在删除前询问用户,避免误删计划模块
```

> **核心要义**: 这个真实会话完美展示了"盲目重试"、"浅尝辄止"、"过度激进"三种模式。V2 技能包通过**强制验证、失败分析、证据链闭环、删除门禁**四项机制,彻底阻止这些问题的再次发生。
