## 最佳实践

### 设计原则

#### P1: 最小权限原则

```
默认禁止，显式允许。
每个 Execution Skill 只声明必需的权限，不申请多余权限。
```

#### P2: 失败即停止原则

```
任何门禁检查失败，立即停止后续操作，不尝试部分执行。
```

#### P3: 可追溯原则

```
所有执行操作必须记录：
- 执行时间戳
- 执行者（Agent ID / 用户）
- 输入参数
- 输出产物
- 影响范围
```

#### P4: 幂等性原则

```
相同输入执行多次，结果一致。
Execution Skill 必须支持安全重试。
```

#### P5: 回滚优先原则

```
执行失败时，优先执行回滚，恢复到执行前状态。
```

### 团队协作规范

#### 规范 1: Execution Skill 变更流程

```
1. 提出变更提案（含理由 + 影响范围）
2. 团队评审（至少 2 人 approve）
3. 实施（按 Phase 1-3 路线）
4. 门禁验证（自动化检查）
5. 文档同步更新
```

#### 规范 2: 门禁规则维护

```
- 新增规则：必须说明触发条件 + 预期效果 + 验证方法
- 修改规则：必须评估存量影响，走变更流程
- 删除规则：必须评估是否仍有依赖，走变更流程
```

#### 规范 3: Guard/Gateway 协作

```
Guard Skills 负责：
  - 安全规则定义
  - 规则校验逻辑
  - 违规处理策略

Gate Skills 负责：
  - 执行流程编排
  - 门禁节点管理
  - 回滚机制实现

协作方式：
  Gate 调用 Guard 检查 → Guard 返回结果 → Gate 决定继续/回滚
```

### 度量指标

#### 核心指标

| 指标 | 定义 | 目标值 | 采集方式 |
|------|------|--------|----------|
| 规则覆盖率 | 已覆盖场景 / 总场景 | ≥ 80% | 静态分析 |
| 规则命中率 | 命中规则次数 / 总执行次数 | ≥ 60% | 日志统计 |
| 门禁通过率 | 一次通过次数 / 总执行次数 | ≥ 90% | CI 统计 |
| 平均回滚时间 | 从失败到恢复的平均时间 | ≤ 5 分钟 | 日志分析 |
| 新技能接入时间 | 从需求到上线的时间 | ≤ 2 天 | 项目管理 |

#### 质量指标

| 指标 | 定义 | 目标值 | 采集方式 |
|------|------|--------|----------|
| 文档完整率 | 有文档的技能 / 总技能 | 100% | 静态检查 |
| 示例覆盖数 | 有示例的场景 / 总场景 | ≥ 70% | 目录扫描 |
| 安全漏洞数 | 发现的安全问题数量 | 0 | 扫描工具 |
| 告警误报率 | 误报次数 / 总告警次数 | ≤ 10% | 反馈统计 |

### 常见问题

#### Q1: Execution Skill 与普通函数的区别？

```
Execution Skill 是带门禁的执行单元：
- 普通函数：只负责业务逻辑
- Execution Skill：业务逻辑 + 前置检查 + 后置校验 + 回滚机制

核心差异：Execution Skill 强制走门禁流程，不绕过检查。
```

#### Q2: 如何处理门禁检查失败？

```
标准处理流程：
1. 记录失败原因（日志 + 告警）
2. 执行回滚操作（恢复到执行前状态）
3. 通知责任人（Agent / 用户）
4. 归档失败记录（用于后续分析）

禁止：
- 忽略失败继续执行
- 手动绕过门禁
- 删除门禁检查（除非走变更流程）
```

#### Q3: Guard Skills 和 Gate Skills 如何分工？

```
Guard Skills:
  - 定义"不能做什么"（禁止性规则）
  - 聚焦安全边界
  - 示例：禁止删除 docs/references/；禁止绕过门禁

Gate Skills:
  - 定义"怎么做"（流程性规则）
  - 聚焦执行流程
  - 示例：发布前必跑测试；变更后必更新文档

协作模式：
  Gate 编排流程 → Guard 校验边界 → 二者缺一不可
```

#### Q4: 如何评估是否需要新增 Execution Skill？

```
判断标准（满足任一即可新增）：
1. 有独立的数据变更场景（非现有 Skill 覆盖）
2. 有独立的文档同步场景（非现有 Skill 覆盖）
3. 有独立的配置管理场景（非现有 Skill 覆盖）
4. 有独立的资产管理场景（非现有 Skill 覆盖）
5. 有独立的发布流程场景（非现有 Skill 覆盖）

禁止新增：
1. 现有 Skill 已覆盖（改为扩展现有 Skill）
2. 场景过于简单（直接内联，不建 Skill）
3. 场景过于复杂（拆分为多个 Skill）
```

#### Q5: 如何处理规则冲突？

```
冲突类型：
1. Guard vs Guard：两条禁止规则冲突
2. Guard vs Gate：禁止规则与流程规则冲突
3. Gate vs Gate：两条流程规则冲突

解决原则：
1. 优先级：安全 > 业务 > 便捷
2. 冲突上报：发现冲突立即上报，不自行解决
3. 显式声明：冲突解决方案必须在文档中显式声明
```

#### Q6: 如何平衡严格度和开发效率？

```
分阶段策略：
- Phase 1: 建立最小规则集，允许例外（显式记录）
- Phase 2: 扩展规则，收紧例外条件
- Phase 3: 全面严格，例外需特批

度量驱动：
- 通过门禁通过率指标监控严格度影响
- 目标：通过率 ≥ 90%（低于则说明规则过严或质量不足）

迭代优化：
- 每两周复盘：哪些规则命中过低（可能过严）
- 哪些规则从未命中（可能过松或无效）
- 哪些规则频繁误报（需优化判定逻辑）
```
