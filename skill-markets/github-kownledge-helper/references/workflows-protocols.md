## 7. 任务启动探测协议（2026-08-13 新增）

> 核心：**先报告现状 + 列决策点 → 等用户确认 → 才动手**。
> 反模式：用户给一堆「放好的资源」就开干，盲改目录/文件，结果方案错位要返工。

### 触发场景

- 用户说「你看看 X」「处理一下 Y」「这些仓库你看看」
- 任何**未知初始状态**的任务（资源已存在但结构未知）
- 涉及**多个决策点**的任务（路径/命名/版本/工具/聚合结构）

### 协议（4 步强制）

```
Step 1 — 探测（仅读，不写）
  ├─ scan 目录结构（用 Recurse + Force，识别隐藏 .git）
  ├─ 对每个 git 仓库读 origin / branch / commit / 备注
  └─ 汇总成「现状报告」表（路径、origin、commit、是否合规）

Step 2 — 列决策点
  ├─ 找出现状与规范的差异（命名 / 路径 / schema / 版本 / fork 状态）
  ├─ 把每个差异作为决策点摆出（如：「opencode 是 fork，是否切换到官方？」）
  └─ 用 AskUserQuestion 一次问所有关键决策点（≤ 4 个）

Step 3 — 等用户决策
  └─ 收到决策后再动手。**绝不**「先做了再说」。

Step 4 — 执行计划公示
  └─ 在动手前列阶段计划（如阶段 1 改名 / 阶段 2 写 manifest / 阶段 3 ...），
     让用户看到完整路径。
```

### 反例（不应发生）

- ❌ 收到「看看如何处理」就立即 `git clone` / `Rename-Item` / `Write-Item`
- ❌ 探测时用 LS（不显示隐藏 .git），漏看 26 个嵌套 git 仓库
- ❌ 决策点超过 4 个导致问题分多次问（一次性 ≤ 4）

### 验证

- [ ] 是否有「现状报告」表？
- [ ] 是否在动手前先问决策点？
- [ ] 计划是否分阶段（每阶段可独立验证）？

## 8. 技术栈迁移协议（2026-08-13 新增）

> 核心：**变更前先列决策点 + 变更后删旧 + 用户视角跑通**。
> 反模式：保留旧脚本（ps1 与 ts 并存），开发子目录跑通就以为交付完。

### 触发场景

- 用户要求更换技术栈（PowerShell → Node.js / Python → Go / etc.）
- 跨平台需求（Windows → macOS / Linux 兼容）
- CLI 化（从 GUI / 一次性脚本 → 可重入 CLI）

### 协议（5 步强制）

```
Step 1 — 决策点
  ├─ 放在子目录还是项目根？ → 用户视角决定
  ├─ 目录命名（避免与 npm scripts 概念冲突）
  ├─ 是否废弃旧实现？→ 是：清理红线
  └─ 验证标准（typecheck / 跑通 / 跨平台）

Step 2 — 创建新结构
  ├─ package.json / tsconfig.json / pnpm-workspace.yaml
  ├─ 源码目录（bin/ + src/commands/ + src/lib/）
  └─ 配置必须兼容新栈（allowBuilds for native dep）

Step 3 — 迁移
  ├─ 一对一翻译旧脚本逻辑（不"优化"，先等价）
  ├─ 实跑对比：旧结果 vs 新结果（计数 / 状态 / 错误信息）
  └─ typecheck exit 0

Step 4 — 清理
  ├─ 删除旧脚本（不留双重实现 → 必然分叉）
  ├─ 删 .bak / .tmp / __pycache__ 等临时文件
  └─ 更新 .gitignore

Step 5 — 用户视角验证
  ├─ 切换到项目根（用户工作目录）跑所有命令
  ├─ 跑通才算交付
  └─ 在 pitfalls 记录迁移期间踩的坑（供下次参考）
```

### 反例（不应发生）

- ❌ 旧 ps1 与新 ts 并存 → 用户不知道用哪个，必然分叉
- ❌ 在 src-cli/ 子目录验证通过就交付 → 用户在项目根跑报错
- ❌ 跳过 typecheck 直接跑 → 编译错误抛到运行时
- ❌ "优化" 旧脚本逻辑一并改 → 验证成本 ×2

### 验证

- [ ] 旧脚本是否完全删除？
- [ ] 项目根跑所有命令 exit 0？
- [ ] typecheck exit 0？
- [ ] pitfalls 是否有本次迁移踩坑条目？
