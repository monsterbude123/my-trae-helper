# 原型-vs-代码差距分析方法论

> 场景：归档后发现"原型设计里的功能找不到"或代码未实现。诊断方法，不是 reviewer 验收。
> 核心：三组并行对比 + 功能点提取 + 漂移等级判定 + feedback-loop 回流。

---

## §0 三大铁律

```
1. MUST 三组并行对比（委派 3 个子代理）
   - spec-writer: spec 文件 vs 代码
   - prototype-writer: prototype 文件 vs 代码
   - contract-writer: contract 文件 vs 代码

2. MUST 功能点提取 + 状态判定
   - 状态: ✅已实现 / 🟡部分实现 / ❌未实现 / 🔵延期

3. MUST 漂移等级判定 + 回流路径
   - 🟢无漂移(≥90%) → 继续
   - 🟡轻微(70-89%) → 警告但继续，记入技术债
   - 🔴严重(<70%) → 必须回流
```

---

## §1 诊断流程（5 步）

```
Step 0 — 触发: 用户说"原型功能找不到" / 归档后发现未实现 / spec 与代码不一致

Step 1 — 三组并行对比（委派 3 个 search 子代理）
  ├─ spec-writer: 读 spec → 提取功能点 → 对照代码
  ├─ prototype-writer: 读 prototype → 提取功能点 → 对照代码
  └─ contract-writer: 读 contract → 提取功能点 → 对照代码

Step 2 — 功能点状态判定
  ├─ ✅ 已实现: 代码存在 + 功能完整
  ├─ 🟡 部分实现: 代码存在但功能不完整/stub
  ├─ ❌ 未实现: 代码不存在或仅 mock
  └─ 🔵 延期: 明确标注 Out of Scope

Step 3 — 漂移等级判定（按实现率）: ≥90% 🟢 / 70-89% 🟡 / <70% 🔴

Step 4 — 回流路径决策
  ├─ spec 错 → 回流 spec-writer
  ├─ 契约错 → 回流 contract-writer
  ├─ 代码错 → 回流 implementer
  └─ 目标错 → 回流 proposal-writer
```

---

## §2 消除 mock/stub 操作清单

```
搜索关键词: mock / MOCK_ / 占位 / stub / pending / TODO / 延期标记

操作规则:
  1. mock 描述 → 删除或重写为真实实现描述
  2. 延期未实现 → 移入 Out of Scope
  3. 枚举值不一致 → 对齐代码中的实际枚举
  4. 版本标记 → 改为 "v{N}（回流修正）"
```

---

## §3 反例

| 错误操作 | 后果 | 教训 |
|---------|------|------|
| 只清理措辞标签，不检查功能实现 | 大量功能未实现但文档看起来正常 | 必须三组并行对比代码 |
| reviewer 以"mock-first 合理范围"放行 | 超前归档，用户发现功能缺失 | mock ≠ 功能完成 |
| spec 枚举与代码枚举不一致 | 前后端脱节，运行时错误 | 必须对齐实际枚举 |
| 归档前未检查延期标记解析 | 归档后发现大量未实现功能 | 归档门禁必须含延期标记审计 |
