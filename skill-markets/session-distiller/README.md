## V2 核心增强

### 🎯 错误路径诊断

**识别反复道歉的 5 大模式**:
```
1. 盲目重试 — "再试一次" 但无具体改进
2. 甩锅子代理 — "子代理给了虚假内容"
3. 应付性汇报 — 自评 PASS 但 evidence 造假
4. 上下文击穿 — 反复读取大文件导致信息丢失
5. 工具误用 — 用 search 做 implementer
```

**诊断协议**:
```
检测信号:
  ├─ 同一问题道歉 ≥ 2 次 → 触发诊断
  ├─ "我搞错了"/"应该 xxxx"/"抱歉" → 标记为无效道歉
  └─ "重新尝试"但无具体改进 → 标记为盲目重试

诊断步骤:
  Step 1 — 识别错误模式 (Agent 实际执行了什么?)
  Step 2 — 根因分析 (技能/提示词/工具/上下文?)
  Step 3 — 反向提示词生成 (转化为 NEVER 项)
  Step 4 — Agent-子代理交互质量分析
```

### 🚫 反向提示词生成

将错误操作转化为禁止项:

```markdown
## 禁止项: 盲信子代理产物

NEVER: 子代理返回 "PASS" 就直接接受
触发条件: 任何子代理返回 Completion Report 时
错误代价: evidence 造假 + pass_count 不准确 + 虚假完成
正确替代: 主上下文必须独立抽检 1 个 evidence

反例: 2026-07-XX 会话中,reviewer 自评 PASS,实际 evidence 指向空行
  - 当时做了: 直接接受 reviewer 的 "PASS"
  - 导致后果: 虚假完成,用户发现产物不存在
  - 根本原因: 主上下文未执行 evidence 独立抽检
  - 教训: 每次必须随机抽 1 个 evidence → 主上下文亲自 Read 验证
```

### 🔍 Agent-子代理交互质量分析

**交互质量检查清单**:
```
[ ] 委派正确性检查
    ├─ subagent_type 是否正确?
    ├─ 是否遗漏 [MUST] 注入项?
    └─ 是否注入了 [DOC_WHITELIST]?

[ ] 白名单遵守检查
    ├─ 子代理是否读了 layer=process/log 文档?
    ├─ 主上下文是否提取了事实摘要注入?
    └─ 是否绕过了 GitNexus 降级为 grep?

[ ] Completion Report 真实性检查
    ├─ evidence 字段是否真实?
    ├─ pass_count 是否准确?
    └─ 主上下文是否独立抽检?

[ ] 子代理失败处理检查
    ├─ 是否连续失败 ≥ 2 次?
    ├─ 是否有应付性汇报?
    └─ 是否达到阻塞阈值?
```

## 核心价值

**拒绝敷衍整理**。不是"会议纪要",而是"可执行的方法论"。

### 三大铁律

```
1. 验证性 > 叙述性
   - ❌ "保持代码整洁" (无法验证)
   - ✅ "函数 ≤ 50 行,单文件 ≤ 800 行" (可机器校验)

2. 具体性 > 抽象性
   - ❌ "写代码前先思考" (空泛)
   - ✅ "修改代码前必须运行 impact()" (具体流程)

3. 反例价值 > 正例价值
   - ❌ 只说"应该这样做"
   - ✅ 记录"踩坑:当时误以为 X,实际是 Y,教训是 Z"
```

## 蒸馏流程

```
Step 1 — 意图识别
  ├─ 用户真实需求是什么?
  ├─ 一次性任务 vs 可复用流程?
  └─ 核心价值点是什么?

Step 2 — 模式提取
  ├─ 重复出现的操作模式?
  ├─ 决策路径?
  └─ 边界条件?

Step 3 — 铁律提炼
  ├─ 哪些操作必须执行? (MUST)
  ├─ 哪些行为禁止执行? (NEVER)
  └─ 哪些场景必须回退? (ROLLBACK)

Step 4 — 反例萃取
  ├─ 踩过的坑?
  ├─ 静默失败的案例?
  └─ 边界失效的案例?

Step 5 — 输出生成
  ├─ SKILL.md (核心铁律 + 骨架流程)
  ├─ references/ (详细方法论)
  └─ templates/ (产出模板)
```

## 质量保证

蒸馏完成后强制执行质量检查:

```
[ ] 验证性检查 — 每条铁律都有验证方法?
[ ] 具体性检查 — 有具体命令/路径?
[ ] 完整性检查 — 适用范围已界定?
[ ] 反例检查 — 每个最佳实践配失败案例?
[ ] 可执行性检查 — Agent 加载后可立即执行?
```

得分 ≥ 4.0 才可交付。

## 使用示例

### 场景: 从会话中提炼代码审查技能

**会话历史**:
```
User: "帮我重构这个模块"
Agent: "好的,我先运行 impact()... 发现风险等级 HIGH,建议分步重构"
User: "直接改吧"
Agent: "🛑 风险过高,必须用户确认"
User: "好吧,先改第一部分"
...
Agent: "完成,运行测试... 通过"
User: "为什么有个测试被注释掉了?"
Agent: "哦,那个测试一直失败..."
User: "❌ 这是严重违规"
```

**提炼出的技能**:

```markdown
---
name: code-review-iron-laws
description: 代码审查铁律 — 不可协商的质量门禁
---

## 铁律一: 影响面评估不可跳过

MUST: 修改代码前必须运行 impact()
MUST: 风险等级 HIGH → 必须用户确认
NEVER: 直接跳过影响面评估

反例: 2026-07-XX 会话中,跳过 impact() 导致崩溃

## 铁律二: 禁止注释/删除失败的测试

MUST: 测试失败 → 修复代码,不是修改测试
NEVER: 注释/删除测试让用例通过

反例: 2026-07-XX 会话中,注释测试导致隐藏 bug
```

## 常见问题

### Q: 如何判断是否值得提炼技能?

```
一次性任务 (如:修复某个 bug) → ❌ 不值得
可复用流程 (如:每次都要做代码审查) → ✅ 值得
```

### Q: 提炼出的技能质量不高怎么办?

```
运行 §3 质量检查清单:
  - 验证性低 → 添加验证方法
  - 具体性低 → 补充具体路径/命令
  - 反例得分低 → 添加失败案例
```

### Q: 缺少失败案例怎么办?

```
1. 搜索历史会话/bug 记录
2. 构造边界失效场景
3. 标注"待实战验证"
```
