# 三源融合方法论

> 场景：旧文档有业务逻辑但视觉过时，新设计有视觉但缺交互逻辑，标准有约束但散落。
> 核心：双源并行 Intake + 映射表 + 批量并行委派 + 变更验证。

---

## §0 三大铁律

```
1. MUST 双源并行 Intake
   - 旧源子代理: 提取业务逻辑（做什么）
   - 新源子代理: 提取视觉规范（怎么做）
   - 主上下文: 提取标准约束（边界）
   - 禁止串行执行（会遗漏细节）

2. MUST 映射后批量并行委派
   - Intake 完成 → 产出模块映射表
   - 每个模块一个子代理并行执行
   - TodoWrite 追踪进度（N/M）

3. MUST 变更验证 + 增量修正
   - git diff --stat 验证变更量
   - grep 检查遗留问题（旧色值/旧术语）
   - 全部通过后再清理旧文件
```

---

## §1 流程骨架（5 步）

```
Step 1 — 双源并行 Intake（委派 2 个 search 子代理）
  ├─ 子代理A: 读旧文档 → 提取业务逻辑清单
  ├─ 子代理B: 读新设计 → 提取视觉规范清单
  └─ 主上下文: 读标准 → 提取约束条件

Step 2 — 映射表生成
  ├─ 旧文档模块 → 新设计页面对应关系
  ├─ 差异评估 → 哪些需重写 / 哪些需增量修正
  └─ 任务列表 → N 个模块待处理

Step 3 — 批量并行委派（TodoWrite 追踪）
  ├─ 每个模块一个 general_purpose_task 子代理
  └─ 注入: 业务逻辑来源 + 视觉规范来源 + 标准约束

Step 4 — 变更验证
  ├─ git diff --stat → 验证变更量
  └─ grep 检查遗留问题 → 发现问题增量修正

Step 5 — 干净归档
  ├─ 旧文件移至 docs/bak_{旧版本}doc/
  └─ 空目录删除
```

---

## §2 MUST / NEVER 清单

```
MUST: 双源并行 Intake / 产出映射表 / TodoWrite 追踪 / git diff 验证 / grep 检查 / 旧文件归档
NEVER: 串行 Intake / 不追踪进度就委派 / 不验证遗留 / 直接删除旧文件
```

---

## §3 反例

```
反例 1（串行 Intake）:
  先读旧文档 → 再读新设计 → 读新设计时旧文档细节已遗忘
  → 映射表漏掉关键业务逻辑。教训: 双源必须并行读取。

反例 2（不验证遗留问题）:
  子代理返回"完成" → 直接归档旧文件
  → grep 发现旧色值 slate-900 仍残留 12 处
  教训: 归档前必须 grep 检查，发现问题增量修正。
```
