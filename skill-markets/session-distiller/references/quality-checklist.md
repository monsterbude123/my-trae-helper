# 会话蒸馏质量检查清单

> 蒸馏完成后强制执行,逐项检查。得分 < 4.0 必须返工。

---

## 一、验证性检查 (权重 25%)

### 1.1 每条铁律都有验证方法?

```
检查项: 对每条 MUST/NEVER 规则,确认有对应的验证方法

判定标准:
  ✅ 有具体验证方法 (如: wc -l, 脚本检查, 人工检查项)
  ⚠️ 有验证方法但不具体 (如: "检查一下")
  ❌ 无验证方法

示例:
  ✅ 铁律: 函数 ≤ 50 行
     验证: wc -l 或 linter

  ❌ 铁律: 代码要整洁
     验证: 无
```

### 1.2 无法验证的已标注为"建议"?

```
检查项: 确认所有无法验证的规则已降级为"建议"

判定标准:
  ✅ 无法验证的规则已标注为"建议"或"Tips"
  ❌ 无法验证的规则仍标注为"铁律"

示例:
  ✅ 建议: 优先选择易读的实现方式

  ❌ 铁律: 代码要有可读性 (无法验证)
```

### 1.3 有具体阈值而非抽象描述?

```
检查项: 规则中有具体的数值/路径/命令

判定标准:
  ✅ 有具体阈值 (如: ≤800 行, impact(), spec.md)
  ⚠️ 有部分具体 (如: "某个配置文件")
  ❌ 全是抽象描述 (如: "适当的行数")

示例:
  ✅ 函数 ≤ 50 行,单文件 ≤ 800 行

  ❌ 函数不要太长,文件不要太大
```

## 二、具体性检查 (权重 25%)

### 2.1 有具体命令/路径?

```
检查项: 引用文件/工具时有具体路径或命令

判定标准:
  ✅ 有具体路径 (如: .trae/rules/strict.md)
  ⚠️ 有部分具体 (如: "某个 .trae 文件")
  ❌ 全是抽象描述 (如: "配置文件")

示例:
  ✅ 修改 .trae/rules/strict.md

  ❌ 修改配置文件
```

### 2.2 有具体流程?

```
检查项: 操作步骤有具体流程而非抽象描述

判定标准:
  ✅ 有具体流程 (Step 1/2/3 + 具体动作)
  ⚠️ 有部分流程 (如: "先检查")
  ❌ 无流程 (如: "思考一下")

示例:
  ✅ Step 1: Read spec.md
     Step 2: GitNexus context()
     Step 3: 读模块文档
     Step 4: 输出理解确认

  ❌ 先思考一下,然后开始写
```

### 2.3 有具体判定标准?

```
检查项: 判定条件有具体标准而非"视情况而定"

判定标准:
  ✅ 有具体判定 (如: HIGH → 必须确认)
  ⚠️ 有部分判定 (如: "如果风险高")
  ❌ 无判定标准 (如: "视情况而定")

示例:
  ✅ 风险等级 HIGH → 必须用户确认
     风险等级 MEDIUM → 建议用户确认
     风险等级 LOW → 可直接执行

  ❌ 视风险情况决定是否需要用户确认
```

## 三、完整性检查 (权重 20%)

### 3.1 适用范围已界定?

```
检查项: 方法/规则的适用场景已明确

判定标准:
  ✅ 有明确适用场景 (如: "适用于 Tauri 项目")
  ⚠️ 有部分说明 (如: "适用于大多数情况")
  ❌ 无适用范围说明

示例:
  ✅ 适用于: Tauri 桌面应用 + UI/UX 维度
     不适用于: 纯后端 API 项目

  ❌ 通用方法
```

### 3.2 不适用场景已列出?

```
检查项: 方法失效的场景已明确列出

判定标准:
  ✅ 有明确不适用场景 + 原因
  ⚠️ 有部分说明
  ❌ 无不适用场景说明

示例:
  ✅ 不适用场景:
     - 纯后端项目 (无 UI)
     - 无视觉证据要求的项目 (已显式锁定)

  ❌ 适用于所有场景
```

### 3.3 前置依赖已声明?

```
检查项: 执行方法需要的前置条件已明确

判定标准:
  ✅ 有完整依赖声明 (工具/环境/知识)
  ⚠️ 有部分声明
  ❌ 无依赖声明

示例:
  ✅ 依赖: GitNexus MCP Server + impact() 工具可用
     降级: GitNexus 不可用时 → 阻塞,禁止降级为 grep

  ❌ 默认环境可用
```

## 四、反例检查 (权重 20%)

### 4.1 每个最佳实践至少配 1 个失败案例?

```
检查项: 所有最佳实践/MUST 规则都有对应的失败案例

判定标准:
  ✅ 每条重要规则都有失败案例
  ⚠️ 部分规则有失败案例
  ❌ 无失败案例

示例:
  ✅ 铁律: 修改代码前必须 impact()
     反例: 2026-07-XX 会话中,跳过 impact() 导致 12 模块崩溃

  ❌ 铁律: 修改代码前必须 impact()
     (无失败案例)
```

### 4.2 失败案例有根因分析?

```
检查项: 失败案例包含根因分析而非表面描述

判定标准:
  ✅ 有根因分析 (为什么会失败 + 深层原因)
  ⚠️ 有部分分析 (描述了现象)
  ❌ 无分析 (只说"失败了")

示例:
  ✅ 根因: 误以为小改动无风险,实际影响面广
     深层原因: 未建立影响面评估意识

  ❌ 失败了,因为没跑 impact()
```

### 4.3 有"避坑指南"?

```
检查项: 失败案例后有明确的避坑方法

判定标准:
  ✅ 有避坑指南 (如何避免 + 具体方法)
  ⚠️ 有部分指南 (如: "要小心")
  ❌ 无避坑指南

示例:
  ✅ 避坑方法:
     1. 修改前强制 impact()
     2. 风险等级 HIGH 必须用户确认
     3. 建立"小改动也有大风险"的意识

  ❌ 以后要注意
```

## 五、可执行性检查 (权重 10%)

### 5.1 Agent 加载后可立即执行?

```
检查项: 规则/方法无缺失的前置条件或依赖

判定标准:
  ✅ Agent 加载后可立即执行 (无缺失信息)
  ⚠️ 需要少量上下文补充
  ❌ 有缺失前置条件或依赖

示例:
  ✅ 修改代码前必须 impact({target: 'symbolName'})
     (已有 GitNexus 工具)

  ❌ 修改代码前必须运行某个脚本
     (未说明脚本路径或来源)
```

### 5.2 无歧义表述?

```
检查项: 规则/方法无多义性解读

判定标准:
  ✅ 无歧义表述 (只有一种解读)
  ⚠️ 有少量歧义 (但不影响执行)
  ❌ 有歧义表述 (可能导致误执行)

示例:
  ✅ 函数 ≤ 50 行 (无歧义)

  ❌ 函数不要太长 (歧义: 多长算太长?)
```

### 5.3 无缺失前置条件?

```
检查项: 所有前置条件已明确列出

判定标准:
  ✅ 前置条件完整 (无缺失)
  ⚠️ 有部分缺失 (但可推断)
  ❌ 有重要前置条件缺失

示例:
  ✅ 前置条件:
     - GitNexus MCP Server 可用
     - 已索引当前项目
     - impact() 工具可用

  ❌ (前置条件未列出)
```

## 六、得分计算

```
总分 = (验证性得分/3 × 25%)
     + (具体性得分/3 × 25%)
     + (完整性得分/3 × 20%)
     + (反例得分/3 × 20%)
     + (可执行性得分/3 × 10%)

得分判定:
  4.5 - 5.0 🟢 优秀
  4.0 - 4.4 🟡 可接受
  3.0 - 3.9 🟠 需改进
  0.0 - 2.9 🔴 必须返工

得分 ≥ 4.0 才可交付。
```

## 七、常见问题与处理

### 7.1 得分 < 4.0 怎么办?

```
处理流程:
  1. 定位得分最低的检查项
  2. 针对性改进:
     - 验证性低 → 添加验证方法
     - 具体性低 → 补充具体路径/命令
     - 完整性低 → 补充边界条件
     - 反例得分低 → 添加失败案例
     - 可执行性低 → 补充前置条件
  3. 重新检查
  4. 重复直到得分 ≥ 4.0
```

### 7.2 某条规则确实无法验证怎么办?

```
处理方式:
  1. 标注为"建议"而非"铁律"
  2. 补充说明: "此建议基于经验,无法机器验证"
  3. 提供人工检查项 (如: "人工检查: 是否有注释?")
```

### 7.3 缺少失败案例怎么办?

```
处理方式:
  1. 如果是新方法,无失败案例 → 标注"待实战验证"
  2. 如果是已有方法 → 搜索历史会话/bug 记录
  3. 如果确实无案例 → 构造边界失效场景
     - "假设场景 X,方法可能失效,原因是 Y"
```

---

> **记住**: 质量检查不是走过场,而是确保提炼出的方法论**真的有用、真的可执行、真的能避免踩坑**。
