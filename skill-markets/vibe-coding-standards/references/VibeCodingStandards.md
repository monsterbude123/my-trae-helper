# Vibe Coding 核心组件编写原则 · v2.5.0

**适用场景**：项目级 AI 代理（多智能体编排、代码生成、自动化脚本系统）的系统提示词、规则、技能与子代理设计。
**核心理念**：分层治理、按需加载、**地图内联（防迷路）** + **规范指针（防击穿）**。

## 一、AGENTS.md 编写原则（项目“宪法”）

`AGENTS.md` 是项目级的长效 System Prompt，定义 AI 代理的身份、工作方式和边界约束。作为主入口，它的**轻量化**决定了整个多智能体系统的响应速度和智商下限。

### 1.1 核心结构与体积红线

* **体积弹性范围 100~350 行（v2.5 放宽 +30%）**。< 100 行：过度拆分导致文件碎片化，反而难维护；350 行：触发上下文击穿风险，应拆。**> 350 行才考虑提取 references/**。超过此限制会大幅增加"中间遗忘（Lost in the Middle）"的风险。
* **内容定位：** 仅包含“大纲 + 指针”，所有具体规范必须剥离并通过相对路径引用。

| 模块 | 作用 | 关键要点 |
| --- | --- | --- |
| **Non-negotiables** | 不可妥协的铁律 | 冲突时仅低于用户直接指令（≤ 5条） |
| **Version & Changelog** | 版本与变更记录 | 标注语义化版本号，重大变更简述原因 |
| **Goal-driven execution** | 目标驱动 | 模糊需求转化为可验证的成功标准 |
| **Surgical changes** | 修改范围控制 | 只动必须改的，不做“顺路优化” |
| **Persistence Rule** | 持久化原则 | **每次代码更新时，必须同步保存所有脚本，禁止遗留未保存状态。** |
| **Tool use & Failure** | 工具与失败回退 | 运行代码 > 猜测代码。连续失败 2 次必须停止并上报 |
| **Communication style** | 沟通风格 | 直接、简洁。有歧义就问，小事直接做（减少不必要的 AskUserQuestion） |
| **Session hygiene** | 会话管理 | 上下文是稀缺资源，用子代理做探索，不污染主对话 |
| **Self-improvement loop** | 自我迭代 | 犯错后补充规则，定期修剪冗余。与 Rules 的增量迭代呼应 |
| **Project Context** | 项目地图（内联）+ 规范指针 | 技术栈/目录树/架构图内联；详细规范指针引用 |

### 1.2 冲突解决黄金法则

当用户即时指令与 `AGENTS.md` 冲突时，以**用户指令为最高优先级**，但 AI 必须明确告知用户冲突点并征求确认，严禁静默违反系统约束。

### 1.3 项目地图原则（防机械指针化）

> **核心洞察**：agent 不知道项目长什么样就会迷路，迷路后的盲搜消耗远大于多内联 30 行。

`AGENTS.md` 的内容分为两类，判定标准完全不同：

| 类型 | 判定口诀 | 策略 | 示例 |
|------|---------|------|------|
| **🗺️ 地图** | "不知道这个会迷路吗？" → 是 | **必须内联** | 技术栈清单、目录结构树、ASCII 架构拓扑图、关键入口文件路径、启动/构建命令、核心设计决策（≤3条）、关键命名/路径约定 |
| **📋 规范** | "不知道这个会迷路吗？" → 否 | **指针引用** | API 详细文档、鉴权流程完整实现、长代码示例（>10行）、配置项完整列表、部署运维手册、历史决策记录 |

**地图的弹性范围 100~350 行（v2.5 放宽）**，条件：每行都经得起"不知道会迷路"的拷问。> 350 行才考虑提取 references/。

**反例（机械指针化的错误）**：
- ❌ 把技术栈 ASCII 架构图（16 行）剥离为指针 → agent 看不到项目拓扑，乱猜模块关系
- ❌ 把目录结构树（42 行）剥离为指针 → agent 不知道文件在哪，盲搜浪费 token
- ❌ 把启动脚本（7 行）剥离为指针 → agent 不知道怎么跑项目，反复试错

**正例（正确的地图内联）**：
- ✅ 架构拓扑图内联 → agent 一眼看清模块关系
- ✅ 一级目录树内联 → agent 知道去哪找什么
- ✅ `npm run dev` / `uv run pytest` 内联 → agent 不用猜命令

## 二、Rules 编写原则（代码“法律”）

`Rules`（如 `.cursorrules` / `CLAUDE.md`）是聚焦于“代码具体应该长什么样”的细粒度规范。偏向可自动检测或人工快速评审的技术约束。

### 2.1 模块化分层与指针模式

严禁在 Rules 中塞满大段代码示例。所有示例必须指向独立文件。

* **P0 - 生产阻断级**（必须遵守）
* 外部输入必须经过 Zod/Pydantic 校验。
* 数据库写操作必须在事务中。


* **P1 - 架构规范**
* API 层只做参数校验和转发，不写业务逻辑。


* **P2 - 代码风格与可读性**
* 单函数不超过 30 行；禁止吞掉异常。
* 复杂逻辑（圈复杂度 > 5）必须加注释解释“为什么这么做”。


* **P3 - 参考规范指针**（防击穿设计）
* 正确的鉴权写法：参考 `references/auth-flow-example.ts`
* UI 组件规范：参考 `references/ui-components-standard.md`



### 2.2 增量迭代

AI 犯一次错加一条规则，全团队共享 Git 版本。规则必须可验证（Lint 自动检测或人工评审点）。

## 三、Skills 编写原则（专业“手册”）

Skill 是按需加载的专业知识包。它必须开箱即用，且具备明确的退出机制与上下文保护。

### 3.1 结构与体积红线

* **体积弹性范围 100~350 行（v2.5 放宽）**。纯铁律 ≤ 200 行。 < 100 行：过度拆分；> 350 行：必须提取 references/。
* **内容约束：** 只能放置**核心铁律**和**骨架流程**。禁止啰嗦。详细内容必须通过文件引用的方式引出，让 AI 在需要时主动选择读取（按需加载）。

**标准文件结构：**

```text
skill-name/
├── SKILL.md          # 核心骨架与入口（v2.5：弹性 100~350 行，最合适；> 350 行必须提取 references/）
├── references/       # 深度参考资料、长篇原理与长代码（仅按需查阅）
├── templates/        # 模板文件
└── scripts/          # 可执行辅助脚本

```

### 3.2 SKILL.md 标准格式 (YAML + Markdown)

```yaml
---
name: react-component-generator
description: 严格根据骨架生成 React 组件。
trigger: ["创建组件", "生成组件"]
version: 2.0
---

```

* **Prerequisites（前置条件）**：缺失依赖时立即报错并给出指引，不盲目执行。
* **Core Workflow（骨架流程）**：每步一句话，通过路径引用细节（例如："第一步：读取 `templates/Button.tsx` 获取基础结构"）。
* **Constraints（边界约束）**：禁止事项。
* **Quality Checklist（质量检查）**：执行完毕后的自检清单。

**可选增强段（按需添加，示例比描述管用 10 倍）：**

| 可选段 | 价值 | 适用场景 |
|--------|------|---------|
| **Quick Start** | 最小可用示例，让 agent 秒懂怎么用 | 有模板/脚本的技能 |
| **Examples** | 输入/输出配对，示范正确行为 | 输入输出模式固定的技能 |
| **Troubleshooting** | 常见错误与修复，减少 agent 犯错后的盲试 | 容易踩坑的技能 |

> 注意：这些段会占行数。优先保证核心 4 段完整，再考虑是否加可选段。若加了导致超过 350 行，应把 Troubleshooting 移到 `references/errors.md`。

## 四、Subagents 子代理编写原则（独立“外包团队”）

Subagent 是独立上下文的专项执行者。为了防止通过 Task 工具注入 prompt 时直接击穿上下文，必须保持极致的原子化。

### 4.1 核心体积与内联禁令

* **体积弹性范围 100~350 行（v2.5 放宽）**。纯铁律 ≤ 200 行。 < 100 行：过度拆分；> 350 行：必须提取 references/。
* **内联禁令：** 严禁把 `references/` 和 `templates/` 中的已有内容内联到 Agent 文件中。
* **组成要素：** 核心铁律（≤10条） + 骨架工作流 + 输入/输出骨架 + 异常速查表 + 参考链接区。

### 4.2 标准结构

```yaml
---
name: security-reviewer
description: 代码提交前的安全审查。
tools: [Read, Grep]                 # 最小权限原则
permissionMode: read-only
timeout: 120                        # 最大执行秒数
maxIterations: 20                   # 最大循环步数
---

```

* **Communication Protocol（通信协议）**：输出必须为高度结构化的 JSON Lines 或 Markdown 表格，主代理将直接解析该结构，**严禁子代理输出大段散文**。
* **降级与回退**：若子代理超时或连续失败 2 次，自动终止并返回部分结果（`status: partial`），交由主代理决定重试或放弃。

### 4.3 标准三件套模式（分工防撞车）

> 将复杂任务拆解为三道工序，每道由独立子代理执行，互不干扰。

```
Explorer（探索者）         Worker（执行者）          Reviewer（审查者）
─────────────────       ─────────────────        ─────────────────
工具: [Read,Glob,Grep]  工具: [Read,Write,Edit,   工具: [Read,Grep]
权限: read-only          RunCommand]              权限: read-only
                        权限: default
       │                       │                        │
       ▼                       ▼                        ▼
  只读扫描代码库           按文件集分工编辑          对抗性验证
  识别需要改的文件         各干各的不冲突            检查执行者的输出
  输出: 待处理清单         输出: 修改后的文件 +       输出: 通过/不通过 +
        [{file, reason}]        Completion Report      问题清单
```

| 角色 | 职责 | 禁止 |
|------|------|------|
| **Explorer** | 摸清范围，产出待处理文件清单 | 修改文件、下结论 |
| **Worker** | 按文件集分工执行修改 | 跨文件集操作、自审 |
| **Reviewer** | 对抗性验证 Worker 的输出 | 修改文件、放水 |

## 五、跨组件治理与质量度量

### 5.1 规则生效决策树

当不同层级输出不一致时，裁决顺序如下：
**用户即时指令** > **AGENTS.md（宪法）** > **Subagent 自身 Prompt** > **Rules（法律）** > **Skills（手册）**

### 5.2 Reference 目录索引规范（解决盲搜问题）

为了防止 AI 在剥离出的 `references/` 目录中盲目消耗 `Read` 工具的次数，项目根目录必须维护一个轻量级的 `REFERENCES_INDEX.md`，或者采用极度语义化的文件命名（如 `ref_auth_token_refresh.md`），确保 AI 仅凭文件名即可精准抓取上下文。

### 5.3 文档自维护脚本

在仓库根目录配置 `validate_vibe_docs.sh`，挂载至 CI 或 Git Hooks：

1. 校验所有 `AGENTS.md`, `SKILL.md`, `subagents/*.md` 行数是否超过弹性上限（v2.5：地图 300 行 / 纯规范 200 行）。
2. 检测文档中是否非法内联了超过 10 行的代码块（地图型内容如架构图、目录树豁免）。
3. 确保所有子代理声明了 `timeout` 与结构化输出协议。
4. 检查是否存在"无地图的 AGENTS.md"——即缺少技术栈、目录结构或启动命令的 AGENTS.md，给出警告。
5. （v2.5 新增）Rule `.mdc` 文件硬上限 ≤ 120 行；超过则建议拆分为多个 .mdc 或拆 references/。

### 5.4 Context Engineering 5 Pillar 联动（2026-08-14 增量）

> 来源：[external-report 2026-08-14 §M-03](../2026-08-14/external-report.md) + [GitHub Copilot context handling 2026-06](https://github.blog/ai-and-ml/github-copilot/getting-more-from-each-token-how-copilot-improves-context-handling-and-model-routing/)

v2.5 已经覆盖「分层治理 / 地图 vs 规范」。**5 Pillar** 补的是 **"内容质量"维度**——光有结构,没有优质 context 一样失灵。

| Pillar | v2.5 已覆盖? | 增量动作 |
|--------|---------------|----------|
| 1. 项目结构 | ✅ (§5.2 references 索引 / §3.3.1 自检) | 无 |
| 2. 代码风格 | ⚠️ 部分(子代理协作提及) | 在 AGENTS.md §2 加 **命名/缩进/异常处理/提交信息** 4 行约定 |
| 3. 领域知识 | ❌ 缺失 | 新增 §X "Domain Glossary" 章节,列出项目关键术语(SPEC / stage / harness 等) |
| 4. 相关代码示例 | ⚠️ 部分 | rule 文件加 "good / bad" 2 段对比(胜过抽象描述 10×) |
| 5. 反馈循环 | ✅ (Self-improvement loop §1) | 无 |

**反例**:只写角色("你是资深工程师")不写技术栈 → agent 每次重新猜 → 输出漂移。前 30 分钟写好 5 Pillar 远比调 prompt 划算。
