# 反例 2：Clarify 跳过（Skip Clarify Rounds）

> **V11.7.0+ 设计入口**: [AC 核销门禁](../skills/09-review/SKILL.md) · [贾维斯门禁守护](../skills/00-boot/SKILL.md) · 评分制废除 → 门禁制 · 详见 [CHANGELOG.md V11.7.0](../CHANGELOG.md)


> Spec 写之前必走 ≥ 2 轮 AskUserQuestion（每轮 < 4 题）。单轮 = 关键决策点未确认 + Stage 4 Review REJECT。

**违反**：铁律 5（CLARIFY ≥ 2 ROUNDS，每轮 < 4 题）
**严重度**：P1（直接导致 spec.md 含未确认假设 + Stage 3 实施返工）

---

## 现象

```markdown
# spec.md（反例版本）

## 流程记录
Round 1: 问"是否需要用户登录？" → 用户答"是"
→ 立即写 spec.md（含 5 个未确认假设）

# ❌ 反例：单轮 Clarify 就写 spec

# spec.md 含未确认假设：
- 假设 1: 用户名用邮箱
- 假设 2: 密码 8 位以上
- 假设 3: 登录态保持 7 天
- 假设 4: 支持第三方登录（Google/GitHub）
- 假设 5: 登录失败 5 次锁 30 分钟
# ↑ 这 5 个假设未经用户确认 = Stage 3 实施时返工
```

**识别信号**:
- spec.md §流程记录只 1 轮 Clarify
- spec.md 含"假设" / "默认采用" / "通常情况下" 等未确认表述
- Stage 3 实施时发现 5+ 关键决策点未确认 → 返工
- Stage 4 Review 时 reviewer 追问"这条决策谁定的"无法回答

---

## 根因

- **认知维度**：把"spec"当作"快速输出"，把"Clarify"视为"浪费时间"
- **流程维度**：跳过 clarify-checklist.md 决策点矩阵（13 类必问）
- **风险维度**：未意识到单轮 Clarify 的假设 = 实施返工因子

| 根因 | 占比 |
|------|:---:|
| 视 Clarify 为浪费时间（效率错位）| 50% |
| 跳过 clarify-checklist 决策点矩阵 | 35% |
| 未识别"假设 = 实施返工"风险 | 15% |

---

## 教训

- **V11 实战**：spec-writer 单轮 Clarify 就写 spec.md，含 5 个未确认假设。Stage 3 实施时用户答"我们不用邮箱做用户名" → 返工 2 天（数据库 schema + API + 前端表单全部重写）
- **真实场景**：spec-writer 假设"密码 8 位以上"实施后用户答"我们要 12 位以上 + 2FA" → 数据库 password_hash 字段长度 + 前端验证 + 2FA 模块全部返工
- **关键决策遗漏反例**：登录态保持时间、第三方登录、失败锁定策略——这些决策通常需要多轮澄清（涉及产品/安全/法务多方），单轮 = 决策盲区

---

## 正确替代

```yaml
# ✅ 正确：≥ 2 轮 Clarify，每轮 < 4 题

## Round 1: 核心能力澄清（4 题以内）
1. 核心用户场景？
   - 选项 A: 普通用户登录
   - 选项 B: 用户 + 管理员双角色登录
   - 选项 C: 多租户 SSO 登录
2. 认证方式？
   - 选项 A: 仅邮箱密码
   - 选项 B: 邮箱密码 + 2FA
   - 选项 C: 邮箱密码 + 第三方（Google/GitHub）
3. 登录态保持时间？
   - 选项 A: 短期（24h）
   - 选项 B: 中期（7 天）
   - 选项 C: 长期（30 天 + Refresh Token）
4. 主要 INV 约束？（开放问答）
   - 必答项: 失败锁定 / 密码强度 / 会话安全

## Round 2: 边界 + 异常 + 集成澄清（4 题以内）
1. 失败锁定策略？
   - 选项 A: 5 次失败锁 30 分钟
   - 选项 B: 10 次失败锁 24 小时
   - 选项 C: 不锁定 + 验证码
2. 数据存储？
   - 选项 A: 自建 DB（Postgres）
   - 选项 B: 第三方（Auth0 / Clerk）
   - 选项 C: 混合（自建 + 第三方）
3. 国际化？
   - 选项 A: 仅中文
   - 选项 B: 中英文
   - 选项 C: 多语言（含 RTL）
4. 审计日志？
   - 选项 A: 仅登录成功/失败
   - 选项 B: 完整审计（IP / UA / 时间戳）
   - 选项 C: 无审计
```

## clarify-checklist 13 类必问决策点

```yaml
# spec-writer 必走清单
必问决策点:
  1. 核心能力边界（做什么 / 不做什么）
  2. 用户角色 + 权限矩阵
  3. 数据所有权 + 存储位置
  4. 认证 + 授权方式
  5. 关键 INV 约束（资金 / 安全 / 合规）
  6. 失败处理策略（重试 / 降级 / 锁定）
  7. 性能 + 容量预期（QPS / 数据量 / 并发）
  8. 集成第三方（API / SDK / 协议）
  9. 国际化 + 本地化
  10. 审计 + 日志 + 监控
  11. 部署 + 运维 + 灾备
  12. 灰度 + 回滚策略
  13. 未来扩展（v2 / v3 路线图）

每轮 Clarify < 4 题 → 多轮覆盖
未覆盖 → spec.md 写"待确认" → 必在 Round 3 覆盖
```

---

## Stage 4 Review 验证协议

```yaml
# reviewer 必走
1. spec.md §流程记录必含 ≥ 2 轮 Clarify
2. 每轮问题数 < 4 题
3. 每条 Clarify 必有"用户答"具体选项（不是"用户同意"）
4. 仍有 ≥ 3 个未澄清假设 → � REJECT（要求补 Round 3）
5. 关键 INV 决策（资金/安全）无 Clarify 记录 → 🛑 REJECT
6. Clarify 含"用户同意" / "用户默许" 等模糊表述 → 🛑 REJECT（必含具体选项）
```

---

## 反模式识别（V11 实战踩雷）

| 反例类型 | 后果 |
|---------|------|
| 单轮 Clarify 就写 spec | 5+ 假设未确认 → 实施返工 |
| 每轮 > 4 题 | 用户疲劳 → 答案敷衍 |
| Clarify 答"用户同意"无选项 | 🛑 REJECT（必含具体选项） |
| 关键决策无 Clarify 记录 | 🛑 P0 资金/安全盲区 |
| spec.md 含"假设" 表述 | Stage 3 实施时返工 |
