# 原型设计规则 — V5.1 模块化原型文档

> 触发条件：spec 的 BDD 场景涉及用户可见的界面时生效。
> 定位：spec 阶段的扩展产出，让前端实现"看图说话"而非"凭空猜测"。
> 与 `视觉验收.md` 的关系：本规则管"开发前的低保真原型"，`视觉验收.md` 管"开发后的高保真验收"。两者用同一套 ASCII 字符（┌┐└┘├┤│┬┴┼─）形成闭环。

## §0 三层次原型分工

```
层次 1: ASCII 线框图         fullstack spec-writer 负责
                                用 ┌┐└┘├┤│┬┴┼─ 画页面布局
层次 2: 交互说明 + 样式说明   fullstack spec-writer 负责
                                每个可交互元素的行为 + 布局方式
层次 3: 详细视觉设计          移交 ui-ux-pro-max 技能
                                配色/组件库/间距/动效/响应式细节
```

fullstack 只做层次 1+2（低保真），层次 3（高保真）交给 ui-ux-pro-max。**不要在 fullstack 阶段做配色/动效/响应式细节**。

## §1 触发判断

```
spec 的 BDD 场景涉及用户可见的界面吗？
  ├── 是 → 必须产出 prototypes/
  │     ├── prototypes/README.md（索引）
  │     ├── prototypes/{page-name}.md（每个页面一个独立文件）
  │     └── prototypes/{component-name}.md（共享组件单独一个文件）
  └── 否（纯后端/纯 API/纯 CLI）→ 跳过原型，走标准流程
```

## §2 4 条原型铁律

```
1. UI MUST HAVE PROTOTYPE       涉及 UI 必先画原型
2. REAL TEXT NOT PLACEHOLDER    线框图标实际文字，禁止 [按钮] 占位符
3. ALL STATES DRAWN             4 状态齐全（默认/加载中/空数据/错误）
4. MODULAR NOT MONOLITHIC       每个页面/模块一个独立文件，不塞单文件
```

违反任一条 → 退回 spec-writer 重画。

## §3 原型文档 5 段内容

每个 `prototypes/{module}.md` 必须包含：

| 段 | 内容 |
|----|------|
| 1. 线框图 | 4 个状态（默认/加载中/空数据/错误）各画一张 ASCII 图，标实际文字和按钮 |
| 2. 交互说明 | 每个可交互元素：行为 + 关联 spec Scenario + 数据需求 |
| 3. 样式说明 | 布局（flex/grid）+ 响应式断点 + 层级关系 z-index |
| 4. 状态变化 | 状态/触发条件/线框图差异/数据需求 |
| 5. 移交清单 | 移交 ui-ux-pro-max 的设计决策清单（配色/间距/动效等） |

## §4 ASCII 线框图字符集

```
┌ ┐ └ ┘  ─ │  ├ ┤ ┬ ┴ ┼
```

示例（默认状态 — 将页面名称替换为实际产品）：

```
┌─────────────────────────────────────────┐
│  页面标题                       [搜索]   │
├──────────┬──────────────────────────────┤
│ 侧边栏    │ 主内容区域                    │
│ ├ 导航1   │ ┌──────────────────────────┐│
│ │ ├ 子项  │ │ 内容区实际文字             ││
│ │ └ 子项  │ │           [按钮1] [按钮2] ││
│ ├ 导航2   │ └──────────────────────────┘│
│ └ 导航3   │ [输入框...]          [提交]  │
└──────────┴──────────────────────────────┘
```

## §5 与下游衔接

```
spec-writer 产出 prototypes/{module}.md
    │
    ├─▶ contract-writer：从原型推导接口数据需求
    │     │  例如：内容区需要 items[] → contract 加 GET /api/items
    │     └→ 字段/类型/来源直接写入 contracts/api-contracts.md
    │
    ├─▶ ui-ux-pro-max：做高保真详细视觉设计
    │     │  接收 prototypes/ + 移交清单
    │     └→ 产出设计系统（配色/间距/动效/响应式）
    │
    └─▶ implementer：作为前端布局实现参考
          │  编码前必读 prototypes/{module}.md
          └→ 布局/交互/状态 1:1 对照实现
```

## §6 与视觉验收的关系

```
开发前：本规则（原型设计.md）→ 低保真 ASCII 线框图
                                       ↓
开发后：视觉验收.md → vision-audit 输出 diagram 字段（用同一套 ASCII 字符）
                                       ↓
对照：原型 vs 实现 → reviewer 审查 4 维度一致性
       ├── 布局：区域结构是否一致
       ├── 交互：可交互元素行为是否一致
       ├── 状态：4 状态是否齐全
       └── 字段：数据字段是否匹配
```

**铁律**：视觉验收阶段的 `diagram` 字段应参考 spec 阶段的 `prototypes/` 作为验收基准。如果实现与原型布局严重偏离 → reviewer 标记为 🔴 HIGH 漂移。

## §7 检查清单

```
[ ] spec 的 BDD 场景涉及 UI？→ 是则产出 prototypes/
[ ] 每个页面/模块是否独立成一个文件？（不塞单文件）
[ ] 每个原型文件是否有 4 状态？（默认/加载中/空数据/错误）
[ ] ASCII 线框图是否标实际文字？（无 [按钮] 占位符）
[ ] 原型 5 段内容是否完整？（线框图/交互/样式/状态/移交清单）
[ ] 共享组件是否单独成文件？
[ ] 是否产出 prototypes/README.md 索引？
[ ] contract-writer 是否从原型推导字段？
[ ] implementer 编码前是否读取 prototypes/？
[ ] reviewer 是否对照原型 vs 实现做 4 维度一致性审查？
```

## §8 反面范例

```
❌ 涉及 UI 但只写 BDD 场景不画原型
   → contract-writer 猜前端数据需求 → 接口字段缺失/冗余
   → implementer 凭空猜测布局 → 边写边改

❌ 原型用 [按钮] [输入框] 占位符
   → implementer 不知道按钮上写什么文字 → 实现走样

❌ 只画默认状态
   → 加载/空/错误状态由 implementer 自由发挥 → 体验割裂

❌ 所有页面塞一个 prototypes/all.md
   → 文件臃肿难维护 → 修改一处影响全局

❌ fullstack 阶段做配色/动效详细视觉设计
   → 越界 → 应移交 ui-ux-pro-max
```
