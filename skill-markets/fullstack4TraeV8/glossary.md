# 术语表（Glossary）

> AI 请注意：以下大写英文短语和中文专有名词是本技能包的专属概念，不要按字面意思理解，也不要从你训练数据中"联想"含义。每个术语的含义只在本文定义。

---

## 核心方法论

| 术语 | 白话解释 |
|------|---------|
| **DOC FIRST** | 文档比代码优先级高。当文档和代码冲突时，以文档为准修改代码。不是"先写文档再写代码"，而是"文档是真相来源"。 |
| **Contract-First** | 先定义接口长什么样（输入/输出/错误码），再写实现。契约一旦 approved 就不能单方面改。契约 = TypeScript interface + API 端点 + 事件格式。 |
| **Spec-Driven** | 用 BDD 场景（WHEN-THEN）描述系统行为。每个功能一个 spec.md，代码必须通过所有场景。 |
| **TDD** | 红→绿→重构。先写一个失败的测试（RED），写最简代码让它通过（GREEN），再优化代码结构（REFACTOR）。 |
| **feedback-loop** | 反馈回流。发现代码偏离了 spec 或契约时，不是改代码迁就，而是停下当前工作，回上游阶段修正 spec/契约，再继续。 |
| **Kit 复用原则** | 可脚本化的检查不要每次都临时写，沉淀到 `scripts/debug/` 并登记索引，后续直接调用。脚本输出走 Schema Q→A 格式，与 LLM 门禁输出统一可消费。 |

## 流程机制

| 术语 | 白话解释 |
|------|---------|
| **Intake（定位）** | 任何需求的第 0 步。30 秒判断：这是什么类型需求？影响哪些文件？走完整流程还是快速模式？ |
| **Spec 原子化** | Intake 阶段将需求拆解为原子化功能点（不可再分的最小可验证单元），计算与已有 change 的重叠比。≥30% 必须合并而非新建。 |
| **30% 重叠合并** | 新建 change 前检查与已有 change 的原子功能点重叠率。≥30%：合并到已有 change；<30%：允许新建但标注重叠警告。防止 spec 堆积和重复工作。 |
| **状态卡 (.state-card.md)** | 一个持久化的进度文件，记录当前在第几阶段、哪些工件完成、有没有阻塞。Agent 激活时先读它，不用重新推理。 |
| **量化验收** | 用 7 个维度（Spec对齐/契约一致/测试质量/代码质量/文档一致/安全/影响面）打加权分，替代凭感觉说"可以了"。总分 < 4.0 不交付。 |
| **量化汇报** | implementer 完成后必须自评 4 维度（Spec/契约/测试/影响面）+ 给出证据，不能只说"做完了"。 |
| **CONTRACT GATE** | 编码前的检查门禁：contracts/ 目录的 4 个文件必须存在且 approved。 |
| **DOC SYNC GATE** | 编码前的检查门禁：持久文档（docs/modules/）的 P0 内容必须已同步，知识不能只留在施工图纸里。 |
| **Schema QA** | 结构化 Q→A 门禁检查格式。Agent 自生成 Q（不来自固定清单），用 `Q: [分类码][编号][内容][选项][提示]` → `A: [编号][选项][备注]` 格式替代叙事输出。只用于逻辑审查，机械检查走脚本 Kit。 |
| **AOP 自检** | Agent 自身的切面自省机制。PRE（前置条件检查）+ POST（产出后验证），Agent 完成产出后自问 3-8 个 Q，通过后再移交下游。不改 SKILL 文件，是 Agent 的内省行为模式。 |
| **Try-Catch 异常处理** | 基于 report 机制的异常分级处理。L1 文件系统 / L2 Agent执行 / L3 状态不一致 / L4 外部依赖。6 大原则：NEVER SILENT FAIL / RETRY ONCE THEN STOP / FAIL FAST REPORT NOW / NEVER GUESS / STATE CARD IS TRUTH / AOP FIRST REPORT SECOND。 |
| **Cockpit（驾驶舱）** | 双层状态卡机制。项目级 `.state-card.md` + 每个 change 的独立状态卡，Agent 新会话启动时先读状态卡自审计，防止假完成。 |
| **Roundtable（圆桌会议）** | spec 阶段的多角色并发审查。前端经理/后端经理/产品经理/测试经理/用户经理/行业专家 6 个干净上下文子代理并行审查 spec，产出会议纪要。 |
| **调试脚本 Kit** | 项目根目录 `scripts/debug/` 下的可复用检查脚本，处理机械性检查（文件存在、计数、格式校验等）。输出也走 Schema Q→A 格式（分类码 `KIT`），在 `INDEX.md` 中登记索引。 |
| **三层防线** | V7 的 Agent 流水线可靠性保障体系：① AOP 自检（自动拦截可修正问题）→ ② Report Try-Catch（记录不可修正问题、升级给人）→ ③ Schema QA 门禁（结构化硬性检查）。 |

## 工件

| 术语 | 白话解释 |
|------|---------|
| **proposal.md** | "为什么做"+"做什么"+"不做什么"。声明能力和边界。 |
| **spec.md** | 用 WHEN-THEN 格式写的行为契约，描述系统 SHALL 做什么。 |
| **contracts/** | 4 个文件：domain-models.md（数据模型）、api-contracts.md（API 接口）、event-contracts.md（事件）、validation-rules.md（校验规则）。 |
| **design.md** | 编号决策 D1..Dn，每个决策对比备选方案 + 契约一致性检查。 |
| **tasks.md** | [x]/[ ] 勾选清单。implementer 逐项完成并标记。 |
| **原型 (prototypes/)** | ASCII 线框图（用 ┌┐└┘├┤│─ 画布局），涉及 UI 时 spec 阶段产出。 |

## 漂移与回流

| 术语 | 白话解释 |
|------|---------|
| **漂移 (Drift)** | 代码实现偏离了 spec 或契约。4 种类型：Spec漂移、契约漂移、文档漂移、目标漂移。 |
| **回流 (Reflow)** | 发现漂移后的动作：停下当前工作 → 回上游阶段 → 修正 spec/契约 → 重新下游。 |
| **目标对齐度** | 当前产出和 proposal.md 原始目标的匹配百分比。≥90% 继续，70-89% 警告，<70% 强制回流 proposal。 |

## 其他

| 术语 | 白话解释 |
|------|---------|
| **ponytail** | 最简实现模式。能删就删 → 标准库 → 复用 → 简单实现 → 论证后才引入新依赖。小修改走这个，不走流水线。 |
| **GitNexus** | 代码智能分析工具，用于影响面评估和依赖分析。 |
| **Hook** | TRAE IDE 的自动化脚本，在特定事件（会话启动/写代码前/写代码后/停止）执行确定性检查。 |
| **BDD** | Behavior-Driven Development。用 WHEN-THEN 场景描述行为。 |
| **SHALL** | spec 中的关键词，表示"系统必须做到"的硬契约。 |
