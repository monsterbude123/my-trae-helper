# 圆桌会议（V7 NEW）

> 在 spec 阶段引入多角色交叉评审，通过多视角审查让需求方案更稳健。可选，config 控制开关。

---

## 为什么需要圆桌会议

AI 单角色写 spec 容易产生盲区：
- 关注功能实现 → 忽略可测试性
- 关注后端逻辑 → 忽略前端交互
- 关注 happy path → 忽略边界情况
- 关注技术优雅 → 忽略用户心智模型

圆桌会议用**多角色干净上下文的子代理**各自从立场出发审查 spec，发现盲区，交叉验证。

---

## 六角色子代理

每个子代理是独立的 Task agent，**上下文干净**：只接收 proposal + 该能力相关 spec + 相关 modules 文档。不知道其他 change 的存在，不参与项目整体判断（由主 Agent 主持）。

| 角色 | 关注维度 | 典型问题 |
|------|---------|---------|
| **前端开发经理** | 组件复用、UI 一致性、响应式、可达性 | "这个组件能复用已有的吗？""移动端这个布局会不会塌？" |
| **后端开发经理** | API 设计、数据模型、性能、安全 | "这个查询 N+1 吗？""需要加缓存层吗？" |
| **业务产品经理** | 用户价值、业务流程完整性、边界情况 | "用户如果中途取消怎么办？""这个流程有没有循环触发风险？" |
| **测试经理** | 可测试性、边界值、异常路径、E2E 覆盖 | "这个状态变化能自动化测试吗？""并发场景测过了吗？" |
| **用户经理** | 用户体验、操作路径、错误提示、帮助引导 | "报错信息用户看得懂吗？""首次使用需要引导吗？" |
| **业界经验** | 同类产品做法、行业模式、已知陷阱 | "Stripe 的支付流程是这样的...""这个 OAuth 模式已知有 CSRF 风险" |

## 会议机制

### 前置条件

- spec.md 初稿已完成
- config.yaml 中 `roundtable.enabled = true`

### 流程

```
第 1 步：主 Agent 准备输入材料
   → 提取 proposal.md（Why + What + Non-Goals）
   → 提取各 capability 的 spec.md
   → 提取相关 modules 文档

第 2 步：并行启动 6 个子代理（6 个独立 Task）
   → 每个子代理从各自角色立场审查
   → 输出：认可点 + 风险点 + 建议修改

第 3 步：主 Agent 汇总
   → 合并 6 份反馈
   → 标记分歧点（前端经理说 X，后端经理说 Y）
   → 落盘 meeting-notes/round-{N}.md

第 4 步：用户 Review
   → 查看会议纪要
   → 裁决分歧（选 X 还是 Y，还是兼顾）

第 5 步：判断收敛
   ├── 用户说"可以了" → 进入 contract 阶段
   ├── 有重大修改 → 回到 spec 修订 → 可再开一轮
   └── 连续两轮无新实质性分歧 → 自动收敛（如 auto_converge = true）
```

### 收敛条件

- 用户明确说"可以了""继续"
- 或 `auto_converge = true` 且连续两轮角色反馈中无新的"建议修改"项（"认可点"和"风险点"不算新内容）

---

## 配置

```yaml
# config.yaml
roundtable:
  enabled: true         # false = 完全跳过圆桌会议
  max_rounds: 3         # 最多轮次，超过后强制进入 contract
  auto_converge: true   # 连续两轮无新分歧自动收敛
```

## meeting-notes 结构

```
docs/specs/changes/{change}/meeting-notes/
└── round-{N}.md
```

**meeting-notes 不参与 DOC FIRST 文档系统**。它是可选的回溯工具——如果后续有人问"这个设计为什么选了 X 而不是 Y"，可以回溯会议纪要。但模块文档中的最终结论才是唯一事实来源。

## 使用建议

| 场景 | 建议 |
|------|------|
| 新功能开发 + 涉及 UI | 开启 |
| 跨模块重构 | 开启 |
| 纯后端/纯 API | 可跳过 |
| 已有明确实现模式 | 可跳过 |
| 快速原型/实验 | 跳过 |
| 简单 bug 修复 | 跳过 |
