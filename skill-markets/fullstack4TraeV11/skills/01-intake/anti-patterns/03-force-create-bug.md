# 反例 3：强制创建 bug 单

> **V11.7.0+ 设计入口**: [AC 核销门禁](../skills/09-review/SKILL.md) · [贾维斯门禁守护](../skills/00-boot/SKILL.md) · 评分制废除 → 门禁制 · 详见 [CHANGELOG.md V11.7.0](../CHANGELOG.md)


> Stage -1 Intake 必询问用户"是否作为 bug 单录入"，绝不默认创建。

---

## 现象

```
用户: "token 刷新报 500"
主上下文: "已识别为 bug，直接创建 bug-001，开始修复"  # ❌ 未询问
```

或：

```
用户: "我想问一下 token 刷新的问题"  # 用户在咨询
主上下文: "已创建 bug-001，正在排查"  # ❌ 用户没说要修
```

**识别信号**:
- 用户问题被自动归类为 bug
- 未询问"是否作为 bug 单录入？"
- Bug 单创建后用户表示困惑（"我没说要修"）
- Bug 单状态卡与用户意图不符

---

## 根因

| 根因 | 占比 | 说明 |
|------|:---:|------|
| 觉得"报错 = bug" | 55% | 自动归类，不区分咨询 vs 修复 |
| 觉得"用户问就是想修" | 30% | 缺乏对意图边界的判断 |
| 跳过询问节省时间 | 15% | 觉得多此一举 |

---

## 教训

**用户可能只是想咨询，不是要修 bug。强制创建 = 后续维护负担 + 用户被冒犯。**

真实案例（2026-08-08 蒸馏）:
- 用户问"为什么我的 token 刷新这么慢？"（咨询性能问题）
- 主上下文直接创建 bug-001 + 路由到 Stage 6 Bug Fix
- 用户困惑："我没说要修，我只是问为什么"
- 后续需要回退 + 删除 bug 单，浪费 1 小时

---

## 正确替代

```
Step 4: Bug 录入触发词判断
  ├─ 命中问题类触发词（"报错"/"不工作"/"应该 X 但 Y" 等）
  │
  └─ 主上下文必问："看起来像是一个 Bug（命中触发词：'XXX'），是否作为 bug 单录入到 docs/bugs/？
                  录入后会由 Stage 6 Bug Fix 专家处理（含 e2e 先行 + 6 层排查 + TDD 修复）。
                  如果只是想咨询或讨论，请告诉我。"
       │
       ├─ 用户同意 → 走 Bug 录入 6 字段 → 创建 Bug 单
       └─ 用户拒绝 → 按"一般咨询"处理
           ├─ 状态卡 health = 🟡 degraded
           ├─ notes: "用户拒绝 bug 录入，按一般咨询处理"
           └─ 路由: Stage 7 Project Health（异步自检）
```

**MUST**: 询问是否录入 bug 单（不默认创建）。

**NEVER**:
- ❌ 用户拒绝时强制创建
- ❌ 跳过询问直接创建
- ❌ 把"咨询"误判为"修复"（关键：用户的"问一下"≠"修一下"）

---

## 检测方法

主上下文每命中问题类触发词时自检：

```yaml
checklist:
  - [ ] 是否已询问"是否作为 bug 单录入？"？
  - [ ] 用户明确同意？（非"嗯"/"哦"等模糊回应）
  - [ ] Bug 单 6 字段用户答全？（未臆测补全）
  - [ ] 用户拒绝时状态卡 health = 🟡 degraded？
```

任一未勾选 → 触发本反例 → 回到 Step 4 重新询问。

---

## 关键区分（咨询 vs 修复）

| 用户原话 | 真实意图 | 主上下文反应 |
|---------|---------|------------|
| "token 刷新报 500" | 修复 | 询问 bug 录入 → 用户同意 → 创建 |
| "为什么我的 token 刷新这么慢？" | 咨询 | 不创建 bug，直接回答 + 询问是否需要性能分析 |
| "token 刷新不工作了" | 修复（强烈）| 询问 bug 录入（语气更确定）|
| "我想问下 token 刷新" | 咨询 | 不创建 bug，先听用户描述 |
| "token 刷新有问题，能否修一下？" | 修复（明确）| 直接创建 bug（用户明确表态）|
