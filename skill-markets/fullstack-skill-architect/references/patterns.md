## 模式 1:精华/糟粕二元判定表

**触发场景**: 升级/改造任何成熟技能包

**模式结构**:

```markdown
## 精华清单(必保留)
✅ 核心架构: {1 句话}
✅ N Articles 宪法: {N 必填字段}
✅ N stage 流水线: {-1 → 0 → ... → 5}
✅ N 实装脚本: {关键脚本名}
✅ 反虚假交付 N 项: {核心反例}
✅ 灵活度铁律 N: {fidelity 等级 + 偏离理由}

## 糟粕清单(必剔除)
❌ 门禁放水: {现象 + 根因 + 剔除方案}
❌ 验收越界: {同上}
❌ 单卡膨胀: {同上}
❌ 子代理无界: {同上}
❌ 历史残留: {同上}
```

**实战来源**: V11.3 升级会话,精华 6 项 + 糟粕 5 项

## 模式 2:质疑性校验 4 维度(每改必走)

**触发场景**: 任何 P0/P1 改动/修复/升级

**4 维度清单**:

```
[1] 根因验证
  ✅ 引用的章节/SKILL.md 条款真实存在(附 file:line)
  ✅ 失效模式有真实证据(用户反馈 / 日志 / 测试报告)
  ✅ 根因不在更上游

[2] 责任主体校验
  ✅ 修复位置 vs 上游层效果一致
  ✅ 已有别的 skill/rule 不覆盖
  ✅ 改在错误位置会导致什么

[3] 与已有规则重叠校验
  ✅ 现有规则 grep 关键词,命中几处
  ✅ 已覆盖章节的"反向提示词"是否包含新主张
  ✅ 新规则的"差异化"在哪里

[4] 修复成本 vs 价值校验
  ✅ 修复行数(10 行 vs 100 行)
  ✅ 是否破坏 ≤ 10 铁律 ≤ 150 行
  ✅ 是否有更低成本的等价方案
```

**实战来源**: skeptical-validation-protocol.md(从 my-trae-helper V10.12 蒸馏)

## 模式 3:零迁移 opt-in 默认行为

**触发场景**: 升级现成技能包,不想破坏现有项目

**模式结构**:

```
核心原则: 老路径完全不动,新行为作为"可选 opt-in"

3 优先级动作:
  1. 新建独立文档(不动老路径)
     - 新建 references/stage-physical-isolation.md
     - 新建 docs/给验收角色的一封信.md
  2. 修改已有文件(必走质疑性校验)
     - SKILL.md 加 [STAGE_CONFIG] 引用
     - references/ 加索引引用
  3. 删除陈旧文件(必查 0 引用)
     - references/V10-distillation-source-map.md
     - skills/*/anti-patterns/V10-battle-tested.md

升级路径:
  V11.x → V11.x+1: 零迁移(只新增,不改老路径)
  V11.x → V12.0: 破坏性(用户决策)
```

**实战来源**: 本会话第3 轮用户表态"避免文档索引迁移"

## 模式 4:借鉴公开工具的"思路"而非工具本身

**触发场景**: 想引入门禁/隔离/边界等机制,不想引入新依赖

**模式结构**:

```
| 设计需求 | 公开工具 | 借鉴什么 | V12 实现 |
|---|---|---|---|
| 门禁硬化 | husky pre-commit | exit 0/1 硬阻断 | stage-gate-pre-stage.sh |
| 物理隔离 | Docker 镜像层 | 镜像层只读 + 容器层可写 | fact/ vs stage/ |
| 子代理边界 | K8s RBAC | role/namespace 白名单 | doc_whitelist |
| git 重置 | git reset --hard | 保留 HEAD ~ 删 commit | --reset-to stage |
```

**实战来源**: 2026 WebSearch husky v9 / lefthook / pre-commit 对比

## 模式 5:给验收角色的"一封信"(独立文档)

**触发场景**: 验收 stage 越界,需要明确边界

**模式结构**:

```yaml
# 给验收角色的一封信(SKILL)
收件人: Stage X Review 子代理 + 主上下文验收人
发件人: 技能升级组
核心: 像产品经理验收,不像工程师审计

§0 30秒读完: 你是验收者,不是审计者
§1 你必须知道的4件事:
  1.1 边界(do/don't)
  1.2 输入(白名单/黑名单)
  1.3 产出(review-report.md 模板)
  1.4 退出方式(4 步)
§2 反例(不要做的事)
§3 Q&A
§4 你不需要做的事(明确委托)
§5 紧急情况(回到主上下文)
§6 工作流程(8 步)
§7 与主上下文协作
§8 一句话铁律
```

**实战来源**: 本会话第2 轮产出《给验收角色的一封信.md》

## 模式 6:文档管理债务诊断 9 类

**触发场景**: 任何 docs/ 目录爆炸的项目

**模式结构**:

```
债务类别:
  1. 重复目录层级(平铺混乱)
  2. _invalidated/ 历史残留
  3. bak_v8doc 类备份无说明
  4. reports/ 膨胀(无索引)
  5. standards/ vs modules/ 双轨边界模糊
  6. 状态卡膨胀(单卡塞 N stage 信息)
  7. 命名违规(下划线开头无 README)
  8. 双层目录(contracts/ vs specs/contracts/)
  9. 子目录命名不统一

诊断方法:
  - ls docs/
  - 列每个子目录的"用途说明文件存在性"
  - grep "README" 子目录
  - 列 INDEX 索引文件存在性

治理方案:
  - 加 5 个 README(治标,推荐 P3 起步)
  - 拆分状态卡(治本,推荐)
  - 革命性瘦身(治本根治,推荐)
```

**实战来源**: 本会话第4 轮 AIGCMediaDesktop 演练

## 模式 7:精简 vs 革命性 升级决策矩阵

**触发场景**: 技能包臃肿时,选哪种升级路径

**决策矩阵**:

```
| 维度 | 精简(加法) | 革命性(减法) |
|---|---|---|
| 改动类型 | 加 README + 索引 | 删 V 过渡产物 + research/ |
| 体积影响 | +320 行(净增) | -32%(净减) |
| 用户感知 | 文档越来越多 | skill 包瞬间清爽 |
| 风险 | 低(只新增) | 中(删错需回滚) |
| 心智负担 | 高(新旧并存) | 0(清空历史) |
| 适用 | 文档债务小 | 文档债务爆炸 |

推荐: 先革命性瘦身 → 再加必要的 INDEX(瘦身后再加才是真需要)
```

**实战来源**: 本会话第5 轮用户表态"直接革命性升级"

## 模式 8:用户表态信号触发保守方案

**触发场景**: 用户表达"不要 X"或"避免 X"时

**模式结构**:

```
信号词识别:
  - "不要文档索引迁移" → 选零迁移方案
  - "不草率" → 选详细方案
  - "不要新建技能" → 选改造现有技能
  - "直接革命性" → 选减法 > 加法
  - "清爽" → 选瘦身 > 膨胀

响应规则:
  - 不再调 AskUserQuestion
  - 选最保守方案直接做
  - 报告"我做了 X,Y 不做(原因)"
  - 结尾无"要不要"问句
```

**实战来源**: AGENTS.md §3.1 R-3 + my-trae-helper §3 行为规约
