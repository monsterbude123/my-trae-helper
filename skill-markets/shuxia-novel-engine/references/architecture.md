# 亚文化创作引擎 · 统一架构设计

> 从"一致性检查工具"到"小说创作引擎"的完整架构
> 版本: v1.0 · 2026-06-16
> 部署模型: Skill + Scripts + References（先 Skill 驱动，后工程化）

---

## 零、设计哲学

### 0.1 引擎是什么

创作引擎不是"写小说的 AI"。它是一个**约束空间内的可能性管理器**：

| 引擎做什么 | 引擎不做什么 |
|-----------|-------------|
| 验证"这个设定是否自洽" | 替你写正文 |
| 列举"接下来可以发生什么" | 替你选剧情方向 |
| 计算"改这个会影响哪些文件" | 替你改文件 |
| 评分"这段武戏的节奏好不好" | 替你写打斗 |
| 检测"这段是否偏离主题" | 替你定主题 |

### 0.2 核心隐喻：艺术种子 → 自洽世界

用户（作者）携带梦境、认知投射和艺术直觉进入创作——这些是"种子"，已经携带了故事的 DNA。引擎的职责是：

1. **接纳种子**：不拒绝"不合理"的灵感，而是找到让它合理的世界规则
2. **保护光泽**：每个艺术种子的独特质感不能被"为了合理"消解
3. **引导生长**：种子之间的空白区域由引擎计算填补，但填补物必须匹配种子风格
4. **防止自毁**：标记冲突（"这个种子和那个种子在物理上冲突"），但不替用户选择

### 0.3 引擎的边界

引擎假设用户已经提供了：
- **亚文化宪法**（3-7 条不可变公理）：世界的物理/文化/社会铁律
- **角色种子**（核心角色的身份/动机/限制）：每个角色的"可用方法"和"禁用方法"
- **剧情方向**（主线骨架/关键转折/结局锚点）：故事的大致走向

引擎在这些边界内工作。它不会替你定义公理——它帮你检查公理是否被遵守。


### 1.2 数据流

```
作者决策 ──→ L4
              │
              ├──→ L3 评估引擎: 六维评分 / 主题检查 / 审美评分
              │         │
              │         └──→ L1 模拟引擎: 物理可行性
              │                   │
              │                   └──→ L0 知识底座
              │
              └──→ L2 生成引擎: 候选枚举 / 影响面计算
                        │
                        └──→ L0 知识底座
```

### 1.3 三层数据架构

```
人类界面: Markdown 文件
  AI 会话读写 / 作者编辑 / Git 版本控制
        │
        ▼ Python 解析器同步
机器界面: SQLite 数据库
  结构化查询 / 关系完整性 / 批量验证
        │
        ▼ 查询驱动
计算界面: Python 量化引擎
  物理计算 / 战力验证 / 六维评分
```

- **Markdown 是权威源**。所有修改在 Markdown 中进行。
- **SQLite 是查询加速器**。从 Markdown 自动同步。
- **Python 是数学运行时**。硬核计算不依赖 AI 判断。

## 二、六维评估框架（R4）

### 2.1 六个维度

| 维度 | 回答的问题 | 关键数据源 |
|------|-----------|-----------|
| **World** 物理/世界 | 灵压/距离/科技树/灵场是否自洽？ | 物理常量表 / 科技树依赖图 |
| **Society** 社会/文化 | 修真者傲慢/阶级矛盾/文化冲突是否体现？ | 角色.arrogance / 势力表 |
| **Character** 角色/心理 | 行为是否符合动机？情绪转折是否成立？ | 角色.motivation / 行为法则 |
| **Plot** 情节/因果 | 因果链/伏笔/赢面/节奏是否合理？ | 伏笔表 / 战力引擎 |
| **Theme** 主题/哲学 | 是否服务于核心主题？ | 主题信号库 / 偏离检测 |
| **Aesthetic** 情感/审美 | 武戏节奏/文戏温度/画面感如何？ | R7 武戏 / R8 温度 |

### 2.2 评分公式

```
维度分 = Σ(子因子得分 × 子因子权重) / Σ(子因子权重) × 100

场景总分 = Σ(维度权重 × 维度分) / Σ(维度权重)
```

维度权重按场景类型动态调整：

| 场景类型 | World | Society | Character | Plot | Theme | Aesthetic |
|---------|-------|---------|-----------|------|-------|-----------|
| 武戏 | 40% | 5% | 10% | 20% | 5% | 20% |
| 文戏 | 5% | 10% | 30% | 10% | 15% | 30% |
| 揭示 | 25% | 15% | 15% | 20% | 20% | 5% |
| 过渡 | 15% | 10% | 20% | 25% | 10% | 20% |

### 2.3 评估输出

```
场景: ch82 工厂躲藏
类型: 武戏
总分: 95/100 (S级)

维度明细:
  World:  95  ✅ 灵压/科技树/距离全部自洽
  Society: 85 ✅ 敌人傲慢体现明确
  Character: 90 ✅ 行为锚点匹配
  Plot:   95  ✅ 赢面 BORDERLINE→叙事成立
  Theme:  90  ✅ 外物证道/认知差突出
  Aesthetic: 88 ✅ 画面感强(94)，节奏(52)因躲藏型偏低

改进建议:
  - Aesthetic.节奏: 可在躲藏间隙插入 2 个"呼吸点"提升节奏分
```

## 三、涟漪传播引擎（R6）

### 3.1 核心问题

> "改一处设定 → 自动列出所有受影响的概念/文件/章节"

### 3.2 依赖图模型

12 种节点 + 9 种边，从 Schema 自动构建（内存图，不需要持久化图数据库）：

| 节点类型 | 示例 | 来源 |
|---------|------|------|
| 概念 | T1 灵子假说 | concept 表 |
| 科技树节点 | I3 频谱分析仪 | tech_node 表 |
| 角色 | 林岳 | character 表 |
| 势力 | 万象宗 | faction 表 |
| 章节 | 第 82 章 | chapter 表 |
| 文件 | 赛博修真科技树.md | 文件系统扫描 |
| ... | ... | ... |

| 边类型 | 含义 | 来源 |
|--------|------|------|
| depends_on | A 依赖 B 的正确定义 | tech_dependency 表 |
| appears_in | 概念在章节中出场 | concept_chapter_ref 表 |
| constrains | A 的合法行为被 B 约束 | 角色.allowed_methods |
| derived_from | A 从 B 推导而来 | concept.provenance |
| ... | ... | ... |

### 3.3 BFS 分层传播

```
输入: 变更 = (实体ID, 旧值, 新值)

1. 定位锚层 (L0/L1/L2/L3)
2. BFS 向上传播 (锚层→L3)
3. BFS 向下传播 (锚层→L0)
4. 4 跳截断（防止无限传播）
5. 按严重度分级输出

输出:
  BLOCKER:  宪法违规 → 变更被硬闸门拦截
  CRITICAL: 概念定义变更 → 需人工审查
  HIGH:     引用需要更新 → 半自动
  MEDIUM:   叙事需要调整 → 提示
  LOW:      文档需要同步 → 提醒
```

例如将某角色战力从 Z=3500 下调至 2500：

## 四、可能性枚举引擎（R5）

### 4.1 核心问题

> "第 N 章结尾，当前状态为 S。接下来可以发生什么？"

### 4.2 四层约束过滤器

```
可能性空间
    │
    ▼ 第一层: 物理约束
    │ 距离/灵压/能耗/战力比
    │ "主角在 Alpha 节点，严峰在 3km 外 → 不可能在 1 分钟内相遇"
    ├─ 剩余候选: N₁
    │
    ▼ 第二层: 角色约束
    │ 动机/性格/当前情绪/行为锚点
    │ "林岳不会用监控 → 不可能通过摄像头发现主角"
    ├─ 剩余候选: N₂
    │
    ▼ 第三层: 情节约束
    │ 伏笔要求/节奏需求/已承诺事件
    │ "F17 必须在 ch50 前回收 → 候选必须包含 F17 进展"
    ├─ 剩余候选: N₃
    │
    ▼ 第四层: 宪法约束
    │ 不可违反的公理
    │ "灵压不可逆衰退 → 不可能出现'灵气突然恢复'事件"
    └─ 最终候选列表
```

### 4.3 三维评分

每个候选事件 = (事件描述, 触发条件, 结果状态, 评分)

```
总分 = 逻辑分(40%) + 惊喜分(35%) + 主题分(25%)

- 逻辑分: 候选在约束空间内的自洽程度
- 惊喜分: 读者没想到但完全合理的程度（避免"安全但无聊"排第一）
- 主题分: 候选服务于核心主题的程度
```

惊喜分 35% 的权重是关键设计决策——它保证了"最安全但最平庸"的选项不会自动排在第一位。

### 4.4 输出示例（ch82 结尾）

| 候选 | 逻辑 | 惊喜 | 主题 | 总分 |
|------|------|------|------|------|
| 物理陷阱周旋 | 9.2 | 8.0 | 8.5 | **8.7** |
| 三重复合策略 | 8.5 | 8.5 | 7.5 | 8.2 |
| 主动误导孟炽 | 8.0 | 7.5 | 8.0 | 7.8 |
| 纯躲藏 | 9.5 | 4.0 | 6.0 | 6.4 |
| 强行突破 | 4.0 | 7.0 | 3.5 | 4.6 |

## 五、审美引擎

### 5.1 武戏量化（R7）

四维评分模型：

| 维度 | 核心思想 | 关键指标 |
|------|---------|---------|
| **节奏密度 R** | 快/慢/静三态交替，呼吸点是蓄能器 | 连续 3F 无 P = 扣分 |
| **空间利用 S** | 空间是第三方参与者 | 转换质量权重 40% |
| **力量逆转 P** | 不对称锯齿波，每次逆转物理锚定 | 禁止运气/降智逆转 |
| **画面感 V** | 电影分镜映射到文字 | 关键帧密度 1 帧/千字最优 |

综合公式: `QS = w_R·R + w_S·S + w_P·P + w_V·V`，权重由武戏类型动态调整。

### 5.2 文戏温度（R8）

五组件模型：

| 组件 | 公式 | 约束 |
|------|------|------|
| **情感阶梯** | 9 级递进 | 每步跃迁 ≤1 级 |
| **关系状态机** | 状态×触发事件×不可逆转移 | 层级差 → R_score |
| **对话张力** | 权力/情感/信息三维博弈 | 每句 Δ 标注 |
| **留白** | O_ratio = 省略/7 | 最佳区间 0.30-0.45 |
| **温度** | T = T_base + E×R×D×O×80 | 乘法共振，缺一不可 |

### 5.3 主题一致性（R9）

三个核心机制：

1. **主题信号库**（25 个可检测信号）
   - T1 外物证道：科技树使用/量化参数/灵↔电转换...
   - T2 文明碰撞：傲慢被利用/双重视角/结构性盲区...
   - T3 认知差即武器：信息不对等/敌人因无知失败...

2. **偏离检测**（6 类偏离 + 三级严重度）
   - D1 主角光环化 → D6 术语残留
   - 轻微(1 分) / 严重(5 分) / 主题断裂(25 分)

3. **密度模型**（5 种场景的最佳信号密度）
   - 武戏: 12-22 信号/千字
   - T1:T2:T3 理想比例 = 3:2:1

## 七、Skill 部署模型

### 7.1 设计原则

**先 Skill 驱动，再工程化。**

- Skill 阶段：AI 通过 SKILL.md 理解引擎规则，通过 scripts/ 调用工具，通过 references/ 查询设计细节
- 工程化阶段：稳定后抽取核心逻辑为独立 Python 包

### 7.2 目录结构

```
skill-novel-engine/
  SKILL.md                          ← AI 入口：何时调用什么
  scripts/
    check.py                        ← 一致性扫描 + 评分模式
    ripple.py                       ← 涟漪传播
    enumerate.py                    ← 可能性枚举
    evaluate.py                     ← 六维评估
    combat_narrative.py             ← 武戏评分
    drama_narrative.py              ← 文戏温度
    theme_check.py                  ← 主题一致性
  references/
    architecture.md                 ← 本文件
    six_dim_evaluation.md           ← R4 设计细节
    ripple_engine.md                ← R6 设计细节
    enumeration_engine.md           ← R5 设计细节
    combat_model.md                 ← R7 设计细节
    drama_model.md                  ← R8 设计细节
    theme_model.md                  ← R9 设计细节
    constitution_guide.md           ← 宪法编写指南（通用模板）
    schema_guide.md                 ← Schema 设计指南
```

### 7.3 SKILL.md 核心规则

```markdown
## 何时调用引擎

| 作者行为 | 调用工具 | 阶段 |
|---------|---------|------|
| 定义/修改公理 | ripple.py | P0 |
| 定义/修改概念 | ripple.py + check.py | P0-P1 |
| 规划章节内容 | enumerate.py | P2 |
| 写完一个场景 | evaluate.py | P3 |
| 写完武戏 | combat_narrative.py | P3-P4 |
| 写完文戏 | drama_narrative.py | P3-P4 |
| 全局检查 | theme_check.py + check.py | P4 |

## 核心规则

1. 引擎不做最终决策——作者始终是"坍缩者"
2. 引擎不允许无知——违反宪法的操作在 L0 就被拦截
3. 引擎必须解释为什么——每个输出带推理链
4. 引擎权重可调——六维权重按场景类型调整
```

```
  │  抽取: scripts/ → pip-installable package
  │  测试: 单元测试 + 集成测试

  │
  ▼ 成熟后
```

## 九、通用化原则

1. **宪法是注入的，不是内置的**：引擎不知道"灵压不可逆"——它从用户定义的宪法文件中读取
2. **六维权重是配置的，不是硬编码的**：不同的亚文化（科幻/奇幻/言情）可以调整权重
3. **主题信号库是开放的**：用户定义自己的主题和信号
4. **Schema 是模板化的**：`schema.sql` 可作为起点，用户按需增删表
5. **所有公式参数可校准**：惊喜分 35%、留白区间 0.30-0.45 都是默认值，可覆盖
