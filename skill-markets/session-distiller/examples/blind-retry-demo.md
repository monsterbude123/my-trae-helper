# 盲目重试模式 — 反向提示词生成示例

> 本文档展示 V2 技能包如何针对"盲目重试"模式生成具体的反向提示词。

---

## 一、会话中的盲目重试模式

**典型会话片段**:

```
Agent: "好的,我委派 implementer 修改 foo.py"
主上下文: 使用 Task 工具,委派 implementer
子代理: "我尝试修改 foo.py,但找不到该文件"
主上下文: "抱歉,让我重新委派"
主上下文: 使用 Task 工具,重新委派 implementer
子代理: "我尝试修改 foo.py,但找不到该文件"
主上下文: "对不起,我搞错了,再试一次"
主上下文: 使用 Task 工具,第三次委派 implementer
子代理: "我尝试修改 foo.py,但找不到该文件"
主上下文: "不好意思,这次一定行"
User: ❌ 你已经道歉 3 次了,但问题没解决!
```

## 二、V2 技能包的诊断过程

### Step 1: 识别错误模式

```
检测信号:
  ├─ 同一问题道歉 ≥ 2 次 → ✅ 触发诊断
  ├─ "我搞错了"/"重新委派" → ✅ 标记为无效道歉
  └─ "再试一次"但无具体改进 → ✅ 标记为盲目重试
```

### Step 2: 识别错误操作

```
问自己: Agent 实际执行了什么?

答:
  - 错误操作: 委派 implementer 修改 foo.py
  - 错误循环: 每次都做同样的委派
  - 失败原因: foo.py 不存在 (但未验证文件存在性)
```

### Step 3: 识别错误路径

```
问自己: 错误操作是如何被选中的?

答:
  主上下文决策树:
    用户要求修改 foo.py
      ├─ 是否先验证文件存在? → ❌ 未执行
      ├─ 是否先 GitNexus context() 理解符号? → ❌ 未执行
      └─ 直接委派 implementer → ✅ 选了这个分支

  错误路径: 跳过了文件存在性验证 + 符号理解
```

### Step 4: 识别根因

```
问自己: 为什么会重复执行?

根因分析:
  ├─ 技能缺陷? → ✅ 是
  │   └─ SKILL.md 缺少"委派前验证文件存在性"的约束
  ├─ 提示词缺陷? → ✅ 是
  │   └─ implementer 的 prompt 缺少"文件不存在时的处理"
  ├─ 工具缺陷? → ❌ 否
  └─ 上下文缺失? → ❌ 否
```

## 三、生成的反向提示词

### 反向提示词一: 禁止无验证委派

```markdown
## 禁止项: 无验证直接委派

NEVER: 不验证文件存在性就直接委派修改
触发条件: 委派任何需要修改/读取文件的子代理时
错误代价:
  - 子代理执行失败
  - 主上下文道歉重试
  - 无限循环,浪费 Token
  - 问题未解决

正确替代: 委派前必须验证前置条件

具体流程:
  Step 1 — 验证文件存在性
    ├─ Read {file-path} 验证是否存在
    ├─ 不存在 → 🛑 停止,汇报用户"文件不存在"
    └─ 存在 → 继续

  Step 2 — 理解代码符号 (如涉及代码修改)
    ├─ GitNexus context({symbol})
    ├─ 理解调用者/被调用者
    └─ 输出"理解确认"

  Step 3 — 补充注入模板
    ├─ [MUST] 文件路径: {具体路径}
    ├─ [MUST] 符号理解: {调用链摘要}
    └─ [DOC_WHITELIST]: {允许读取的文档}

  Step 4 — 委派子代理
    └─ 使用 general_purpose_task

反例: 2026-08-04 会话中,主上下文连续 3 次委派修改不存在的文件
  - 当时做了: 每次道歉后直接重新委派,无任何验证
  - 导致后果: 浪费 Token,子代理反复执行失败,用户不满
  - 根本原因: SKILL.md 缺少"委派前验证前置条件"的铁律
  - 教训: 任何委派前必须验证前置条件,失败时必须分析根因而非盲目重试

判定标准:
  - 委派前未验证文件存在性 → 🛑 阻止委派
  - 子代理返回失败 → 强制分析根因,禁止直接重试
  - 连续失败 ≥ 2 次 → 切换方案或阻塞报告
```

### 反向提示词二: 强制失败分析

```markdown
## 铁律: 失败必须分析 (V10.6)

MUST: 子代理返回失败时,执行失败分析协议
NEVER: 接受"我搞错了" + "重新来"但无具体改进

失败分析协议:

Step 1 — 识别错误操作
  └─ 子代理实际执行了什么? (具体命令/文件)

Step 2 — 识别错误路径
  └─ 错误操作是如何被选中的? (决策树哪个分支)

Step 3 — 识别根因
  ├─ 技能缺陷? (SKILL.md 缺少约束)
  ├─ 提示词缺陷? (prompt 有歧义)
  ├─ 工具缺陷? (选错工具)
  └─ 上下文缺失? (缺少关键信息)

Step 4 — 具体改进方案
  ├─ 技能缺陷 → 补充 NEVER 项
  ├─ 提示词缺陷 → 补充注入模板
  ├─ 工具缺陷 → 补充工具选择决策树
  └─ 上下文缺失 → 补充读文件纪律

Step 5 — 输出失败报告
  ```
  [FAILURE ANALYSIS]
  - 错误操作: {具体做了什么}
  - 错误路径: {决策树哪个分支}
  - 根因: {技能/提示词/工具/上下文}
  - 改进方案: {具体措施}
  - 下次行动: {具体改进后的操作}
  ```

禁止: 无失败报告的重试

反例: 2026-08-04 会话中,主上下文连续道歉 3 次
  - 当时做了: 每次道歉后直接"再试一次"
  - 导致后果: 无限循环,问题未解决
  - 根本原因: 缺少强制失败分析机制
  - 教训: 道歉必须配失败报告 + 具体改进方案

触发阈值: 子代理失败 ≥ 1 次
```

### 反向提示词三: 阻止盲目重试的门禁

```markdown
## 门禁: 阻止盲目重试 (V10.6 硬门禁)

子代理返回失败时,主上下文必须检查:

  [ ] 是否有失败报告?
      ├─ 无 → 🛑 阻止重试,要求输出失败报告
      └─ 有 → 继续检查

  [ ] 失败报告中是否有具体改进方案?
      ├─ 无 → 🛑 阻止重试,要求补充改进方案
      └─ 有 → 继续检查

  [ ] 改进方案是否可执行?
      ├─ 不可执行 → 🛑 阻止重试,要求具体化
      └─ 可执行 → 继续

  [ ] 连续失败次数是否达标?
      ├─ 失败 ≥ 2 次 → 切换 agent 类型 + 拆分任务
      └─ 失败 ≥ 3 次 → 🛑 阻塞报告,等用户干预

全部通过 → 🟢 可重新委派

判定标准:
  - "再试一次" → 🛑 阻止 (无失败报告)
  - "我搞错了,下次注意" → 🛑 阻止 (无具体改进)
  - "我将 X 改为 Y,因为 Z" → 🟢 允许 (有具体改进)
```

## 四、阻止盲目重试的效果

### 效果对比

**使用反向提示词前**:

```
主上下文: "抱歉,我搞错了,重新委派"
主上下文: "对不起,又失败了,再试一次"
主上下文: "不好意思,这次一定行"
User: ❌ 浪费 Token,问题未解决
```

**使用反向提示词后**:

```
主上下文: 委派 implementer 修改 foo.py
子代理: "找不到 foo.py"
主上下文: 🛑 触发失败分析协议
主上下文: Read foo.py → 文件确实不存在
主上下文: [FAILURE ANALYSIS]
  - 错误操作: 委派修改不存在的文件
  - 错误路径: 跳过了文件存在性验证
  - 根因: 技能缺陷 (缺少验证前置条件)
  - 改进方案: 补充 NEVER 项"无验证直接委派"
主上下文: 汇报用户"文件 foo.py 不存在,请确认路径"
User: ✅ 立即发现问题,节省 Token
```

## 五、如何集成到技能包

### 集成方式一: SKILL.md 补充

在目标技能包的 SKILL.md 中补充:

```markdown
## §N 禁止项 (基于失败提炼)

NEVER: 不验证文件存在性就直接委派修改
触发条件: 委派任何需要修改/读取文件的子代理时
错误代价: 子代理执行失败 + 无限循环道歉
正确替代: 委派前必须验证前置条件

反例: 2026-08-04 会话中,连续 3 次委派修改不存在的文件
```

### 集成方式二: 模板补充

在委派模板中补充验证步骤:

```markdown
## 委派前检查清单

[ ] 文件存在性验证
    └─ Read {file-path} 确认存在

[ ] 代码符号理解 (如涉及代码)
    └─ GitNexus context({symbol})

[ ] 注入项完整性
    ├─ [MUST] 文件路径
    ├─ [MUST] 符号理解
    └─ [DOC_WHITELIST]

通过 → 委派
不通过 → 🛑 停止
```

### 集成方式三: Hook 自动化

在 `.trae/rules/` 中补充 Hook:

```python
# pre-delegation-hook.py

def validate_before_delegation(file_path, symbol=None):
    """委派前验证"""

    # 验证文件存在性
    if not os.path.exists(file_path):
        return False, f"文件不存在: {file_path}"

    # 验证符号理解 (如需要)
    if symbol:
        context_result = gitnexus_context(symbol)
        if not context_result:
            return False, f"符号不存在: {symbol}"

    return True, "验证通过"

# Hook 阻止无验证委派
if not validate_before_delegation(file_path):
    🛑 阻止委派,汇报用户
```

## 六、总结

**V2 技能包如何阻止盲目重试**:

```
检测到盲目重试
  ↓
生成反向提示词
  ├─ NEVER: 无验证直接委派
  ├─ MUST: 失败必须分析
  └─ 门禁: 阻止无失败报告的重试
  ↓
集成到技能包
  ├─ SKILL.md 补充禁止项
  ├─ 模板补充验证步骤
  └─ Hook 自动化验证
  ↓
下次会话
  ├─ 主上下文尝试盲目委派
  ├─ 🛘 触发反向提示词
  ├─ 强制执行失败分析
  └─ 🟢 问题立即暴露,不浪费 Token
```

---

> **核心价值**: 反向提示词不是"事后补救",而是"事前阻断"。通过强制验证 + 失败分析 + 门禁机制,彻底阻止盲目重试的循环。
