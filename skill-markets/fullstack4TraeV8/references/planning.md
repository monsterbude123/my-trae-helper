# planning.md — 规划工作流（V3）

> 用于 fullstack-planner Agent。V3 核心新增：产出结构化 design.md（编号决策）。

---

## 核心原则

```
fullstack-planner 的第一身份是"文档同步者"——先确定需要创建/更新哪些文档，再基于文档思考方案。
```

---

## 五步流程（严格顺序）

```
Step 1: 文档影响面识别（必须先做）
    ↓
Step 2: 创建/更新模块文档草稿（必须先做）
    ↓
Step 3: 苏格拉底式需求澄清（基于 Spec 追问）
    ↓
Step 4: 方案设计（2-3 方案 + 编号决策）
    ↓
Step 5: 实施计划（2-5 分钟粒度 tasks.md）
    ↓
输出: design.md + tasks.md
```

---

### Step 1: 文档影响面识别

从 proposal 和 specs 出发，判断本次需求涉及哪些文档：

```markdown
## 1. 文档影响清单

| 文档 | 动作 | 变更内容 | 同步优先级 | 同步时机 |
|------|------|---------|----------|---------|
| docs/modules/{module}.md | 创建 | {描述} | P0 | 编码前 |
| docs/modules/{existing}.md | 修改 | {描述} | P0 | 编码前 |
| docs/ARCHITECTURE.md | 修改 | {描述} | P2 | 编码后 |
```

**优先级**：P0(编码前) → P1(编码中) → P2(编码后) → P3(迭代结束)

---

### Step 2: 模块文档草稿

新模块 → 创建 `docs/modules/{module}.md` 骨架（接口契约 + 数据模型 + 依赖）。
已有模块 → 在现有文档基础上标注本次变更部分。

---

### Step 3: 苏格拉底式需求澄清

基于 Spec 中未覆盖的细节追问。五类问题：
1. 背景与目标
2. 范围
3. 用户故事
4. 业务规则与边界
5. 验收标准

---

### Step 4: 方案设计

#### 4.1 编号决策（V3 核心）

每个技术决策编号（D1, D2...），附备选方案对比表：

```markdown
### D1. {决策标题}

**背景**: ...
**决策**: ...
**备选方案**:
| 方案 | 优点 | 缺点 | 风险 |
|------|------|------|------|
| A: {...} | {...} | {...} | {...} |
| B: {...} ✅ | {...} | {...} | {...} |
**理由**: ...
```

**决策数量指南**：
- 简单变更：1-2 个决策
- 中等变更：3-5 个决策
- 复杂/架构变更：5-8 个决策

#### 4.2 整体方案对比

| 维度 | A: 保守 | B: 平衡（推荐）| C: 激进 |
|------|---------|---------------|---------|
| 改动范围 | ... | ... | ... |
| 实现成本 | ... | ... | ... |
| 风险 | ... | ... | ... |

---

### Step 5: 实施计划（tasks.md）

```
## 1. 基础设施层
- [ ] 1.1 {任务描述} (30min)
- [ ] 1.2 {任务描述} (45min)

## 2. 业务核心层
- [ ] 2.1 {任务描述} (60min)
- [ ] 2.2 {任务描述} — **用户驱动** (外部依赖)

## 3. API/网关层
- [ ] 3.1 {任务描述} (30min)
```

**任务粒度**：每个 30 分钟-2 小时。外部依赖显式标注。

## 特殊模式

### 架构模式

触发条件：用户说"架构"/"技术选型"/"重构"；影响评估 HIGH/CRITICAL。

增项：
- ADR 记录（可选，记录到 design.md 的决策章节）
- 非功能需求分析（性能/可用性/安全）
- 权衡分析（至少 2 方案，含成本/风险/时间）

### 迷雾消除

触发条件：开发现有模块但模块文档缺失。

流程：分析代码 → 汇报迷雾范围（完全/部分/轻微）→ AI 推断 + 用户确认 → 反推生成 `docs/modules/{module}.md` → 进入正常规划。

---

## 输出规范

设计完成后，按 design.md 模板输出，文档影响清单必须排第一：

```markdown
# 规划报告: {变更名称}

## 1. 文档影响清单（第一位）
## 2. 架构决策 (D1..Dn)（第二位）
## 3. 方案对比
## 4. 架构设计
## 5. 迁移计划
## 6. 风险矩阵
## 7. Tasks（见 tasks.md）

---
**🛑 WAITING FOR CONFIRMATION**
```
