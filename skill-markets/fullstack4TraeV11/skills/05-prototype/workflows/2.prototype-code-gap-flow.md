# 原型代码 GAP 流程（Prototype-Code Gap Flow）

> Stage 1.5 Prototype 子流程。代码原型可反向追溯 spec.md AC，识别 spec 不全 / prototype 越界两类 GAP。

---

## 流程图

```
[prototype 已构建 + data-ac 标注完成]
   ↓
[Step 1] prototype-reverse-spec（代码 → AC 反查）
   ↓
[Step 2] 缺失 UI 元素 → spec 不全报告
   ↓
[Step 3] 多余 UI 元素 → prototype 越界报告
   ↓
[Step 4] GAP 报告模板产出
   ↓
[Step 5] spec-writer 反馈回路（修正 spec.md 或回退 prototype）
```

---

## Step 1：prototype-reverse-spec

**目标**：从代码原型反查 spec.md AC，建立双向追溯。

**方法**：
- 扫描 `prototypes/` 下所有 HTML 元素 `data-ac` 属性
- 与 `docs/specs/changes/{change-id}/spec.md` 的 AC 列表比对
- 输出 3 类映射表：

| 状态 | 含义 | 数量 |
|------|------|------|
| ✅ 已覆盖 | AC ID 在 prototype 中有对应元素 | N |
| ❌ 缺失 | spec 有 AC 但 prototype 无元素 | M |
| ⚠️ 多余 | prototype 有元素但 spec 无 AC | K |

**工具**（Node 脚本示例）：
```javascript
const { chromium } = require('playwright');
const browser = await chromium.launch();
const page = await browser.newPage();
await page.goto('http://localhost:1420/prototype');
const acs = await page.$$eval('[data-ac]', els => els.map(e => e.dataset.ac));
console.log('prototype ACs:', acs);
```

## Step 2：缺失 UI 元素 → spec 不全报告

**识别信号**：M > 0（spec 有 AC 但 prototype 无元素）。

**根因 2 种**：
- (a) spec 描述模糊，prototype-agent 无法理解 → spec 需细化
- (b) prototype-agent 实现遗漏 → prototype 需补全

**处置**：
```
报告: spec-insufficient.md
- AC 列表: [AC-1, AC-3, AC-7]
- 根因: 推测 (a) 还是 (b)（必填）
- 建议: spec 细化 OR prototype 补全
```

## Step 3：多余 UI 元素 → prototype 越界报告

**识别信号**：K > 0（prototype 有元素但 spec 无 AC）。

**根因 2 种**：
- (c) prototype-agent 自作主张添加（违反铁律 1 双源一致）
- (d) spec 遗漏（应补 AC）

**处置**：
```
报告: prototype-overreach.md
- 元素列表: [selector1, selector2]
- 根因: 推测 (c) 还是 (d)（必填）
- 建议: 移除元素 OR 补 AC 到 spec
```

## Step 4：GAP 报告模板

**输出文件**：`docs/specs/changes/{change-id}/prototype-gap-report.md`

**模板**：
```markdown
# Prototype-Code GAP Report — {change-id}

## 总览
- AC 覆盖: {N}/{total}
- 缺失 AC: {M}
- 多余元素: {K}

## 缺失 AC 详情
| AC ID | spec 描述 | 推测根因 | 建议处置 |
|-------|-----------|----------|----------|
| AC-3 | 用户点击头像展开菜单 | (a) 描述模糊 | spec 加交互说明 |

## 多余元素详情
| 选择器 | 元素类型 | 推测根因 | 建议处置 |
|--------|----------|----------|----------|
| .theme-toggle | 按钮 | (c) agent 自加 | 移除 |

## 反馈回路
- [ ] spec-writer 收到报告并更新 spec.md
- [ ] prototype-agent 收到反馈并修正 prototype
- [ ] 重跑 Step 1 确认 M=0 + K=0
```

## Step 5：spec-writer 反馈回路

**触发条件**：M > 0 或 K > 0。

**回路流程**：
```
1. prototype-agent 提交 GAP 报告
2. spec-writer 接收 → 评估根因 (a/b/c/d)
3. 若 (a)/(d) → 修正 spec.md（新增/细化 AC）
4. 若 (b)/(c) → 反馈给 prototype-agent 重做
5. 重跑 Step 1（不超过 3 轮，超出则升级到主上下文决策）
```

**收敛条件**：M = 0 且 K = 0 → GAP 报告归档 → 进 Stage 2 Contract。

## 反例

### 反例 A：把 prototype 当实现（引 anti-patterns/03）

```
prototype-agent: prototype 直接交付给 impl-agent 当作生产代码
                          ↑ ❌ prototype 是验证工具，非最终产物
正确: prototype 仅用于双源校验 + GAP 识别，不可作为 Stage 3 实现起点
```
详见 [anti-patterns/03-prototype-as-impl.md](../anti-patterns/03-prototype-as-impl.md)。

### 反例 B：跳过 GAP 报告直接进 Stage 2

```
prototype-agent: "看起来差不多" → 直接通知 spec-writer 进 Contract
                          ↑ ❌ 未走 prototype-reverse-spec，无可追溯证据
正确: Step 1-4 全走 + GAP 报告 M=0/K=0 才进 Stage 2
```
