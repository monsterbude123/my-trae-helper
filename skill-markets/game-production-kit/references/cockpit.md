# Cockpit 驾驶舱

> 参照 fullstack4TraeV7 Cockpit 模式，适配游戏制作的 97% 变更率场景。
> 解决"素材跟设计脱节 + 断连后不知道做到哪 + 临时改方向丢上下文"三大痛点。

---

## 设计动机

来自游戏开发实战教训：

- **素材脱节**：story-design.md 改了角色发色，但 asset-manifest 不知道，门禁也不检查版本。素材跟设计版本脱钩。
- **重入困难**：用户断连后重连，Agent 不知道"上次做到哪个阶段、哪批素材已生成、哪个素材对应哪个版本的设计"。
- **方向调整丢上下文**："这个场景氛围不对，换昏暗一点"——只改了一句设计，但不知道影响多少素材。

Cockpit 通过**单层状态卡 + 版本对比**解决这三个问题。

---

## 状态卡架构

游戏制作是单项目单流水线（不像 fullstack 有多个并行 change），使用单层状态卡：

```
{game_key}/.project-state-card.md     # 游戏驾驶舱：唯一状态源
```

### 为什么不双层

```
fullstack:  项目级 Cockpit + per-change 状态卡（多个 change 并行）
game kit:   一个游戏 = 一个 change，不需要项目级/diff 双层
```

如果后续支持"一个项目多个并行变更"（如同时开发多个引擎版本），再升级到双层。

```markdown
| 素材 | 类型 | source_version | 当前设计版本 | 状态 |

- (无)

```

### 版本对比逻辑

门禁/重入时对比 `素材.source_version` vs `story-design.md 当前版本`：

| 状态 | 条件 | 含义 |
|------|------|------|
| ✅ | source_version == 当前设计版本 | 素材与设计一致 |
| ⚠️ | source_version < 当前设计版本 | 素材可能过时，检查影响范围 |
| 🛑 | 素材不存在 or source_version 无法追溯 | 缺失，需要重新生成 |

## 新会话自检流程

```
Agent 在新会话激活时：

1. 读 {game_key}/.project-state-card.md
   → 输出驾驶舱快照

2. 对照文件系统验证：
   a. story-design.md 是否存在 + 版本号是否匹配
   b. asset-manifest.md 是否存在
   c. 素材版本追踪表中每个文件是否实际存在
   d. 设计变更日志中每项影响范围的素材是否已更新

3. 如果状态卡声称 ✅ 但文件不存在
   → 标记 ⚠️ 状态失真
   → 修正状态卡

4. 如果状态卡不存在
   → 询问用户："检测到未初始化的游戏项目，从哪个阶段开始？"
     A) Phase 0: 选引擎
     B) Phase 1: 剧情设计
     C) 已有设计文档，从素材管线开始
     D) 已有素材，直接脚本编写
```

## 方向调整协议（Pivot）

游戏开发中临时改方向是常态。Cockpit 支持三种调整粒度：

| 粒度 | 示例 | 影响 | Cockpit 动作 |
|------|------|------|-------------|
| 视觉微调 | 发色红→深棕 | 该角色立绘需重新生成 | 标记 ⚠️ 该角色素材 → 询问用户 |
| 设计调整 | 新增一个结局分支 | 新增场景 + TTS | 在状态卡中追加变更日志 → 追加素材清单 |
| 引擎换型 | WebGAL → Ren'Py | 脚本全部重写 | 状态卡引擎字段更新 → Phase 3 从头开始 |

方向调整后：
1. 在设计变更日志中追加一行
2. 素材版本追踪表中标记受影响素材为 ⚠️
3. 更新"下一步"
4. 不回退已完成阶段（已生成的立绘可能仍可用）

## 状态卡生命周期

```
Phase 0 完成 → 创建状态卡（引擎+路由）
Phase 1 完成 → 更新剧情设计版本
Phase 2 进行中 → 每批素材生成后更新素材追踪表
Phase 4 门禁 → 更新门禁结果
新会话开始 → 先读状态卡（自检）
方向调整 → 追加变更日志 + 标记受影响素材
项目完成 → 状态卡归档
```
