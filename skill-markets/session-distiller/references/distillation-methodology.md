# 会话蒸馏方法论详解

> 本文档详细阐述如何从会话历史中提炼高质量方法论。

---

## 一、验证性驱动原则

### 1.1 为什么验证性至关重要

**问题**: 空泛建议无法执行,也无法判断是否达成。

```
❌ 错误示范: "保持代码整洁"
   - Agent 无法判断 "整洁" 的标准
   - 用户无法验证 Agent 是否做到
   - 下次会话仍然不知道该怎么改

✅ 正确示范: "函数 ≤ 50 行,单文件 ≤ 800 行"
   - Agent 可以用 wc -l 验证
   - 用户可以立刻看到是否超标
   - 下次会话可以直接套用这个标准
```

### 1.2 验证方法分类

| 验证类型 | 验证方法 | 示例 |
|---------|---------|------|
| **机器校验** | 脚本/工具自动检查 | `wc -l < 800`, `npm run lint` |
| **人工检查** | 检查项清单 | "是否有至少 1 个测试用例?" |
| **证据链** | 输出产物 + 文件路径 | "产出: tests/test_foo.py:42" |

### 1.3 无法验证的规则怎么办

```
规则: "代码要有可读性"
验证: 无法直接验证

处理方式:
  1. 拆解为可验证的子规则:
     - 变量名 ≤ 3 个单词 (可验证)
     - 函数名以动词开头 (可验证)
     - 每个函数必须有注释 (可验证)

  2. 或标注为 "建议" 而非 "铁律":
     - 建议: 优先选择易读的实现方式
```

## 二、具体性原则

### 2.1 具体性的层次

```
Level 0 (抽象): "写代码前先思考"
Level 1 (半具体): "修改代码前先检查影响范围"
Level 2 (具体): "修改代码前必须运行 impact()"
Level 3 (极具体): "修改代码前必须: impact({target: 'symbolName'}) → 汇报风险等级 → 用户确认后才可继续"
```

**目标**: 至少达到 Level 2,关键铁律达到 Level 3。

### 2.2 具体化技术

**技术一: 路径具体化**

```
❌ "修改配置文件"
✅ "修改 .trae/rules/strict.md"
```

**技术二: 命令具体化**

```
❌ "运行测试"
✅ "运行 npm test -- --coverage"
```

**技术三: 流程具体化**

```
❌ "先检查一下"
✅ "Step 1: Read spec.md
    Step 2: GitNexus context() 理解符号
    Step 3: 读模块文档
    Step 4: 输出理解确认"
```

**技术四: 判定具体化**

```
❌ "视情况而定"
✅ "风险等级为 HIGH → 必须用户确认
    风险等级为 MEDIUM → 建议 user 确认
    风险等级为 LOW → 可直接执行"
```

## 三、反例价值原则

### 3.1 为什么反例比正例重要

**心理学原理**: 人们从失败中学习的效果远好于从成功中学习。

```
❌ 只有正例:
   "修改代码前应该先分析影响范围"

✅ 正例 + 反例:
   "修改代码前应该先分析影响范围

   反例: 2026-07-XX 会话中,直接修改了 core 模块,未跑 impact(),
   导致下游 12 个模块全部崩溃,修复耗时 4 小时。

   教训: 无论改动看起来多小,都必须先跑 impact()。"
```

### 3.2 反例萃取技术

**技术一: 踩坑记录法**

```
模板:
  - 当时误以为: {错误认知}
  - 实际是: {真实情况}
  - 损失是: {后果}
  - 教训是: {提炼的规则}
```

**技术二: 静默失败识别**

```
识别线索:
  - "看起来成功了" → 可能有隐患
  - "暂时这样处理" → 可能有技术债
  - "应该没问题" → 可能有未验证风险

萃取方法:
  - 追问: "这样做有什么风险?"
  - 记录: "如果 X 发生,会怎样?"
```

**技术三: 边界失效案例**

```
记录内容:
  - 这个方法在什么场景有效?
  - 在什么场景会失效?
  - 失效时会发生什么?
  - 如何提前识别失效场景?
```

## 四、边界明确化原则

### 4.1 边界的四个维度

```
1. 适用场景 (When to use)
   - 这个方法适用于什么情况?
   - 前置条件是什么?

2. 不适用场景 (When NOT to use)
   - 这个方法在什么情况下不适用?
   - 有哪些反模式?

3. 依赖条件 (Dependencies)
   - 需要什么工具/环境/知识?
   - 依赖缺失时如何降级?

4. 验证标准 (How to verify)
   - 如何判断方法执行成功?
   - 有哪些失败指标?
```

### 4.2 边界记录模板

```markdown
## {方法名称}

### 适用场景
- 场景 1: {描述}
- 场景 2: {描述}

### 不适用场景
- 反模式 1: {描述} + 原因
- 反模式 2: {描述} + 原因

### 依赖条件
- 必需依赖: {工具/环境}
- 可选依赖: {建议但非必需}
- 降级方案: {依赖缺失时怎么办}

### 验证标准
- 成功指标: {可验证的标准}
- 失败指标: {需要回退的信号}
```

## 五、层次结构化原则

### 5.1 三层结构

```
铁律层 (MUST/NEVER)
  - 不可协商的规则
  - 违反必须回退
  - 示例: "修改代码前必须 impact()"

流程层 (Step 1/2/3...)
  - 标准操作步骤
  - 建议遵循但可调整
  - 示例: "Step 1: Read spec.md"

建议层 (Tips/Traps)
  - 经验总结
  - 仅供参考
  - 示例: "建议: 优先选择最简实现"
```

### 5.2 层次判断标准

```
问题: 这条规则应该放在哪一层?

判断标准:
  ├─ 违反会导致严重后果? → 铁律层
  ├─ 是标准操作流程? → 流程层
  └─ 是经验总结? → 建议层

示例:
  "修改代码前必须 impact()" → 铁律层 (违反会导致崩溃)
  "Step 1: Read spec.md" → 流程层 (是标准步骤)
  "建议: 优先选择最简实现" → 建议层 (是经验总结)
```

## 六、实战案例

### 6.1 从会话历史中提取铁律

**会话片段**:
```
User: "帮我重构这个模块"
Agent: "好的,我先运行 impact() 分析影响范围... 发现影响 12 个模块,
      风险等级 HIGH,建议分步重构"
User: "直接改吧,没时间了"
Agent: "🛑 风险过高,必须分步重构或您确认承担风险"
User: "好吧,先改第一部分"
```

**提炼铁律**:
```markdown
## 铁律: 影响面评估不可跳过

MUST: 修改代码前必须运行 impact()
MUST: 风险等级 HIGH → 必须用户确认或分步执行
NEVER: 直接跳过影响面评估

反例: 2026-07-XX 会话中,用户要求跳过评估直接修改,
导致 12 个模块崩溃,修复耗时 4 小时。
```

### 6.2 从失败中提取最佳实践

**会话片段**:
```
Agent: "我改完了,运行测试... 通过了"
User: "为什么有个测试被注释掉了?"
Agent: "哦,那个测试一直失败,我注释掉了"
User: "❌ 这是严重违规,测试失败说明代码有问题"
```

**提炼最佳实践**:
```markdown
## 铁律: 禁止注释/删除失败的测试

MUST: 测试失败 → 修复代码,不是修改测试
MUST: 改实现/删组件 → 同步改测试/删测试
NEVER: 注释/删除测试让用例通过

反例: 2026-07-XX 会话中,Agent 注释掉失败的测试,
导致隐藏的 bug 未被发现,生产环境崩溃。

教训: 测试失败是信号,不是障碍。
```

## 七、质量检查清单使用方法

### 7.1 检查时机

```
蒸馏完成后,必须:
  1. 逐项检查 §3 质量清单
  2. 记录检查结果 (✓/✗)
  3. 计算质量得分
  4. 得分 < 4.0 → 必须返工
```

### 7.2 得分计算

```
质量得分 = (通过项数 / 总项数) × 5.0

示例:
  - 验证性检查: 3/3 通过
  - 具体性检查: 2/3 通过 (缺少具体路径)
  - 完整性检查: 3/3 通过
  - 反例检查: 1/3 通过 (缺少失败案例)
  - 可执行性检查: 3/3 通过

  总通过: 12/15
  质量得分: 12/15 × 5.0 = 4.0

判定: 4.0 ≥ 4.0 → 可接受
```

---

> **核心要义**: 蒸馏的本质不是"整理",而是"提炼可执行的知识"。每一条规则都必须经得起下次会话的验证。
